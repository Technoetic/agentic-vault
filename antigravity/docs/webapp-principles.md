# 웹앱 제작 원칙 / Webapp development principles

웹앱을 만들거나 수정·검토할 때 적용하는 여섯 가지 개발 규칙이다. Claude Code와
Codex가 같은 기준을 읽도록 [webapp-principles 스킬](../skills/webapp-principles/SKILL.md)에서
이 문서를 참조한다. 볼트 밖의 일반 프로젝트에서도 사용할 수 있다.

현재 사용자의 명시적 요청과 프로젝트 정책을 우선하고, 이미 선택한 작업 흐름과
프레임워크를 따른다. 기존 구조가 같은 책임을 충족하면 그 방식을 유지한다.
이 문서를 읽는 것만으로 설치·배포·호스트 설정 변경·볼트 초기화·노트 저장이
승인되지는 않는다. 읽기 전용 검토는 발견 사항과 근거를 보고하는 범위로 진행한다.
일반 노트의 웹사이트 언급이나 웹 개념 설명만으로 앱 작업을 시작하지 않는다.

## 1. JavaScript를 책임별 모듈로 나눈다 / Responsibility-based modules

진입점은 초기화와 연결을 맡고, 화면 모듈은 화면 상태와 표현을, 서비스는 API·저장소
접근을, 공통 모듈은 재사용 가능한 작은 기능을 맡는다. 한 파일에 모든 화면·통신·상태를
계속 추가하지 않는다. 모듈 사이의 입력·출력과 의존 방향을 명확히 한다.

개발 소스의 분리와 배포 파일 수는 별개다. 여러 JS 모듈을 번들링해 하나의 HTML로
배포할 수 있다. 이미 사용하는 번들러·프레임워크의 모듈 구조를 활용하고 이 규칙만을
위해 빌드 도구나 실행 의존성을 추가하지 않는다.

## 2. CSS 토큰·기본 스타일·컴포넌트를 분리한다 / Layered styles

색·간격·타이포그래피 같은 디자인 토큰, 요소의 기본 스타일, 화면·컴포넌트 스타일을
개발 소스에서 구분한다. 반복되는 값을 토큰으로 모으고 컴포넌트의 영향 범위를
제한한다. 이미 쓰는 CSS modules, utility CSS, CSS-in-JS 등 프로젝트 스타일 체계가
이 책임을 충족하면 그대로 사용한다. 배포 시 CSS를 합치거나 HTML에 포함해도 된다.

## 3. 화면·서비스의 책임 경계를 클래스로 표현한다 / Screen and service boundaries

별도 관례가 없는 새 코드에서는 화면과 서비스를 책임별 클래스로 구성한다.
예를 들어 `OrdersScreen`은 표시·이벤트·화면 수명주기를, `OrdersService`는 조회·저장을
맡는다. 화면 해제 시 이벤트·요청을 정리하고, 서비스가 DOM이나 화면 이동을 직접
소유하지 않도록 경계를 정한다.

사용자 지시나 프로젝트·프레임워크가 함수 컴포넌트, hooks, composables 같은 방식을
정했다면 같은 책임을 그 방식으로 분리한다. 클래스 문법을 맞추기 위해 기존 앱을
재작성하지 않는다. 검토에서는 책임과 상태의 소유자가 명확한지 확인하고 적용한
프로젝트 예외를 기록한다.

## 4. async/await로 데이터와 렌더링 순서를 관리한다 / Async loading and rendering

데이터가 필요한 렌더링은 해당 I/O의 완료를 기다리며 loading·empty·success·error를
구분한다. HTTP 실패 상태와 응답 형식 오류를 처리하고, 사용자가 재시도할 수 있게 한다.
독립 요청은 병렬로 처리할 수 있지만 앞선 결과에 의존하는 작업은 순서를 보장한다.

느린 이전 요청이 최신 화면을 덮어쓰지 않도록 취소 또는 요청 식별자를 사용한다.
화면이 해제되었거나 더 최신 요청이 완료되었다면 오래된 결과를 반영하지 않는다.
저장은 진행 상태와 실패를 추적하고 실패한 저장을 완료로 표시하지 않는다. 기존
프레임워크의 비동기 데이터·취소 기능이 이 책임을 맡으면 이를 활용한다.

## 5. 단일 진입점과 화면 URL을 함께 제공한다 / Single entry and navigable screens

앱의 진입점은 하나로 두고 각 화면에는 공유 가능한 URL을 부여한다. URL을 앱 상태로
해석하고 화면 이동을 주소와 동기화한다. 직접 연 deep link와 해당 URL의 새로고침,
브라우저 Back/Forward가 모두 같은 화면을 복원해야 한다. 기존 라우터나 서버의
프레임워크 진입점을 활용하며 별도 라우터로 교체하지 않는다.

서버의 앱 셸 fallback은 실제 화면 경로에 적용한다. 없는 JS/CSS/이미지 같은 정적 자산과
API 요청에 HTML을 200으로 반환해 404를 숨기지 않는다. 알 수 없는 화면 경로의 처리도
프로젝트 정책에 맞게 정의한다. 루트 경로에서만 동작하는지 확인하는 것으로 끝내지 않는다.

## 6. 강력 새로고침 없이 새 배포를 적용한다 / Safe deployment updates

목표는 새 배포 후 사용자가 hard refresh를 하지 않아도 새 앱 코드를 받는 것이다.
HTTP 캐시를 설정하는 일과 이미 실행 중인 문서를 교체하는 일은 둘 다 필요하다.
`no-store` 헤더만 바꿔도 열린 탭의 메모리에 올라온 JavaScript는 교체되지 않는다.

### 배포 식별자와 캐시 / Build identity and HTTP cache

- **현재 실행 버전:** 로드된 HTML의 메타 정보나 그 HTML에 대응하는 번들에 build ID를
  포함한다. 페이지 시작 뒤 서버 최신 버전을 fetch해서 이를 현재 실행 버전으로 삼지
  않는다. A 문서가 열린 직후 B가 배포되면 A가 자신을 B로 오인할 수 있기 때문이다.
- **서버 배포 버전:** 같은 출처의 버전 엔드포인트나 동등한 프레임워크 기능으로 새 값을
  조회한다. 엔드포인트와 요청의 캐시 정책을 새 응답을 얻도록 맞추고 응답 상태·형식을
  검증한다. 비교는 `serverBuild !== loadedBuild`처럼 **동일성**으로 판단한다.
  B에서 A로 롤백해도 다른 배포다. 버전의 대소·시간 순서로만 비교하지 않는다.
- **진입 HTML:** 매 요청 재검증하는 `Cache-Control: no-cache`와 ETag 조합 또는
  적절한 `Cache-Control: private, no-store`를 사용할 수 있다. 인증·민감한 사용자별
  HTML/API 응답을 공용 캐시에 저장하도록 만들지 않는다. 실제 브라우저·프록시·CDN의
  응답과 재검증 동작을 프로젝트 환경에서 확인한다.
- **정적 자산:** 내용 해시가 있는 JS/CSS 파일명 등으로 배포별 자산을 구별한다. 공개해도
  되는 불변 자산에는 긴 캐시를 사용할 수 있다. HTML과 자산 그래프를 함께 배포하고
  전환 중 필요한 이전 자산의 제공 방식을 정한다. HTML URL에 `?v=...`만 붙이면
  그 안에서 import하는 JS/CSS까지 모두 갱신된다고 가정하지 않는다.

### 열린 탭의 다음 이동 / Already-open tabs and the next navigation

이미 A를 실행하는 탭도 검사 대상이다. 내부 화면 이동 전에 버전을 확인하고, 탭으로
돌아올 때의 focus/visibility 복귀와 관련 history/BFCache 복원에서도 새 배포를 확인한다.
프레임워크의 navigation·`pageshow`·history 수명주기 기능을 활용한다. 복원된 문서도
자신에게 포함된 build ID를 기준으로 삼는다.

새 버전을 감지한 뒤 **미저장 입력이 없고 저장도 진행 중이지 않은 다음 화면 이동은,
사용자가 의도한 대상 URL을 전체 문서로 자동 로드한다.** 기존 SPA 화면만 교체하면
오래된 런타임이 남으므로 이 전환에는 새 문서를 받는 navigation 또는 그와 동등한
프레임워크 배포 전환이 필요하다. 일반적인 full-document 이동에서는 대상 URL로
`location.assign(targetURL)`을 사용하는 방식이 가능하다. Back/Forward에서는 기존
history 의미를 보존하는 전환을 선택한다. 안내 배너만 표시하거나, 사용자가 '업데이트
수락'을 눌러야 이동하거나, F5를 누르라고 안내하는 것으로 이 조건을 충족하지 못한다.

포커스 복귀나 백그라운드 감지는 업데이트를 대기 상태로 표시할 수 있다. 이때 페이지를
강제로 새로고침하지 않는다. 다음 이동을 확정하기 **직전**에 dirty 상태와 save-in-flight를
다시 확인한다. 비동기 버전 확인 중 새 입력이나 저장이 시작될 수 있기 때문이다.

미저장 입력이 **있거나** 저장 중이면 업데이트 사실을 알리고 입력·저장 작업을 보존한다.
저장 완료, 편집 취소 또는 사용자의 명시적 폐기로 안전해진 뒤 다음 이동에서 적용한다.
실패한 저장을 안전한 상태로 취급하지 않는다. 기존 이탈 방지 정책을 유지하며 업데이트
때문에 초안이 사라지거나 중복 저장이 발생하지 않게 한다.

버전 조회의 네트워크 실패·타임아웃·잘못된 응답은 현재 앱과 초안을 계속 사용할 수 있게
처리한다. 무한 새로고침이나 이탈 불가능한 상태를 만들지 않는다. 현재 런타임으로
이동하는 것이 가능한지는 앱 정책에 따르고, 연결이 회복되면 다음 적절한 시점에 다시
확인한다. 업데이트 감지를 위해 새 service worker나 polling 라이브러리를 기본 설치하지
않는다. 기존 service worker가 있다면 캐시·활성화·클라이언트 전환도 함께 검증한다.

### 데이터 최신성은 별도 / Data freshness is separate

앱 build가 같아도 데이터는 바뀔 수 있다. 데이터만 갱신됐다는 이유로 앱 전체를
새로고침하지 않는다. 화면 이동·사용자 새로고침 등 필요한 시점에 fresh data request를
보내고 서버의 캐시 정책도 맞춘다. 같은 출처의 **절대 경로/절대 URL**을 사용해 깊은
화면 URL에 상대적인 API 주소로 잘못 요청하지 않게 한다. 예를 들어 API가 출처 루트에
있다면 `new URL('/api/orders', location.origin)`과 요청의 `cache: 'no-store'`를 사용할 수
있다. 하위 경로에 배포하는 프로젝트는 설정된 API base를 반영한다. 인증·권한 정책과
응답 상태 검증을 유지하고, 데이터 요청 실패와 앱 build 변경을 구분해 표시한다.

## 실제 앱 합격 기준 / Real-app acceptance matrix

변경한 범위에 맞는 행을 실제 앱 환경에서 실행하고 결과·근거를 기록한다. 버전 A와 B는
서로 다른 화면 표시나 build ID로 식별 가능하게 준비한다. 실행하지 않은 행은
`미검증 / untested`, 환경이 지원하지 않는 경우는 `미지원 / unsupported`와 이유를 쓴다.

| 검사 | 실행 조건·행동 | 기대 결과 |
|---|---|---|
| JS·CSS 소스 | 화면·서비스·공통 JS와 토큰·기본·컴포넌트 스타일을 검토하고 기존 빌드 실행 | 책임 경계가 명확하고 기존 산출 형식도 동작한다. 단일 HTML 번들도 허용한다. |
| 프로젝트 관례 | 기존 함수형 프레임워크 또는 명시적 구조 지시가 있는 앱을 검토 | 기존 구조로 책임을 충족하며 불필요한 클래스·프레임워크 재작성 없이 예외를 기록한다. |
| 비동기 오류·경합 | 요청 실패와, 이전 요청이 최신 요청보다 늦게 끝나는 상황 재현 | 오류·재시도가 보이고 오래된 결과가 최신 화면을 덮어쓰지 않는다. |
| 직접 링크·새로고침 | 루트가 아닌 화면 URL을 새 탭에서 열고 일반 새로고침 | 의도한 화면과 필요한 자산·데이터를 받는다. |
| Back/Forward·404 | 화면 이동 후 뒤로·앞으로; 없는 정적 자산/API 요청 | 화면·URL이 일치하며 자산/API 실패를 HTML 200으로 숨기지 않는다. |
| 새 진입 A → B | A 접속 후 B 배포, 앱 URL에 새로 진입 | hard refresh 없이 B HTML과 일치하는 자산이 실행된다. |
| 이미 열린 A 탭 | A를 열어 둔 채 B 배포, 깨끗한 상태에서 내부 대상 화면으로 이동 | 수락 버튼 없이 대상 URL을 전체 문서로 자동 로드하고 B가 실행된다. |
| 시작 시점 경합 | A HTML을 받은 직후 B 배포, 이후 버전 조회 완료 | 현재 실행을 A로 유지해 비교하고 B 변경을 놓치지 않는다. |
| 탭 복귀·history 복원 | A 탭을 떠난 사이 B 배포; 복귀 또는 BFCache 복원 후 이동 | 변경을 감지하고 다음 안전한 이동에서 B가 실행된다. 백그라운드 강제 reload가 없다. |
| dirty 입력 | A에서 초안 작성 후 B 배포·이동 시도 | 업데이트를 알리고 초안을 보존한다. 저장·취소·명시적 폐기 후 다음 이동에서 B를 받는다. |
| 저장 중·확인 중 편집 | 저장 요청이 진행 중일 때, 또는 버전 확인 대기 중 새 입력 후 이동 | 전환 직전 상태를 재확인해 작업을 보존한다. 실패한 저장을 완료로 처리하지 않는다. |
| 롤백 B → A | B 탭을 열고 서버를 A로 롤백한 뒤 안전한 이동 | 버전 대소가 아닌 다른 ID를 감지하고 A 문서를 받는다. |
| 버전 조회 실패 | 네트워크 단절·타임아웃·잘못된 버전 응답 재현 | 현재 앱·초안이 사용 가능하며 reload loop가 없다. 복구 후 다시 확인한다. |
| 데이터만 갱신 | 앱 build를 유지하고 API 데이터 변경 후 데이터 갱신 동작 | 같은 출처의 올바른 절대 API URL에서 최신 데이터를 받으며 문서 전환은 일어나지 않는다. |
| 자산·인증 캐시 | HTML·자산·API 응답 및 열린 탭의 실제 로드 요청 검사 | HTML은 재검증/적절한 no-store, 자산은 build와 일치, 민감한 응답은 public 캐시 대상이 아니다. |

헤더·스크린샷·문서의 키워드 확인만으로 열린 탭 전환을 증명하지 않는다. 실제 문서
navigation, 실행 build ID, 대상 URL, 초안·저장 상태와 데이터 응답을 함께 확인한다.
스킬 발견과 설치된 파일의 바이트 비교는 **지침 전달**을, 합성 baseline/candidate
시나리오는 **에이전트 계획의 관찰**을 확인한다. 실제 앱 시험과 별도로 보고하며,
스킬이 항상 선택되거나 모든 에이전트·앱이 자동 준수한다고 주장하지 않는다.

## 검증과 인계 / Verification and handoff

중요 산출물은 실제 실행한 명령·결과와 적용 범위를 다음 여섯 필드로 남긴다.
프로젝트의 기존 인계 위치·형식을 사용하고 새 볼트 기록을 자동 생성하지 않는다.

| 필드 | 기록 내용 |
|---|---|
| `task_id` | 작업 식별자 |
| `artifact_paths` | 변경·검증한 파일 또는 산출물 경로 |
| `verification_commands_and_results` | 실제 실행한 명령/시험 절차, 환경, 관찰 결과, 실패·미검증 항목 |
| `assumptions` | 배포·라우팅·캐시 전제와 적용한 사용자/프로젝트 예외 |
| `unresolved` | 남은 문제와 미지원·미검증 범위 |
| `next_safe_action` | 현재 권한 안의 다음 행동; 배포·설치는 별도 승인 범위에 따른다. |

중요한 코드·구조·집계 결과는 별도 세션 또는 읽기 전용 검증자가 검증 명령을 재실행하고
`verified_by`에 행위자·일시·범위·결과를 덧붙인다. 자체 확인과 독립 검증을 구분한다.
실행하지 않은 시험을 통과로 쓰거나 에이전트의 계획 응답을 실제 앱 실행 결과로 바꾸지 않는다.
