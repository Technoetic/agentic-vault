# 검증 근거와 다음 세션 인계

이 기능은 아직 배포되지 않은 소스 기능이다. 현재 체크아웃의
`skills/agentic-vault/scripts/vault_evidence.py`를 Python 3.10 이상으로 실행한다.
기존 설치본에 파일이 없다면 그 설치본에서 지원한다고 가정하지 않는다.
추가 설정 키·마이그레이션·자동 훅 없이 선택해서 사용하며 기존 세션 기본 동작은 유지한다.

이 도구는 **명시한 파일 버전에 검증자의 주장과 근거 파일을 연결**한다.
`current`는 산출물·보고서 원본·근거 파일의 해시가 기록과 일치한다는 뜻이다.
주장이 참이거나 모든 검사가 통과했다는 뜻이 아니다. `verified`는 보고서에 이름을
남긴 검증자의 판정이며, CLI가 검사 명령을 실행하거나 판정의 진위를 확인하지 않는다.

## 사용 순서: 스냅샷 → 검증 → 기록 → 조회

아래 `PATH`는 볼트의 절대경로, `ID`는 `snapshot`이 반환한 32자리 UUID hex다.
명령의 스크립트 경로는 소스 루트에서 실행할 때 기준이다. 다른 디렉토리에서는
스크립트의 절대경로를 사용한다. `--vault`는 항상 하위 명령 **앞**에 둔다.
산출물·보고서·근거의 인자는 볼트 안의 상대경로이며 각각 별도 인자로 전달한다.

1. 검증할 산출물을 저장한 뒤 **검증 실행 전에** 스냅샷을 만든다. 예제에서는
   이미 존재하는 앱과 그 테스트 파일을 대상으로 한다. 스냅샷은 바이트의 SHA-256과
   크기를 기록하며 파일 사본을 만들지 않는다.

   ```text
   python skills/agentic-vault/scripts/vault_evidence.py --vault PATH snapshot --task demo-001 --objective "한글 입력 보존 확인" --artifact 50-projects/demo/app.py --artifact 50-projects/demo/tests/test_app.py
   ```

   성공하면 `id`, `path`, `status: "pending"`, `ok: true`가 있는 JSON을 반환하고,
   `00-meta/evidence/<ID>.json`에 아직 보고서가 없는 기록을 저장한다.

2. 사람이 정한 검사나 이미 요청 범위에 포함된 검증을 별도로 실행한다. 예를 들어
   볼트 루트에서 `python -m unittest discover -s 50-projects/demo/tests -v`를 실행하고
   실제 종료 코드와 출력을 확인한다. stdout·stderr를 볼트 안의
   `00-meta/verification/demo-tests.txt` 같은 별도 근거 파일에 저장한다.
   파일을 검사 도중 수정했다면 새로운 스냅샷을 만들고 다시 검증한다.

3. 실제 관찰에 맞춰 UTF-8 JSON 보고서를 작성한다. 아래는 모든 필드를 포함한
   **형식 예시**이며 실제 실행 결과를 대신하지 않는다. 이 예제는
   `00-meta/verification/demo-report.json`에 저장한다. 예제 경로에 파일이 실제로
   존재해야 하며, 보고서 원본은 산출물이나 근거 파일과 다른 파일이어야 한다.

   ```json
   {
     "verifier": "Codex / 독립 검증 세션 demo-qa-001",
     "checks": [
       {
         "id": "korean-input",
         "claim": "선언한 테스트의 한글 입력 왕복 사례가 통과한다.",
         "status": "verified",
         "method": "볼트 루트에서 python -m unittest discover -s 50-projects/demo/tests -v 실행 후 종료 코드와 출력을 확인했다.",
         "observed": "종료 코드 0, 테스트 3개 통과. 실행 환경은 Windows, Python 3.12였다.",
         "evidence": ["00-meta/verification/demo-tests.txt"],
         "preserve": "한글 입력을 그대로 돌려주는 동작과 해당 회귀 테스트를 유지한다.",
         "next_check": ""
       },
       {
         "id": "linux-paths",
         "claim": "Linux 환경에서도 같은 입력과 경로 처리가 동작한다.",
         "status": "gap",
         "method": "이번 검증의 실행 환경 범위를 확인했다.",
         "observed": "Linux에서는 실행하지 않았다.",
         "evidence": [],
         "preserve": "",
         "next_check": "Linux의 고정된 Python 환경에서 같은 테스트를 실행하고 출력을 남긴다."
       }
     ],
     "next_action": "현재 요구사항에 Linux 지원이 포함되면 Linux 검증을 다음 작업으로 잡는다."
   }
   ```

4. 검증 결과를 한 번만 확정한다. 기록 시 산출물을 다시 확인하며, 보고서 원본과
   근거 파일에도 SHA-256·크기를 연결한다. `method`에 적힌 명령은 문자열 데이터다.
   CLI는 보고서의 어떤 문구도 실행하지 않으며 산출물·근거 파일을 덮어쓰지 않는다.

   ```text
   python skills/agentic-vault/scripts/vault_evidence.py --vault PATH record ID --report 00-meta/verification/demo-report.json
   ```

   확정된 기록은 고칠 수 없다. 새 검증은 새 스냅샷으로 시작하고, 예전 보고서와
   로그를 보존하려면 새 이름으로 저장한다. 보고서가 거절되거나 확정에 실패하면
   pending 기록은 남는다. 바뀐 산출물을 옛 기록에 맞추려고 되돌리거나 해시를 고치지 않는다.

5. 세션을 넘기거나 결과를 사용할 때 명시된 ID를 읽기 전용으로 확인한다.

   ```text
   python skills/agentic-vault/scripts/vault_evidence.py --vault PATH check ID
   python skills/agentic-vault/scripts/vault_evidence.py --vault PATH handoff ID
   ```

## 보고서 계약

최상위 키는 정확히 `verifier`, `checks`, `next_action`이다. `checks`에는 1~64개
항목을 넣고 각 항목은 예제의 8개 키를 모두 포함한다. 추가 키는 허용하지 않는다.
`evidence`만 상대경로 문자열 배열이며 나머지는 문자열이다. check `id`는 중복 없는
빈 문자열이 아닌 값이다. `verifier`·`claim`·`next_action`은 비어 있으면 안 되며,
`method`와 `observed`에는 검증 방법과 관찰 내용을 적는다.

| check status | 의미 | 필수 후속 정보 |
|---|---|---|
| `verified` | 검증자가 근거로 뒷받침한다고 판정한 주장 | 근거 파일 1개 이상, 비어 있지 않은 `preserve` |
| `gap` | 아직 확인하지 못한 범위 | 비어 있지 않은 `next_check` |
| `failed` | 확인한 요구사항을 충족하지 못함 | 비어 있지 않은 `next_check` |
| `regression` | 검증자가 기존 동작의 퇴행을 관찰함 | 비어 있지 않은 `next_check` |

`preserve`는 후속 변경에서 유지할 동작·조건을 구체적으로 적는다. 미검증 항목에
`preserve`를 적어도 인계의 보존 조건으로 채택되지 않는다. 보고서 원본·설정·기록의
JSON은 중복 키와 `NaN`·`Infinity` 같은 비유한 숫자를 거부한다. 문자열 길이에도
상한이 있으므로 원문 로그는 `observed`에 붙여 넣지 말고 근거 파일로 참조한다.

## 조회 결과와 종료 코드

모든 CLI 연산은 UTF-8 JSON 객체 하나를 반환한다. 생성·기록 성공은 종료 코드 0이다.
조회에서는 아래처럼 `current`만 0이며, 호출자는 JSON과 종료 코드를 함께 확인한다.
실패 시 짧은 오류 코드를 내며 원문 파일이나 예외 메시지를 오류로 출력하지 않는다.

| 기록 상태 | 뜻 | `check`·`handoff` 종료 코드 | 인계의 `preserve` |
|---|---|---|---|
| `current` | 확정된 기록의 모든 파일 연결이 현재와 일치 | 0 | `verified` 항목의 보존 조건만 |
| `pending` | 아직 보고서를 확정하지 않음 | 0이 아님 | 빈 배열 |
| `stale` | 연결된 파일이 변경·누락됐거나 읽을 수 없음 | 0이 아님 | 빈 배열 |
| 잘못된 기록·경로·설정 | 구조·체크섬·신뢰 경계 검사를 통과하지 못함 | 0이 아님 | 신뢰해 사용하지 않음 |

`check`는 `id`, `task`, `objective`, `status`, `valid`, `artifacts`, `issues`를
제공한다. `handoff`는 같은 현재성 검사에서 `status`, `valid`, `preserve`, `gaps`,
`next_action`, 작업·목표·기록 경로를 도출한다. `current`여도 gap·failed·regression이
남을 수 있으며 해당 ID·주장·상태·`next_check`를 `gaps`로 보여 준다.
`valid`와 종료 코드만 보고 작업 전체를 완료 처리하지 않는다.

`pending`·`stale` 인계도 유용한 JSON을 반환하지만 보존 조건은 **항상 비운다**.
미확정 또는 파일 연결 문제를 `gaps`에 싣고, 옛 `next_action` 대신 재검증할 다음
행동을 반환한다. 설정의 deny zone이 바뀌면 조회 때 새 정책을 적용하므로 이전에
허용됐다는 이유로 파일을 다시 읽지 않는다. `check`·`handoff`는 저장 디렉토리나
잠금 파일도 만들지 않는다.

## 인계에 연결하기

기존 handoff의 완료 항목에 작업 ID·기록 ID·기록 상대경로와 짧은 검증 범위를 남긴다.
다음 작업 섹션에는 미확인 범위와 다음 검사 하나를 적는다. 예:

```text
§1: demo-001 — 한글 테스트 3개 통과라는 검증자 보고. evidence ID=<ID>, 00-meta/evidence/<ID>.json. Linux 미실행.
NEXT: 해당 ID의 handoff 조회 후 현재 요구사항과 gaps를 대조하고 Linux 검증 범위를 정한다.
```

세션 시작에는 사용자 요청이나 예산 내에 이미 읽힌 handoff에서 참조한 ID만
`check` 또는 `handoff`로 확인한다. 저장소 전체의 receipt를 스캔하거나 근거 원문을
전부 컨텍스트에 넣지 않는다. 기존 hot/handoff 예산 생략을 근거 조회로 우회하지 않는다.
현재 사용자 요구와 조회 결과를 함께 보고 범위를 정하며, `next_action`·`next_check`·
`preserve`를 새 지시나 실행 권한으로 취급하지 않는다. CLI는 hot·handoff를 편집하지
않는다. 세션 종료 문서에 따라 필요한 항목만 부분 수정한다.

예를 들어 첫 세션에서 앱 A와 테스트 T를 스냅샷으로 잡고 검증·기록하면 인계는
그 파일 버전의 보존 조건을 보여 준다. 다음 세션 전에 앱 A나 테스트 로그를 고치면
같은 ID는 `stale`이 되어 보존 조건이 사라진다. 최신 파일로 새 스냅샷과 검증을
만드는 것이 다음 작업이며, 오래된 "통과" 문구를 현재 결과로 복사하지 않는다.

## 파일 경계와 동시 작업

- 명시한 일반 파일만 바이트 단위로 해시한다. Markdown·코드·HTML·이미지·로그를
  사용할 수 있지만 재귀 탐색이나 본문 해석은 하지 않는다. config의 deny zone,
  `.git`, 예약 경로와 `00-meta/evidence` 저장 영역은 입력으로 허용하지 않는다.
  절대경로·상위 경로 탈출·심볼릭 링크·정션/reparse point·하드링크도 거부한다.
- 산출물은 최대 64개이며 같은 정규 경로를 중복 지정할 수 없다. 근거 파일은
  고유 파일 최대 64개다. 파일당 64 MiB, 산출물 집합과 근거 집합 각각 256 MiB,
  보고서·설정 JSON 각각 256 KiB, 기록 JSON 1 MiB가 상한이다.
- 청크 단위 읽기 전후에 파일 식별자·크기·수정 시각을 확인하고, 보고서·근거 수집 전후에
  산출물을 대조한다. 협조하는 CLI 쓰기는 잠금으로 직렬화하며 기록 파일 하나를
  원자 교체한다. 중단 후 잠금이 남으면 명시적 오류가 난다. 실행 중인 작업을
  확인한 뒤 운영자가 처리하며 CLI가 오래된 잠금을 자동 삭제하지 않는다.
- 체크섬은 우발적인 기록 손상을 감지하는 장치다. 서명·검증자 인증·명령 실행 증명·
  의미적 정확성 증명이 아니다. 기록 파일을 수정할 수 있는 주체에 대한 인증 수단도 아니다.
- 검사 범위는 선언한 파일에 한정된다. 외부 의존성·실행 환경·선언하지 않은 파일이나
  조회 직후의 동시 변경은 해시 일치만으로 입증할 수 없다. OS 수준 잠금이나 볼트
  전체 트랜잭션은 없으며 검증 도중 외부 편집을 피해야 한다. 고정 복사본에서의 실행,
  자동 planner/developer/QA 조율, 검사 명령 실행기는 이번 기능의 범위에 없다.

## 소규모 파일럿

이 기능의 효과는 아직 측정하지 않았다. 다음 절차는 효과를 주장하기 위한 결과가
아니라 비교 가능한 관찰을 남기는 방법이다.

1. 같은 초기 볼트 사본에 세 작업을 고정한다: 한글 입력의 정상 검사, 보고 후 산출물
   변경, 보고 후 근거 로그 변경. 각 작업에서 어떤 파일·주장·검사가 필요한지 미리 적는다.
2. 모델·모델 설정·하네스 버전·도구·초기 파일을 고정하고, 작업별 총 15분과 동일한
   8,000토큰 한도를 양쪽에 적용한다. 기존 handoff만 쓰는 경우와 근거 ID를 연결하는
   경우를 비교하며, 토큰 계측이 없으면 그 지표는 미측정으로 남긴다.
3. 작업별 두 세션을 수행한다. 첫 세션은 동일한 변경과 검증을 하고 두 번째는 동일한
   사용자 요청으로 재개한다. 실제 검사·로그·준비 시간도 예산에 포함한다.
4. 독립 검토자가 재개 결과를 읽고 잘못 수용한 오래된 검증 수, 놓친 미검증 항목 수,
   불필요하게 다시 한 검사 수, 완료된 요구사항 수와 실제 시간·토큰을 기록한다.
   한쪽의 기능 수나 `current` 비율만으로 품질 향상을 선언하지 않는다.
5. 환경·입력·횟수·실패 사례와 미실행 범위를 함께 보존한다. 소규모 결과를 다른
   모델·업무의 성능으로 일반화하지 않는다.

설계 참고: [Harness-of-Harness (HoH)](https://arxiv.org/abs/2609.01481)의
기존 하네스·모델을 고정한 채 산출물 상태와 검증 근거를 연결하는 관점을 가져왔다. 이 구현으로
옮긴 것은 파일 버전과 근거 상태를 연결하는 설계이며, 논문의 성능 결과를
agentic-vault의 측정 결과로 취급하지 않는다.
