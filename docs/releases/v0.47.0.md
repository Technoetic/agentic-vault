# v0.47.0 — 안내서 대조 검토 반영과 aside-repl 절차 명령

이 플러그인의 명령·규칙·브리지·어댑터를 공급사의 프롬프트 작성 안내서(아래 `참고와 기존 활용의 차이`)와
견준 대조 검토가 고칠 곳을 찾았고, 이번 릴리스는 그 가운데 열한 항목을 다룬다.
저장소 기여자 안내, Telegram 브리지의 선택형 모델·노력 수준과 계속 실패하는 정기 브리핑의 시도 상한,
교훈 은퇴 사유, 인박스 처리의 완료 조건, 종료 기록을 읽는 사람, 문구 정리, Aside의 `/aside-repl` 절차
명령, 시험 fixture의 경합, v0.46.0 문서 정정이다. 엔진 사본 소유를 밝히는 계약 한 줄은 계획해 시험했으나
통과하지 못해 넣지 않았다. 새 옵션 없이도 결과가 바뀌는 곳이 있으므로 아래 `기본 결과 변경`을 먼저 본다.

## 변경

- 저장소 루트에 기여자·에이전트 안내 [AGENTS.md](../../AGENTS.md)를 두고, Claude Code가 이를 불러오도록 .claude/CLAUDE.md(한 줄: @../AGENTS.md)를 둔다. 유지관리자가 설계와 릴리스를 정하고, 기여자와 에이전트는 요청받은 범위만 작게 고친다는 것, import 없이 같은 규칙을 지녀야 하는 파일(볼트에서 혼자 실행되는 healthcheck·deny zone 가드, vault_paths.py를 불러오면 안 되는 vault_lint_extensions.py, import 순환을 피하는 vault_state.py) 때문에 일부러 둔 다섯 규칙의 사본(일곱 곳)과 그것을 지키는 시험, 엔진 파일과 볼트 자료의 구분, 릴리스 규칙과 시험 실행법을 적는다. 볼트에는 설치하지 않는다.
- [Telegram 브리지 설정](../../commands/vault-jarvis-setup.md): 선택 키 `jarvis.model`·`jarvis.effort`를 더한다.
  두 키의 기본값은 빈 문자열이고, 비어 있으면 브리지는 `--model`·`--effort`를 넘기지 않아 claude CLI 인자
  배열이 v0.46.0과 같다. 값이 있으면 `--settings` 다음, `--append-system-prompt` 앞에 `--model`과 그 값,
  `--effort`와 그 값을 이 순서로 더한다. `effort`는 `low`·`medium`·`high`·`xhigh`·`max` 중 하나이고,
  `model`은 ASCII 영문자·숫자로 시작해 영문자·숫자와 `. _ : @ / + [ ] -`만 쓴 256자 이하의 이름이다. 다른
  값은 설정 오류로 브리지를 시작하지 않고, doctor는 값을 적지 않은 채 `jarvis_configuration_invalid`를
  보고한다. 브리지는 모델 이름이 CLI에서 쓸 수 있는지는 검사하지 않는다.
- [정기 브리핑](../../commands/vault-jarvis-setup.md): 같은 회차가 8번 연속 실패하면(응답 생성 실패, 생성 중
  예외, Telegram 전송 실패) 그 회차를 `pending`에서 빼고 그날은 다시 시도하지 않으며, 소유자에게 날짜·시각·회차
  이름과 시도 횟수를 적고 원인은 짐작하지 않는 안내를 한 번 보낸다. 시도 사이의 간격은 기존 재시도
  간격(60초에서 시작해 실패마다 두 배, 최대 1시간)을 따른다. 이 간격은 회차마다 따로 두지 않고 `pending`이 빌
  때만 60초로 돌아가므로, 두 회차 이상이 함께 `pending`에 있으면 뒤 회차는 앞 회차의 실패로 늘어난 간격에서
  이어 시도하고 건너뛰기 안내도 그만큼 늦게 온다. 날이 바뀔 때 전날의 `pending` 회차는 한 번만 더 시도하고,
  실패하면 같은 방식으로 건너뛴 뒤 그날 회차를 같은 처리에서 이어 간다. 상태 파일 `last_brief`의 형식은
  그대로다.
- [교훈 은퇴 사유](../hardening.md#교훈-은퇴-사유): `vault_lesson_delta.py`의 RETIRE가 선택형 `reason`과
  `date`를 받아 대장 줄의 상태 칸을 `상태: retired(사유, YYYY-MM-DD)`로 쓴다. 대장 줄의 표지 키는 그대로다.
  제목형 기록에는 사유를 받지 않고(`retire_reason_unsupported`), 이미 적힌 사유는 바꾸지 않는다
  (`retire_reason_exists`). 새 볼트의 [교훈 대장 템플릿](../../assets/templates/lessons.md)은 형식 줄에 두
  은퇴 형태를 적고 은퇴 항목을 둔다. [실수 노트 템플릿](../../assets/templates/mistakes.md)은 "교훈은 만료되지
  않는다" 대신, 이유가 사라진 항목을 사용자 확인 뒤 은퇴시키는 방법을 적는다. `/vault-session-end`는 은퇴를
  그 근거를 이번 세션에서 확인했을 때만 제안하고 승인 뒤 적용하며, 승격 초안에 적용 범위·이유·출처를 담고
  사용자 확인만 필요한 행동은 "X 전에 확인받는다"로 쓴다. [`constraints_note` 안내](../hardening.md#compact-constraints-note-constraints_note)는
  항목마다 적용 범위와 이유를 적고 이유가 사라진 항목을 지우라고 권한다.
- [`/vault-process-inbox`](../../commands/vault-process-inbox.md)에 완료 조건(`## 3-1.`)을 둔다. 1에서 찾은
  파일이 모두 처리를 마치거나 사유와 함께 보류돼야 끝난다. 보류 사유는 판독 불가, 이동 뒤 이름 충돌, 보완하고
  다시 검사해도 `check_compile`이 통과하지 않음, 진단하고 다시 시도해도 풀리지 않은 장애의 넷이다. 권한
  거부·훅의 차단·deny zone은 우회하지 않는다. 보고 직전에 인박스를 다시 나열해 남은 파일(실행 중에 들어온
  파일 포함)을 2단계부터 처리한다.
- [`/vault-session-end`](../../commands/vault-session-end.md) 첫머리에 `**읽는 사람:**` 문단을 둔다.
  handoff·hot·log와 종료 보고는 이 세션에 없던 사람이 읽으므로 지어낸 약어는 풀어 쓰고, 명령이 요구하는
  식별자와 기계 값은 그대로 적되 처음 나올 때 뜻을 붙인다.
- 문구 정리: 새 볼트의 hot·handoff 템플릿과 SKILL.md는 "500단어 이내" 대신 "500단어 권고"와 세션 주입
  예산(`hot_max_tokens`)을 말한다. 상시 로드 규칙 `vault-architecture.md`의 문구는 바꾸지 않았다. 설정
  템플릿의 `gates.note_move` 설명은 처리한 인박스 원본의 격리 이동과 `/vault-lint` 관리성 이슈의 아카이브
  이동을 나눠 적는다.
- `/vault-session-end`의 원격 push 줄을 예외가 드러나게 고쳤다. 동작은 같다.
- [선택형 Aside 어댑터](../../assets/adapters/aside/aside-repl-command.md)에 엔진 소유 절차 명령 `/aside-repl`을
  더한다. `/vault-init`과 `/vault-upgrade`(Codex `init`·`upgrade`)가 따로 묻고, 승인할 때만 볼트의
  `.claude/commands/aside-repl.md`로 복사한다. 스크립트를 파일로 써서 bash 셸이 있으면
  `aside repl "$(cat 파일.js)"` 꼴로, 없으면 Python에서 셸을 거치지 않고 넘기며, 요청 글은 셸 명령줄에 넣지
  않는다. 본문에 주입 셸 명령과 `allowed-tools`가 없으므로 `aside` 호출은 모두 에이전트 자신의 도구 호출로
  권한 확인과 훅을 거친다. `vault_adapters.py`의 새 `--offer-aside-command`와 `adapters.aside_command` 항목이
  사본의 상태를 보고하고, 새로 넣는 Aside 조항에는 `**repl 스크립트 전달:**` 줄이 붙으며, 새로 만드는 운영
  가이드 노트에는 2026-11-12~13의 repl 호출 실측 표가 들어간다. 명령·스킬 본문이 주입하는 셸 명령이
  PreToolUse 훅을 거치지 않은 관찰은 [SECURITY.md](../../SECURITY.md)와
  [deny zone 가드 안내](../../assets/adapters/deny-guard/guide.md)에 적었고, 이 플러그인의 명령·스킬에 주입
  셸 명령이 없음을 시험이 지킨다. Codex 설치 확인이 바이트로 대조하는 리소스는 129개에서 130개가 된다.
- 시험 fixture: tests/test_vault_commit.py가 모든 시험에서 복사하는 시드 Git 저장소에 maintenance.auto=false와 gc.auto=0을 둔다. v0.46.0 master CI의 macOS 작업 하나가 이 저장소를 복사하는 동안 .git/objects/maintenance.lock이 사라져 오류를 냈다. 자동 유지보수가 커밋 뒤 배경에서 그 파일을 만들고 지운 것으로 보이며, 원인 프로세스를 직접 관측하지는 않았다. 런타임 코드는 바뀌지 않는다.

## 기본 결과 변경

플러그인을 갱신하면 명령·스킬·브리지 코드는 바로 바뀐다. 볼트에 설치된 사본(규칙·healthcheck·어댑터)은 /vault-upgrade(Codex는 upgrade)를 실행하기 전까지 예전대로 동작하고, 이전 플러그인 폴더에서 시작한 Telegram 브리지는 다시 시작하기 전까지 예전대로 동작한다.

1. `/vault-process-inbox`는 보고 직전에 1단계와 같은 범위로 인박스를 다시 나열하고, 처리하지도 보류하지도
   않은 파일(실행 중에 들어온 파일 포함)을 2단계부터 처리한다. 보류 사유는 정확히 넷이다. 권한 거부, 훅의
   차단, deny zone은 우회하지 않고(문서에 적힌 `mv -n` 경로만 쓴다) 무엇이 막았는지를 적어 풀리지 않은
   장애로 보류한다. 보고 표에는 보류한 파일마다 사유와 필요한 사용자 결정이 붙는다. 대상: 플러그인을 갱신한
   모든 사용자(Claude Code와 Codex).
2. `/vault-session-end`는 handoff·hot·log와 종료 보고를 이 세션에 없던 사람이 읽는다는 기준으로 쓴다.
   지어낸 약어는 풀어 쓰고, 명령이 요구하는 ID·해시·상태 값은 그대로 적되 처음 나올 때 뜻을 붙인다. 구조,
   예산, log 형식은 그대로다. 대상: 모든 사용자.
3. `/vault-session-end`의 승격 초안은 조항 안에 적용 범위·이유·출처를 적고, 사용자 확인만 필요한 행동은
   "X 전에 확인받는다"로 쓴다. 이미 승격된 조항은 바뀌지 않는다. 대상: 모든 사용자의 새 승격.
4. 새 볼트의 실수 노트 템플릿은 "교훈은 만료되지 않는다" 대신, 이유가 사라진 항목을 사용자 확인 뒤 제목
   아래 `상태: retired(사유, YYYY-MM-DD)` 줄로 은퇴시킨다고 적는다(교훈 표지가 있으면 그 다음 줄에 달고, 사유
   없는 RETIRE로 표지 상태도 `retired`로 맞춘다). 본문은 남는다. 기존 실수 노트는 바뀌지 않는다. 대상: 새
   볼트(`/vault-init`, Codex `init`).
5. `vault_lesson_delta.py`: 상태 칸이 이미 `상태: retired(…, YYYY-MM-DD)`인 줄에 사유 없는 RETIRE를 하면 그
   칸을 `상태: retired`로 다시 쓰지 않고 그대로 둔다. 그 밖의 RETIRE 결과는 바이트 단위로 같다. 대상: 사유를
   손으로 적은 칸에 RETIRE를 실행하는 사용자.
6. 새 교훈 대장은 새 형식 줄(두 `retired` 형태)과 은퇴 항목을 받는다. `/vault-upgrade`가 맞추는 v0.8.2 이하의
   대장도 새 형식 줄을 받는다. 다른 기존 대장은 바뀌지 않는다. 대상: 새 볼트, v0.8.2 이하의 대장.
7. 새 볼트의 hot·handoff 템플릿은 "500단어 이내" 대신 "500단어 권고"와 세션 주입 예산(`hot_max_tokens`)을
   말하고, SKILL.md의 안내도 같이 바뀐다. 상시 로드 규칙 `vault-architecture.md`는 그대로다("500단어 핫
   컨텍스트", 스탬프 `engine=0.6.0`). 기존 노트는 바뀌지 않는다. 대상: 새 볼트(템플릿), 모든 사용자(SKILL.md).
8. 새 볼트의 설정 템플릿에서 `gates.note_move` 설명이 인박스 원본의 격리 이동(확인 없음)과 관리성 아카이브
   이동(승인 뒤)을 나눠 적는다. 값은 그대로이고 게이트는 집행되지 않으며 기존 설정은 바뀌지 않는다. 대상: 새
   볼트.
9. `/vault-upgrade`는 기존 `jarvis` 블록에 빈 `model`·`effort` 키를 더하고, 새 볼트도 두 키를 받는다. 키가
   비어 있는 동안 브리지의 claude 인자 배열은 v0.46.0과 같다. 대상: `jarvis` 블록이 있는 볼트, 새 볼트.
10. v0.46.0까지 무시되던 `model`이나 `effort` 키가 이미 `jarvis` 블록에 있으면 이제 검증한다. 올바른 값은
    `--model`·`--effort`를 더하고, 올바르지 않은 값(문자열이 아닌 값 포함)은 브리지를 시작할 때 멈추게 하며
    (종료 코드 2) doctor는 `jarvis_configuration_invalid`를 보고한다. CLI가 받지 않는 모델 이름은 모든 질문과
    브리핑을 실패하게 한다(`--bare` 없이 이름 하나로 확인했다). 대상: 그런 키가 있는 브리지 사용자.
11. 같은 정기 브리핑 회차가 8번 연속 실패하면(생성 실패, 생성 중 예외, 전송 실패) `pending`에서 빠지고 그날은
    다시 시도하지 않으며, 소유자는 날짜·시각과 시도 횟수가 든 안내를 한 번 받는다. v0.46.0은 끝없이 다시
    시도했고 소유자에게 알리지 않았다. 그 회차는 `fired`로 기록하지 않고, 전달되지 않은 안내는 로그에만
    남는다. 대상: 브리지 사용자.
12. 날이 바뀔 때 전날의 `pending` 회차는 한 번 더 시도하고 실패하면 안내와 함께 건너뛰며, 그 뒤 같은 처리에서
    그날 회차를 진행한다. v0.46.0은 전날 회차가 성공할 때까지 그날 회차를 처리하지 않았다. 대상: 브리지 사용자.
13. 생성 중 예외(설정 오류 제외)도 실패한 시도로 센다. 로그 줄이 `스케줄 브리핑 생성 실패(HH:MM) — 시도 k/8`,
    `스케줄 브리핑 생성 오류(HH:MM, …) — 시도 k/8`(괄호 안에 시각과 오류의 유형·위치),
    `스케줄 브리핑 전송 실패(HH:MM) — 시도 k/8`로 바뀌고 `스케줄 브리핑 생성 실패 — pending 유지`는 없어진다.
    상태 파일 쓰기 오류의 처리는 그대로다. 대상: 브리지 사용자, 로그를 읽는 사람.
14. `vault_adapters.py`에 새 옵션 `--offer-aside-command`와 항목 `adapters.aside_command`가 생긴다. 이 항목은
    그 옵션을 주거나 `.claude/commands/aside-repl.md`가 있을 때만 나온다. 같은 이름의 명령을 직접 만든 볼트는

## 검증

[검증 계약](../verification/v0.47.0.md)에 따라 공개한다. 공개 순서는 다음과 같다.

후보 브랜치 CI(최종 커밋) → 로컬 태그·ZIP·재빌드 확인·Codex 설치 확인·인증서 → 태그 push → 태그 CI 11/11 → 참고 대장 갱신과 독립 확인 → 독립 릴리스 검토 → master push → master CI 11/11 → 검증 기록(verification.json) → 업로드 → 초안 점검 → 게시 → 게시 후 확인

전체 로컬 시험은 통합한 트리에서 첫 후보 브랜치 push 전에 한 번, 최종 커밋에서 다시 한 번 실행한다. 같은
단계에서 항목별 시험 모듈, 컴파일과 공백 검사, 워크플로의 smoke 명령, 두 Claude 매니페스트의 엄격 검증, 새
옵션 없이 v0.46.0과 출력을 비교해 모든 차이를 위 `기본 결과 변경`의 항목에 대응시키는 대조, v0.46.0 기준과
함께 재는 항목별 기능 근거, 독립 소스 검토, 통합한 명령 파일로 하는 실제 `/aside-repl` 실행 한 번을 거친다.
결과는 공개 `verification.json`에 기록하고 게시 후 확인은 별도 기록으로 보관한다. 과거 릴리스의 수치를 이번
버전의 결과로 옮기지 않는다. 엔진 사본 소유 줄의 규칙 문구 시험 결과는 [hardening.md](../hardening.md#engine-copy-ownership-line-tried-not-shipped)에 있다.

## 알려진 경계

- 기여자 안내(AGENTS.md와 이를 불러오는 .claude/CLAUDE.md)가 다른 폴더의 세션에 읽히지 않는 것은 Claude Code 2.1.252 출력 모드에서 --plugin-dir로 플러그인을 불러 한 번 확인했다. 마켓플레이스 설치본, IDE 확장, 플러그인 파일을 읽는 턴은 시험하지 않았고 Codex는 실행하지 않았다(호스트 문서의 탐색 규칙을 따른다). 플러그인 체크아웃 폴더에서 세션을 시작하면(볼트 안에 둔 체크아웃 포함) Claude Code가 그 .claude/CLAUDE.md를 읽는다. 플러그인 루트에는 CLAUDE.md를 두지 않는다: claude plugin validate --strict가 루트의 CLAUDE.md를 경고로 막는다(2.1.252).
- 엔진 사본 소유를 밝히는 계약 한 줄은 계획해 규칙 문구 시험을 했으나 통과하지 못해 넣지 않았다: 시험한 세 문구가 모두, 사용자가 명시적으로 요청한 볼트 사본 수정을 거절하게 만들었다(줄 없이 4건 중 3건 수행, 줄이 있으면 0건; 로컬 모델 하나, 문구마다 1회, 지어낸 사례 — [hardening.md](../hardening.md#engine-copy-ownership-line-tried-not-shipped)). 그래서 vault-architecture.md와 그 스탬프는 v0.46.0과 같다.
- 브리지는 모델 이름이 CLI에서 쓸 수 있는지 검사하지 않는다. --effort가 없는 이전 claude CLI는 값을 지정하면 실행이 실패할 수 있다. 설치된 claude CLI 2.1.252에서 브리지 인자 배열에 두 옵션을 넣어 확인했다(2026-11-13, 경우마다 1회): --bare에서는 옵션 해석까지만 확인했고(이 기기에는 API 키가 없어 응답 생성은 못 했다), --bare 없이 로그인한 상태에서는 haiku·low로 응답했다. CLI가 받지 않는 모델 이름 하나는 --bare 없이 0이 아닌 종료 코드로 끝났다. --bare에서 인증된 응답 생성과 노력 수준 적용은 확인하지 않았다. 모델·노력 수준을 바꿔 응답 시간이나 품질이 어떻게 달라지는지는 재지 않았다.
- 브리지는 claude CLI의 텍스트 출력과 종료 코드만 읽어 모델 제공자의 요청 거절과 장애·빈 응답을 구별하지 못한다. --output-format json은 쓰지 않는다. 실제 거절의 출력 형태는 확인하지 않았다. --bare에서 API 키가 없을 때 CLI는 로그인하지 않았다는 줄을 표준 출력에 내고 종료 코드 1로 끝났다(1회). 브리지는 0이 아닌 종료 코드를 생성 실패로 처리하고 그 출력을 전달하지 않는다.
  정기 브리핑의 시도 횟수는 브리지 메모리에만 두므로 브리지를 다시 시작하면 0부터 센다. 건너뛴 회차의
  안내가 전달되지 않아도 다시 보내지 않고 로그에만 남긴다. 자정 뒤 첫 처리는 진행 중인 재시도 대기(최대
  1시간)가 끝나기를 기다린다. 상태 파일 쓰기 오류는 시도 횟수에 세지 않는다.
- 제목형 기록(실수 노트 항목)의 은퇴 사유는 사람이 손으로 적는다(제목 바로 다음 줄에 교훈 표지가 있으면 그
  표지 다음 줄에). 사유는 기록일 뿐 은퇴를 승인하거나 원인이 사라졌다고 확정하지 않는다. v0.8.3 이후에 만든
  교훈 대장의 형식 줄은 `/vault-upgrade`가 바꾸지 않으므로 그 대장에는 새 형식 줄이 없다.
- 6·7·8번은 명령과 템플릿의 문구다. 절차 글은 동작을 강제하지 못하며, 모델이 이 문구를 따르는지는 재지
