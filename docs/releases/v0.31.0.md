# v0.31.0 — 사례별 뒤집힘 표, 대장 사실 표 표시와 기간 정규화, 세션 기록의 SessionStart 확인

개선 전후 실행을 assertion마다 맞대어 평균 점수에 가려진 퇴행을 따로 세고, 시간 대장의 `check-support`가 다른 대장의 사실 표에만 기댄 뒷받침을 표시하며, 선택하면 기간 표현을 날짜 구간으로 대조한다. Doctor는 사용자가 지정한 Claude Code 세션 기록 하나에서 SessionStart 훅이 실행·실패·잘렸는지를 내용 없이 보고한다. 시험용 루프백 서버는 요청 본문을 읽는다. 기준 공개판은 v0.30.0 `452c5c0beb055320565eab39669e46ac6b18d075`, 검토를 마친 통합 커밋은 `169d8a66bb422bd0e07f8787e7d6340d75fb1624`이며 최종 소스는 게시 전 `verification.json`에 기록한다. 핵심 엔진은 Python 3.10+ 표준 라이브러리만 쓰며 모델·네트워크 호출, 런타임 의존성, 훅 정의를 추가하지 않는다. **`vault_ssot.py`가 바뀌어 경고 승격 인증서의 `checker_sha256`가 바뀐다. 경고를 `fatal`로 올린 볼트는 갱신하거나 되돌리기 전에 [아래 순서](#하위호환업그레이드)를 따른다.**

## 변경

- **사례별 뒤집힘 표(`vault_runs.py flips`, 읽기 전용):** `compare` 점수는 모든 assertion을 같은 무게로 평균하므로 다른 사례가 좋아진 몫이 soft assertion의 퇴행을 가릴 수 있다. `vault_runs.py --vault PATH flips BASELINE_ID CANDIDATE_ID`는 두 완료 실행을 (사례, assertion)마다 맞대어 반복별 완료·통과 수를 센다. 모든 반복이 통과나 실패로 정해진 항목만 `flip_counts`의 `pass_to_pass`·`pass_to_fail`·`fail_to_pass`·`fail_to_fail`에 넣고, 일부만 통과하면 `mixed`, error 반복이 있으면 `incomplete`로 센다(여섯 값의 합은 `item_count`). error 반복은 실패로 세지 않고 `error_outcomes`에 따로 센다. 통과 수가 줄어든 항목은 `pass_count_drops`에, 전체 항목 대비 `pass_to_fail` 비율은 `negative_flip_rate`(MUSCLE의 NFR 정의)에, 기준안이 통과한 항목 대비 비율은 `conditional_negative_flip_rate`에 담는다. `compare`와 같은 현재성 검사로 두 실행을 다시 읽고, 비교 조건이 다르면 `incompatible_execution_contracts`, 미완료면 `run_not_complete`로 거절한다(종료 코드 2). 영수증·잠금 파일을 만들지 않으며 `compare`의 점수·`eligible`·비교 영수증, 개선 실험의 결정, 비용 도구의 `performance`에 더해지지 않는다.
- **정정·유지 역할(fixture assertion의 선택 키 `role`):** `correction`은 개선이 고치려는 검사(SWE-bench의 FAIL_TO_PASS에 해당), `retention`은 개선 전후 모두 통과해야 하는 검사(PASS_TO_PASS에 해당)다. `correction`은 soft assertion에만 붙인다. hard에 붙이면 `hard_correction_assertion`, 다른 값·`null`·빈 문자열은 `invalid_assertion_role`로 거절한다. `role`이 하나라도 있으면 `flips` 결과의 `roles`에 실행별 `correction_pass_rate`·`retention_pass_rate`, 후보 실행만 채점한 `resolution`(`FULL`·`PARTIAL`·`NO`), `retention_break_count`, 기준안에서 이미 통과한 `invalid_correction_tests`, 역할별 항목 수(`correction_count`·`retention_count`·`unlabelled_count`)를 담는다. `role`은 `compare`의 점수·`eligible`·개선 결정에 쓰이지 않는다. `role`이 없는 fixture는 바이트가 같아 manifest 해시와 실행 ID가 v0.30.0과 같다. [사용법](../tower-reliability.md#사례별-뒤집힘-표와-정정유지-역할-선택)
- **다른 대장의 사실 표에만 있는 값(`check-support`):** 인용한 노트가 다른 대장이면 그 사실 표는 2차 자료다. `check-support`는 인용 노트마다 `parse_ledger`가 알아보는 사실 표를 찾고, 값이 뒷받침됐지만 표를 뺀 본문 어디에도 없으면 그 행을 따로 표시한다. 기본 출력에 `rows_supported_ledger_table_only`(그런 행 수)와 `ledger_table_only`(항목마다 대장의 행 번호 `line`과 값이 사실 표에 있던 대장 경로 `via`, 값·칸 내용은 넣지 않음)가 더해진다. 그 행도 지금처럼 `rows_supported`로 센다. 선택형 `--primary-text-only`(API `check_support(vault, path, primary_text_only=True)`)를 켜면 그 행을 `rows_unsupported`로 세고 `ssot-source-unsupported` 경고의 `details`에 `reason: "ledger_table_only"`를 더한다. 이때 `parse_ledger`가 본문을 거절해 사실 표를 가려내지 못한 인용 노트를 `ledger_tables_unseparated`(항목마다 `path`와 `reason`: `column_limit`·`cell_limit`·`table_limit`·`row_limit`·`invalid_text`)로 알린다. 그런 노트는 본문 전체와 비교한다. 1차 출처 원칙은 W3C PROV-DM §5.2.4에서 빌렸고, 인용 그래프를 따라가거나 순환을 찾지 않는다. [사용법과 한계](../hardening.md#다른-대장의-사실-표에만-있는-값)
- **기간 표현 정규화(`check-support --normalize-periods`):** 리터럴 비교는 `2026-10-07`과 `2026. 10. 7.`, `2026년 3분기`와 `3Q26`을 다른 값으로 본다. 이 선택을 켜면 값과 인용 본문의 날짜·분기·반기·회계연도 표현을 반열린 날짜 구간으로 바꿔 행마다 `normalized_match`(`equal`·`contained`·`none`·`abstain`)를 따로 낸다. 결과는 새 필드 `normalized_periods`와 `period_convention`(`fiscal_start`와 비교 범위를 적은 고정 문자열 `scope`)에 담긴다. `normalized_periods`의 항목에는 `line`, `normalized_match`, `equal`·`contained`이면 `via`, `abstain`이면 `reason`이 있다. 같은(또는 안쪽) 구간이 다른 대장의 사실 표에만 있으면 `via_ledger_table_only`, 인용 노트가 읽는 길이(1,048,576자)를 넘어 비교에서 빠지면 `incomplete: ["period_text_limit"]`가 붙는다. 보류 사유(`reason`)는 `no_year`·`fiscal_start_undeclared`·`quarter_basis_ambiguous`·`relative_needs_anchor`·`multiple_periods`·`period_qualifier`·`partial_range`·`invalid_date`다. 기간 뒤의 수식어는 고정 목록에 있는 것만 알아본다. 기간 바로 뒤의 `말`은 문서의 조사 목록에 맞으면 그 기간의 마지막 하루로 계산하고, `초`와 기간을 좁히는 말(`후반`·`마지막 날`·`종료일` 등)은 `period_qualifier`로 보류한다. 회계연도(`FY2026`·`2026 회계연도`)는 `--fiscal-start MM`(`1`~`12` 또는 `01`~`12`, API는 `fiscal_start=4` 같은 정수)을 줄 때만 해석한다. `--fiscal-start`를 혼자 쓰거나 범위를 벗어나면 stderr의 `{"error":"ssot_operation_unavailable"}`와 종료 코드 1이다. `equal`·`contained`는 `rows_supported`에 넣지 않으며, 켜도 `rows_*` 수·경고·`issue_id`·`ledger_table_only`·종료 코드는 그대로다. 해석은 이 선택을 켤 때만 불러오는 새 표준 라이브러리 모듈 `vault_period.py`가 한다. 이름표는 Library of Congress EDTF에서 빌렸으며 `vault_period.parse()`의 결과(`label_edtf`)에만 있고 `check-support` 출력에는 넣지 않는다. 대장의 `valid_from`·`valid_until`·`recorded` 칸 검사, `check`, 현재 값 조립(`vault_assembly.py`)은 바뀌지 않는다. [사용법과 한계](../hardening.md#기간-표현-정규화---normalize-periods)
- **세션 기록으로 SessionStart 확인(`vault_doctor.py --session-evidence`):** 사용자가 지정하거나 승인한 Claude Code 세션 기록(`.jsonl`) 파일 하나만 읽어 결과를 Doctor 출력의 `session_evidence`에 붙인다. 폴더를 훑지 않고, 아무것도 쓰지 않고, 네트워크·모델을 부르지 않으며, Doctor의 종료 코드는 볼트 진단 값 그대로다. 옵션이 없으면 읽기 모듈 `vault_session_evidence.py`를 불러오지도 않는다. `status`는 `observed_error`(성공하지 못한 SessionStart 훅 기록이 있다. 실행되지 않음도 기록 없음도 아니다), `observed_truncated`(훅 출력이 호스트 상한 10,000자를 넘어 잘렸다), `observed_ran`, `not_recorded`(훅 기록이 없다. 실행되지 않았다는 뜻이 아니다), `unsupported_host_version`, `unparsed` 가운데 하나다. 기록이 섞이면 `observed_error`, `observed_truncated`, `observed_ran` 순으로 앞선 것을 보고한다. `session_start_hooks`에는 성공 기록 수(`records`)·잘린 수(`truncated`)·실패 수(`failed`)와 목록 `entries`(훅마다 `source`·`exit_code`·`duration_ms`·`emitted_chars`·`injected_chars`·`truncated`·`command_mentions_session_start_py`), `failed_entries`(실패마다 `source`·`outcome`·`exit_code`·`duration_ms`·`command_mentions_session_start_py`)가 있다. 지침 파일 첨부 수, 첫 응답의 프롬프트 토큰 합(`first_turn_usage`, 훅의 몫이 아니다), API 오류 수, 기록의 판 범위도 낸다. 내용·stdout·stderr·명령·식별자·기록 파일 경로는 출력하지 않는다. 지침 파일 경로는 `--session-instruction-paths`를 함께 줄 때만 보인다. 텍스트 출력에는 `session_evidence: <status> (<reason_code>)`로 시작하고 `session_next_action:`으로 끝나는 `session_` 줄들이 붙는다(목록에 실린 실패 기록마다 `session_start_hook_failed:` 한 줄). 세션 기록은 문서화되지 않은 호스트 내부 형식이다(`trust_boundary`: `host_internal_format_undocumented`). Codex 기록은 읽지 않는다. [읽는 값과 한계](../reliability.md#세션-기록으로-sessionstart-실행-확인-선택), [Doctor 절차](../../commands/vault-doctor.md)
- **요청 본문을 읽는 시험 서버(시험·문서만):** `tests/test_tool_safety_evaluation.py`의 루프백 전송 시험 두 개가 Windows에서 가끔 기대한 오류 대신 `transport_error`로 실패했다. 처리기가 POST 본문을 읽지 않고 응답한 뒤 연결을 닫아, 읽히지 않은 수신 데이터 때문에 연결이 RST로 끊긴 것이 원인이다(RFC 1122 §4.2.2.13). 두 처리기의 `do_POST`가 응답 전에 본문을 읽도록 시험 코드만 고쳤고 엔진·전송 코드는 그대로다. 새 `tests/test_http_handlers.py`는 `tests/*.py`(하위 폴더 제외)를 ast로 읽어, `def`·`async def`로 정의한 `do_POST`·`do_PUT`·`do_PATCH`가 첫 매개변수의 `rfile.read(...)`도, 허용한 도우미(`BODY_READ_HELPERS`)도 부르지 않으면 실패한다. 메서드 안에 읽기 호출이 있는지만 보며, 응답보다 먼저 읽는지·모든 경로에서 읽는지는 증명하지 않는다. 대입·`setattr`로 붙이거나 검사 범위 밖의 부모 클래스에서 물려받은 처리기는 찾지 못한다. 2026-10-24 22:33–22:46 KST, Windows 11, Python 3.12.10에서 `flaky_repeat.py`로 300번씩 반복하자 리다이렉트 시험은 수정 전 4/300(단측 95% 상한 0.0303)에서 수정 후 0/300(상한 0.0099)이 됐고, 응답 바이트 시험은 수정 전후 모두 0/300이었다. [원인·측정·한계](../evaluation-stability.md#요청-본문을-읽지-않는-시험-서버)
- **패키지:** Codex 격리 설치 검사(`scripts/verify_codex_plugin.py`)가 설치본의 `vault_period.py`도 저장소와 바이트로 대조한다. `commands/vault-doctor.md`에 `--session-evidence` 절차를 더했다. slash command는 15종 그대로다.

## 하위호환·업그레이드

**기본 동작.** 기본 출력에서 바뀌는 것은 `check-support` 결과에 더해지는 두 필드(`rows_supported_ledger_table_only`·`ledger_table_only`)뿐이다. 그 행도 `rows_supported`로 세며 나머지 필드·경고·`issue_id`·종료 코드는 v0.30.0과 같다. 시험이 v0.30.0(`452c5c0`)에서 캡처한 출력과 비교한다. 새 하위 명령·옵션을 쓰지 않으면 나머지 기본 출력과 종료 코드도 v0.30.0과 같다. 최종 검증(통합 커밋 `371143f`, 2026-10-25)이 `vault_ssot.py`의 `check`·`prepare`·기본 `check-support`, 시계를 고정한 `vault_runs.py`의 실행 ID·영수증 해시, `vault_doctor.py`, healthcheck(전체·`--staged`), SessionStart·checkpoint 훅과 CI 평가 단계를 v0.30.0과 비교했고, 그 뒤 `169d8a6`의 기본 `check-support` 출력은 `371143f`와 바이트가 같았다. 이 비교는 최종 트리에서 다시 실행해 [검증 기록](../verification/v0.31.0.md)과 `verification.json`에 남긴다. `--help`에는 새 하위 명령·옵션(`flips`, `--primary-text-only`·`--normalize-periods`·`--fiscal-start`, `--session-evidence`·`--session-instruction-paths`)이 보인다.

**기본 `check-support`의 비용.** 기본 `check-support`는 이제 인용 노트마다 `parse_ledger`를 한 번 실행해 사실 표를 찾는다. 출처 읽기 합계 상한(8 MiB) 근처의 합성 입력(인용 노트 128개, 합계 8.26~8.32 MB)에서 v0.30.0의 0.44초가 노트 모양에 따라 약 0.89~1.29초가 됐다(2026-10-25 최종 검증, 세 번 중 가장 빠른 값). 제목 줄 정규식은 공백이 아주 많은 제목 줄에서 이차 시간으로 느려지며, 이 비용이 이제 인용 노트에도 생긴다([알려진 경계](#알려진-경계)).

**경고 승격 인증서.** 이번 버전은 위 대장 기능을 위해 `vault_ssot.py`를 바꿨다. 이 파일은 `checker_sha256`가 묶는 일곱 파일(`vault_lint_extensions.py`·`vault_warning_policy.py`·`vault_provenance.py`·`vault_egress.py`·`vault_ssot.py`·`jev_client.py`·`vault_paths.py`) 가운데 하나이고, 일곱 파일 가운데 바뀐 것은 이 파일 하나다. 저장소 바이트(LF)로 다시 계산한 `checker_sha256`는 v0.26.0~v0.30.0의 `84cf52358d2bf2562af6e79e80a76572f0cfa3230d062cd8cd6438febcc04bfd`에서 `d8f9559a873ed7cf00f6982a2aeab28880227f403cec358e8e4e5c3fbfcbeb9c`로 바뀐다. benign corpus는 같다(LF `38efaabd…`). 2026-10-25에 v0.30.0(`452c5c0`)과 v0.31.0 릴리스 트리를 `git -c core.autocrlf=false archive`로 꺼내, 합성 git 볼트에서 `missing-anchor`를 `fatal`로 올리고 각 엔진에 다른 버전의 인증서를 두었다. 두 방향 모두 결과가 같았다.

- healthcheck는 `warning promotion rejected: promotion certificate checker_sha256 differs from current harmless replay`와 함께 종료 코드 1로 멈췄다.
- SessionStart 훅은 종료 코드 0이었지만 hot 노트를 주입하지 않고 stderr에 `agentic-vault: invalid session context configuration`만 남겼다.
- 볼트 pre-commit 훅이 실행하는 staged 검사(`vault_healthcheck.py --staged`)는 같은 오류와 종료 코드 1로 커밋을 막았다.
- `vault_doctor.py`는 `ready`(종료 코드 0) 대신 `invalid_config`(`config_schema_invalid`, 종료 코드 2)를 보고했다.

같은 버전에서 만든 인증서와 단계를 `warning`으로 되돌린 설정에서는 두 버전 모두 네 경로가 정상이었다. 인증서는 그것을 검사하는 엔진 사본마다 맞아야 한다. Claude Code와 Codex의 플러그인 설치본, 그리고 git 볼트에서 pre-commit 훅이 실행하는 볼트 안 엔진 사본(`00-meta/scripts/`)이 그 대상이다. 그래서 경고를 `fatal`로 올린 볼트는 갱신 전에 다음 순서를 따른다. 이전 버전으로 되돌릴 때도 같은 순서다.

1. 볼트 설정 `warning_policy.levels`에서 `fatal`로 올린 단계를 `warning`으로 되돌린다.
2. 볼트를 읽는 엔진을 모두 같은 버전(되돌릴 때는 이전 버전)으로 바꾼다. Claude Code와 Codex 설치본을 함께 바꾸고, git 볼트의 엔진 사본은 갱신할 때 `/vault-upgrade`(Codex `upgrade`)로 바꾼다. `/vault-upgrade`는 사본을 이전 버전으로 내리지 않으므로, 되돌릴 때는 그 사본도 이전 버전의 파일로 직접 되돌린다.
3. 바꾼 설치본에서 `vault_warning_policy.py --certificate`로 인증서를 다시 만들어 볼트 설정의 `warning_policy.certificate`에 넣는다.
4. 단계를 다시 `fatal`로 올린다.

버전이 섞인 동안에는 하나의 인증서가 모든 사본에 맞을 수 없으므로 승격을 켜 두지 않는다. 실제 사용자 볼트의 인증서는 자동으로 다시 쓰지 않는다. 인증서는 설치본의 실제 바이트를 묶으므로 줄바꿈 등이 다른 설치본에서도 맞지 않을 수 있다([v0.25.0 안내](v0.25.0.md#하위호환업그레이드)). 위 해시는 최종 트리에서 다시 계산해 `verification.json`에 남긴다. v0.25.0 이하에서 올라오면 [v0.26.0 이행 조건](v0.26.0.md#하위호환업그레이드)의 `via_bot` 수집 출처 조건도 따른다.

**혼합 버전과 되돌리기.** `role`이 있는 fixture는 v0.30.0 이하가 `invalid_assertion`(종료 코드 2)으로 거절한다. 새 버전이 `role` fixture로 준비한 실행도 v0.30.0의 `inspect`·`compare`가 같은 코드로 거절했다(2026-10-25 합성 볼트). `flips`는 v0.30.0에 없다. Claude Code와 Codex의 플러그인 캐시는 따로 갱신되므로 `role`로 준비한 실행을 읽는 설치본을 함께 갱신한다. 이전 버전으로 되돌리면 그런 실행은 조회·비교할 수 없다. `role` 없이 준비한 실행은 두 버전에서 같게 읽힌다.

**명령줄 약어.** `check-support`에 `--primary-text-only`가 생겨 `--path`를 줄여 쓴 `--p`가 모호해졌다. v0.30.0은 `--p`를 `--path`로 받았지만 이제는 argparse의 `ambiguous option` 오류와 종료 코드 2다. 약어는 문서화한 인터페이스가 아니므로 `--path`를 쓴다.

**그 밖.** healthcheck 스탬프(`engine=0.31.0`)와 `ENGINE_VERSION`은 0.31.0이다. 그 파일의 변경은 버전 표면뿐이며 내용이 같은 기존 규칙 6종은 스탬프를 유지한다. 기본 세션 훅·검색·모델/네트워크 호출·자동 적용·승격·런타임 의존성을 추가하지 않는다. Jarvis API 인증 조건도 유지한다. Codex 설치 ref는 `--ref v0.31.0`이다. [설치 안내](../codex.md#설치)에 따라 등록 소스·기존 캐시를 확인한다. 공개 릴리스, 활성 설치 캐시 갱신과 실제 볼트 upgrade는 별도 작업이다.

## 검증

구현은 다섯 갈래로 나눠 시험을 먼저 쓰고 통합했다. 구현 검토 두 번(뒤집힘 표·대장 표시·시험 서버·세션 기록의 조기 검토, 기간 정규화와 횡단 두 관점의 후기 검토)에서 확정한 차단 3건을 모두 고쳤다. 실패한 SessionStart 훅을 '기록 없음'으로 보고하던 문제, 조사가 붙은 `말`(`3분기 말에`)을 버려 기간 전체로 비교하던 문제, 연도를 생략한 범위 끝(`2026.10.07~10.09`)을 버려 첫날만 비교하던 문제다. 통합 커밋 `371143f`의 최종 읽기 전용 검증(기간·대장·세션·뒤집힘과 시험 서버·통합·문서와 릴리스 점검의 여섯 관점, 차단 지적은 별도 반박 검토)에서 차단 1건이 나왔다. 기간 뒤의 `후반`·`마지막 날`·`종료일` 같은 말을 무시하고 기간 전체로 비교하던 문제이며 `169d8a6`에서 고쳤다. 별도 읽기 전용 확인에서 차분 파싱 200만 건에 새 `equal`·`contained`가 없었고 기본 `check-support` 출력이 같았다. 나머지 다섯 관점은 차단·오류가 없었다. 차단이 아닌 지적은 [검증 기록](../verification/v0.31.0.md)에 남긴다.

`169d8a6`에서 로컬 Windows 11·Python 3.12.10 전체 시험 2,143개가 통과했다(환경 제외 34개, 실패·오류 0, 2026-10-25). v0.30.0 구현 당시는 2,025개였다. CI 평가 단계 11개와 컴파일·전체 트리 공백 검사도 통과했다. 이 수치는 버전 표면을 바꾼 최종 릴리스 트리의 검증을 대신하지 않는다. Python 3.10·3.14와 Linux·macOS는 CI 행렬에서만 확인한다.

최종 metadata·README·CI 행렬·Codex 격리 설치·Claude 매니페스트 검사·ZIP/blob·재빌드와 독립 검토는 고정 소스의 게시 전 `verification.json`에 기록한다. [릴리스 검증 범위](../verification/v0.31.0.md)를 함께 본다. 자산은 `agentic-vault-0.31.0.zip`, `SHA256SUMS`, `verification.json`이며 게시 후 증명·공개 재다운로드 확인은 별도 `post-publication.json`에 남긴다.

## 알려진 경계

- **기간 정규화의 남은 꼴:** 기간 뒤의 수식어는 고정 목록에 있는 것만 알아본다. 목록에 없는 말과 최종 검증에서 찾은 몇몇 표기는 여전히 기간 전체나 한쪽 끝으로 비교되어 틀린 `equal`·`contained`를 낼 수 있다. 꼴과 예는 [기간 표현 정규화의 한계](../hardening.md#기간-표현-정규화---normalize-periods)에 있다. `equal`·`contained`는 같은 구간이 인용 본문 어딘가에 나온다는 뜻일 뿐 같은 사실에 대한 서술이라는 뜻이 아니다. 실제 볼트에서의 오탐률·놓침률은 측정하지 않았다.
- **제목 줄 정규식의 이차 시간:** `parse_ledger`의 제목 정규식은 `#` 뒤 공백이 아주 많은 한 줄에서 이차 시간으로 느려진다. 인용 노트에 `# a` 뒤 공백 N개와 `b`가 있는 줄이 있으면 기본 `check-support`가 N=16,000에서 1.79초, 32,000에서 5.31초, 64,000에서 20.25초 걸렸다(v0.30.0은 0.3~0.5초, 판정은 같음, 2026-10-25 `169d8a6`, Windows 11·Python 3.12.10). 검사하는 대장 자체에 그런 줄이 있으면 v0.30.0도 같은 비용이 든다(N=32,000에서 약 5.3초). 정규식을 선형으로 바꾸는 일은 별도 강화로 남긴다.
- **SessionStart 실패 기록의 모양:** 성공하지 못한 훅 기록(`hook_non_blocking_error`·`hook_blocking_error`·`hook_cancelled`·`hook_error_during_execution`)과 잘림 안내 문구는 Claude Code 2.1.309 실행 파일의 문자열에서 확인했고 실제 세션 기록에서 관측하지 않았다. 훅 기록의 판 범위는 2026-10-24 Windows PC 한 대의 기록에서 본 관측값이다. `not_recorded`는 실행되지 않았다는 뜻이 아니며, 기록은 모델이 기억을 사용했다는 증거가 아니다.
- **플랫폼:** 로컬 검증은 Windows 11·Python 3.12.10에서만 했다. Python 3.10·3.14와 Linux·macOS는 CI 행렬에서만 확인한다. 루프백 시험의 경쟁은 Linux·macOS에서 드러나지 않을 수 있어 CI 통과가 그 수정의 증거는 아니며, 플랫폼과 무관한 방어는 ast 검사다. 0/300은 실패율 상한이지 실패가 없다는 증명이 아니다.
- **뒤집힘 표와 역할 등급:** 반복 2~10회, 최대 16사례×8assertion에서 센 서술 값이며 p값을 내지 않는다. 관찰은 호스트가 보고한 값이고, correction 검사가 기준안에서 올바른 이유로 실패했는지는 확인하지 않는다. 등급은 검토 자료이며 적용 승인이 아니다.
- **사실 표 표시의 범위:** `ledger_table_only`는 표 구조만 보는 규칙이며 출처 계보를 판정하지 않는다. 대장의 산문이나 대장 값을 옮겨 적은 일반 노트를 거친 값은 1차 근거로 센다. `parse_ledger`가 거절한 인용 노트는 기본값에서 아무 표시 없이 본문 전체와 비교한다(`--primary-text-only`에서만 `ledger_tables_unseparated`로 보인다).
