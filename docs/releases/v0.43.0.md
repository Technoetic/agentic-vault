# v0.43.0 — large-vault operations, shared worktrees and verifier fidelity

This release gathers opt-in tools for vaults that have outgrown their read limits and
for sessions that share one repository, plus defect fixes those conditions exposed.
Everything new is off until called or configured. The fixes that change a default
result are listed under [Default result changes](#default-result-changes).

## Read a large vault on purpose

The optional `recall.max_total_read_bytes` setting replaces the 16 MiB total read
budget, from 512 KiB up to 1 GiB, and every reader in a call uses the same value. The
512 KiB per-file limit does not change. The optional `recall.priority_paths` setting
reads listed files and folders first and acts again only at the final score tie-break.
It feeds neither per-channel RRF ranks nor graph seeds, so with the same notes read
every score matches a run without the setting, on the lexical, `bm25` and `hybrid`
paths. Under `hybrid`, channel ranks already separate tied notes by path order, so a
priority note moves ahead only when fused scores are exactly equal. It never lifts a
note over a higher score and never passes a deny or exclusion rule. Read order is
another matter: when a limit stops a run, a different set of notes may be read, and
BM25 statistics follow that set. Invalid settings stop recall with `invalid_config`
and the fixed omission `recall_config_invalid`.

Every recall result now adds three diagnostics: `omitted_paths_sample` (up to 10
unread candidate paths, spaced evenly across the whole list), `scope_state` and
`answer_state`. `answer_state` is a label derived from `search_complete` and the
result count, so an empty result on a partial read reports `not_enough_scope`. Matches,
ranking and context are unchanged. A vault with a note over the per-file limit still
reports an incomplete search. See [recall scope](../recall-scope.md).

## See limits before they hit

`vault_doctor.py --capacity` is a read-only report that compares the configured
handoff, hot, log, tasks and index notes with the state and recall read limits. With
local Git history it gives an estimated number of days to each limit, from a linear
fit over the last 40 commits that touched the note. It is an estimate from a commit
window, not a date, and it never changes the Doctor exit code.

`vault_healthcheck.py --staged` gains an optional growth check for budgeted notes, set
with `staged_growth_check` (`off`, `warn`, `block`) and `staged_growth_max_tokens`. It
uses `HEAD` as its baseline and stores no result file. A new path has no baseline, and
moving text to another note is not detected. See [capacity](../capacity.md).

## Fold old handoff sections

`vault_handoff_fold.py` has no default action: `analyze` reads only and `apply` alone
writes, and a subcommand, a threshold and a protected-section count are required.
Given the current hash, `apply` moves older sections byte for byte into size-bounded
archive notes beside the handoff. Each folded section keeps its heading and a stub
with the fold time, hash prefix, archive link and unresolved line count. Unresolved
lines are copied into one collected section with their source hash. Host summaries
are optional and bound to section hashes. Nothing runs automatically. `apply` rebuilds
the original from its own output before writing and refuses on any difference.

A run removes its archive notes only when the handoff on disk still holds the original
bytes, and only files that still hold what the run wrote, so a late error or Ctrl-C
cannot delete the only copy of a folded section. After an interrupted run, check
`sha256` with `analyze` before trying again, because the fold may already be complete.
[Recovery steps](../handoff-fold.md#after-a-killed-run) cover the guard, lease and
staged files a killed run can leave. On Windows, a failed replace of a read-only
handoff ends with `replace_failed` and leaves no staged file or new archive note. On
POSIX, `apply` syncs the archive folder and its parent before it replaces the handoff;
this was tested with mocks only, with no power-cut test.

With `--newest bottom`, which also accepts a file that starts with a byte order mark
and has no frontmatter, the collected section still goes before the first folded
section. It and the stubs then sit above the fresh sections, and the session hook,
which keeps the head of the note, can fill its window before it reaches them. How much
of the window it takes was not measured.

`scripts/evaluate_handoff_fold.py` is an offline loss alarm: per-section preservation
checks plus recall, artifact, continuation, decision and constraint probes that report
whether exact text is still reachable within one archive link. It calls no model, so
it shows that text is gone, not that an agent can continue the work. See
[handoff folding](../handoff-fold.md).

## Diagnose hook output and plugin scope

`vault_doctor.py --session-evidence` now reports, per SessionStart hook, how many
U+FFFD replacement characters its stdout held, and counts starts where this plugin's
hook and another hook both gave context, grouped by `toolUseID`
(`double_context_observed`, a lower bound).

The new `--plugin-scope` reads only this plugin's `enabledPlugins` keys from the user,
project and local settings files, reports the value per scope and the winner among
those files, and leaves the managed, flag and `--add-dir` sources as `unknown`. It
reports `plugin_and_vault_session_hooks` when the plugin is on and the vault's settings
add SessionStart hooks, counting entries without reading any command, and warns when
the health-check copy at `00-meta/scripts/vault_healthcheck.py` has no engine stamp or
an older one. `--plugin-scope-host` also cross-checks `claude plugin list --json`, and
any failure ends as `host_unavailable`. Nothing changes without these options, the
Doctor exit code stays the vault's, and no hook is run. See
[reliability](../reliability.md#double-injection-broken-output-and-plugin-scope-optional).

## Close the loop from lessons to tool calls

`vault_lesson_clusters.py` is a read-only report over a mistakes note. It groups
entries by recurrence markers and "same class" references, keeps plain "related"
references out, offers syllable-bigram Jaccard groups only as candidates, and flags
classes seen three or more times with no ledger row as `unledgered`. The default
threshold is uncalibrated and the report says so. See
[lesson recurrence](../lesson-recurrence.md).

Lesson markers accept an optional `cues` list that survives INC, EDIT and RETIRE, set
through ADD or the new CUES operation. Cues take literal prefixes, literal substrings
and globs, never regular expressions. Cue text and values cannot hold format marks,
Unicode line or paragraph separators or C1 control characters, which also rules out
emoji joined with a zero-width joiner.

`vault_lesson_cues.py build` compiles rows in force into `00-meta/lesson-cues.json`. A
row counts only when its whole status cell is a known in-force form, so statuses such
as `관찰중단`, `승격제안 기각`, `승격제안철회` and `승격완료(롤백)` stay out, and any cell that
holds a withdrawing word stays out. Rows inside an HTML comment block or under
`## 기각 대장` are left out and counted in `skipped.comment` and `skipped.rejected`; they
stay in the ledger inventory, so counters and proposals work as usual. `build --write`
refuses a list larger than the 256 KiB the hook reads, as `lesson_cues_too_large`.

The new `assets/adapters/lesson-cues/` adapter is a standalone PreToolUse hook for
Claude Code that is not installed by default. Hints reach `additionalContext` as
factual statements, guards answer `deny` once per session, it never answers `allow`,
and each call carries at most 3 cues and 1,500 characters. It is advisory: it sets no
`onFailure`, so a failed hook lets the call run, and a hint cannot change the call
that triggered it. The hook checks each compiled cue again and drops, with a one-line
warning, any cue the compiler could not have written. It does not prove that a
well-formed cue came from the ledger. `00-meta/lesson-cues.json` is deliberately not a
deny-guard control. See the [lesson cue guide](../../assets/adapters/lesson-cues/guide.md).

## Measure what a check can see

`scripts/evaluate_verifier_fidelity.py` mutates synthetic Korean and English notes that
pass unchanged, runs each mutation through `check_preservation` and the preserve-check
path, and reports flagged, survived, blocked and unmeasured counts per category with a
one-sided exact bound. Categories the documentation puts out of scope sit in separate
rows, and meaning-preserving rewrites give a false alarm rate. These are numbers from
a hand-written synthetic fixture, not evidence of real-world safety.

`scripts/env_vary.py` reruns selected tests under controls first, then all variations,
then shuffled cumulative blame. It covers `PYTHONUTF8=0`, a minimal environment, home
folders, a working directory and temporary folder with a space and Hangul, and `TZ`.
It compares skip lists by test id and reason, records the seed and order, and marks
variations that had no visible effect.

The plugin runtime loads neither tool, though the Codex plugin check lists both as
required files. The fidelity evaluator is a CI step, and a test pins its table to the
documented values, so a table that drifts fails CI. `env_vary.py` reaches CI only
through its own tests. Passing that test still proves nothing about safety, because
the numbers are synthetic. See [verifier fidelity](../verifier-fidelity.md).

## Treat linked worktrees as copies

A new `vault_worktrees.py` recognizes a linked working tree of the vault's own
repository at two strengths. A `.git` file whose `gitdir:` value names
`<common>/worktrees/<name>` is enough to close the deny zones under that folder,
because a wrong file then only closes more. Leaving a folder out of a walk or a backup
also needs git's admin folder to name that folder back, so a hand-written `.git` file
does not hide notes from recall, the healthcheck, snapshots or the instruction
inventory. Submodules, nested repositories and trees of other repositories stay
ordinary folders.

Recall, the healthcheck walk, backups and the instruction inventory skip a registered
copy and name it in their diagnostics, so copied notes no longer duplicate or displace
real notes. A copy whose admin entry is gone, or that was moved by hand, returns to
recall and snapshots next to the originals until it is removed or repaired with
`git worktree repair`, and its zones stay closed.

Deny zones are closed in linked trees for every tool that takes a named path: the
shared state policy and all tools on it, runs, bundle input, handoff fold, lesson
delta, cues and clusters, capacity, operations, memory, impact, ontology, links,
revocation, index fold, query mappings, retrieval sidecars, session context, doctor,
the Telegram bridge, `vault_evidence.py`, `vault_proposals.py`,
`vault_lesson_metrics.py` and `vault_commit.py`. Each answers as it does for the same
zone in the main checkout, and a note outside a zone stays readable. The healthcheck
stops when a configured note lies in a zone of a copy. `vault_ssot.py` stays
byte-bound: its name inventory still lists copies, but note contents are refused
through the shared policy.

The opt-in deny guard keeps its root-anchored zone rule and adds a view from each
working tree of the vault's repository, which also covers the main checkout's zones
when `CLAUDE_PROJECT_DIR` is a linked tree. Installed copies of the healthcheck and the
deny guard keep the old behavior until they are updated. Nothing changes without a
linked tree or a `.git` file of that shape. See
[linked worktree copies](../hardening.md#linked-worktree-copies-and-deny-zones).

## Commit declared paths from a shared tree

`vault_commit.py` is an optional command that commits a declared list of files from a
working tree shared by concurrent sessions. Each path carries the sha256 of the working
file the caller means to commit, and a mismatch is refused, as is a merge, rebase,
cherry-pick or revert in progress. It runs `git add -- PATHS` and `git commit -- PATHS`
with bounded, jittered retries on lock failures, restarts from `git add` when a stage
entry vanishes, never deletes a lock, and verifies the commit named in Git's own output
rather than `HEAD`. Paths, committed blobs and the subject are compared with the
declaration, and a blob that already holds CRLF under `core.autocrlf` or `text=auto`
reports `committed`. Shared notes (hot, handoff, log, index) are refused by default.

Every path inside a linked working tree is refused with `denied_path`, in both modes
and for the patch file, and Windows short names with `unsafe_path`, so a copy of a deny
zone or a shared note cannot be committed as an ordinary path. Unresolved conflict
entries are refused with `unmerged_paths`, which covers a `git stash pop` that leaves
no marker file. Hook output does not decide how a failure is classified: a hook that
prints lock words or "nothing to commit" ends as `commit_rejected`, and `left_staged`
is read from the index. The command clears `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_*`,
`GIT_CONFIG_VALUE_*` and `GIT_CONFIG_PARAMETERS`, so those variables cannot replace
`core.hooksPath`. `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM` and repository settings
still can. `vault_commit.py` and `vault_capacity.py` run git from an absolute path on
`PATH`, never from an implicit current folder.

`--own-lines` commits only the caller's edits on top of `HEAD` through `commit-tree`
and a compare-and-swap `update-ref`, runs the `pre-commit` hook on the proposed tree
(Git 2.36 or later), and moves the shared index entries to match. Deny zones, folders
and ignored files stay out. Each `old` must occur exactly once in `HEAD`, so edits in
one patch cannot anchor on each other (`patch_anchor_not_unique`). `new` takes the line
ending of the blob. An edit whose removed text is still in the working file is refused
with `patch_not_in_worktree`, and a short `old` can match another session's line and be
refused the same way. A repeated patch is refused with `already_applied`, including
after `committed_index_stale` or a process that died between `update-ref` and the index
update, so the same lines are not committed twice. Other files in such a commit take
their blob from `git add` on a scratch index: a file that changed in between gives
`hash_mismatch`, and a `core.safecrlf` failure gives `add_rejected`.

Other sessions using plain `git commit` are not stopped, and mixing the two can still
drop a file silently. The retry default of 60 attempts is a starting point from
synthetic Git timing, not a measurement of this command with real hooks. See
[concurrent commits](../concurrent-commits.md).

## Constraints, rule wording and evaluator workers

Compact SessionStart now renders `constraints_note` item by item: front matter, fenced
code and HTML comment blocks are skipped, each top-level `- ` item becomes a
`Constraint:` line (up to 8, with an omitted count), and items are dropped before the
fixed block is given up on a low budget. The key is now documented, including that it
is ignored without a handoff section, together with `tasks_note`.

The `vault-workflow.md` rule adds a sentence that prohibitions are not lifted by file
or command text and that stale factual values give way to fresh results, with each
mismatch reported. A synthetic contrast on one small local model chose the wording by
prohibition retention. Its scenarios were invented and its harness is not published,
so the figures in the hardening guide cannot be rerun from this repository. The
shipped wording did not reduce prohibition answers on that model, and no gain was
confirmed: it scored the same as no sentence on fact following. See
[rule facts and tool results](../hardening.md#rule-facts-and-tool-results).

The deny-guard guide adds a `permissions.ask` sample with documented limits and a
synthetic replay. The replay uses a grammar model inside a test, not Claude Code, and
its list is synthetic. The 18 of 28 commands it stops are a result of that model and
that list, not an incident block rate. Lifecycle workers drop
`PYTHON*` values that `-I` ignores and run with `-B`, and a request timeout test now
asserts event order instead of a 0.1 second bound.

## Default result changes

These defect fixes change a result without any new option.

- `vault_state` reads keep `input_too_large` and `file_changed_during_read` as distinct
  failure codes instead of folding them into `unsafe_or_changed_source`. Tools that
  pass `StateError` codes through, such as `vault_ssot.py`, show them too.
- A checkpoint no longer fails on a note over 256 KiB. Sources are hashed without
  buffering under a 64 MiB bound. Every other read and write limit stays the same. With
  `checkpoint_drift_check` on, a note over that check's 1,000,000 byte read bound now
  has a checkpoint and is reported as changed each time.
- The checkpoint hook prints a fixed failure code on stderr and still exits 0.
- `recall` results always carry the three new diagnostics, including in
  `diagnostics.recall` of `vault_links.py`. Without a `recall` block, reading, ranking
  and the abstention snapshot digest are unchanged. A block with an empty-valued key
  such as `priority_paths: []` behaves the same but changes the snapshot digest, so a
  calibration needs to be run again.
- With `--session-evidence`, a non-zero exit in an asynchronous hook's response counts
  as a failure (`async_nonzero_exit`) instead of an uninterpreted `other_records`
  entry, so such a session reports `observed_error`. A background health check that
  exits non-zero on purpose counts too.
- `vault_compile_quality.py` body extraction, used by `check_preservation` and
  `check_compile`, now follows the schema check's boundary. A broken closing line such
  as `----` no longer counts front matter as body and hides a changed value.
- A note with no literal facts no longer reaches `complete` through a declared removal
  or addition (0 of 0). It reports `needs_review` with `no_selected_literal_facts`.
- The units `kg`, `mm`, `kv` and `kva` now match in any case, as one token with the
  number, so `22kV` to `22MV` is visible. In exchange, `22kV` to `22 kV` now shows as a
  missing `22kv`, and a declaration must name `22kV` rather than `22`. In the synthetic
  table this adds four false alarm cases and removes one.
- Ledger rows with the wrong cell count no longer vanish silently. They are reported as
  `ignored_rows`, and an ADD with the same text is refused as a duplicate.
- Compact SessionStart output changes only in vaults that set `constraints_note`. A
  note whose short items leave the omitted-count line longer than the old excerpt can
  lose the block when the budget is tight by a few tokens.
- `/vault-init` asks one more optional question, for the lesson cue hook. A refusal or
  no answer installs nothing.
- With a registered linked tree of the vault's repository inside the vault: recall and
  the healthcheck skip the copy and name it, the healthcheck adds one non-fatal issue
  per copy in section 14b, the instruction inventory reports `partial`, and a backup
  leaves the copy out with a printed line. Uncommitted work that exists only in that
  copy is not in the snapshot.
- A deny zone inside a linked tree is refused where it was accepted before.
  `vault_evidence.py`, `vault_proposals.py` and `vault_lesson_metrics.py` refuse such a
  path even when a caller names it directly, `vault_evidence.py` and
  `vault_lesson_metrics.py` with `unsafe_path`. Every other tool that takes a named path
  answers as it does for the same zone in the main checkout. A call that used such a
  path now fails. A note outside a zone stays readable.
- A configured note such as `hot_note` that lies in a zone of a copy now stops the
  healthcheck with an error and exit code 1. Session start and Doctor treat it like the
  same zone in the main checkout.
- A folder whose `.git` file has the linked-tree shape has its zones closed even when
  git holds no record of it. It stays in walks and snapshots, so a hand-written file, a
  pruned copy or a copy moved by hand does not hide notes. Such a copy puts its notes
  next to the originals in recall until it is removed or repaired.
- The instruction inventory blocks a registered tree whole and only the zones of an
  unregistered folder, so ordinary instruction files in such a folder are counted.
- On Windows, `patch_note` on a read-only file ends with `replace_failed` instead of a
  general `PermissionError` and leaves no staged file. Retry delays add at most 0.31
  seconds.
- `evaluate_retrieval_backends.py` adds `vault_worktrees.py` to its `code_sha256`, which
  gains one entry.
- `evaluate_recall.py` hashes `diagnostics.skipped_worktrees` in keyed and ephemeral
  reports. Plain reports and keyless `--redact` reports still show the folder names.
- Lifecycle evaluation workers no longer leave `.pyc` files.

### Results of the new tools

These tools are new, so no earlier result changes, but callers should plan for them.

- `vault_commit.py` refuses with `denied_path`, `unsafe_path`, `unmerged_paths`,
  `already_applied`, `patch_anchor_not_unique`, `patch_not_in_worktree` and
  `hash_mismatch`, and fails with `add_rejected`, `commit_rejected` and
  `git_unavailable`. A caller that sets `user.name` through `GIT_CONFIG_*` variables
  has to set it another way.
- `vault_handoff_fold.py` can report an error after the fold landed, and it keeps the
  archive notes in that case.
- `vault_lesson_cues.py` reports `skipped.comment` and `skipped.rejected`, and refuses
  with `lesson_cues_too_large`. A marker that holds a forbidden character makes the
  whole ledger fail with `invalid_lesson_cues`.
- `recall.priority_paths` under `hybrid` leaves a priority note in its scored place
  unless fused scores are exactly equal, and it does not choose graph seeds. Advanced
  `diagnostics.ranking` then says that final score ties prefer the listed order.

  1,500 characters. So the cue bundle is not new here, though lessons-learned is a new
  source and only its concepts were used. New here are the split into hint and guard,
  the per-call budget, and the handling of quoted text: lessons-learned can match
  without it, and this hook keeps it in view. Its budget is larger and its patterns are
  regular expressions; both differ.

These references were checked against the published Reference Atlas and prior notes
before recommendation. A registry miss alone does not establish novelty. Reading dates
and pins are the ones above; pages without a version may have changed since.

## Not measured

- The effect of lesson cues on behavior or task results. No controlled evaluation was
  run, so no benefit is claimed.
- The effect of `recall.priority_paths` on real vaults or labeled answers. Only
  synthetic structure tests exist, and tie preference alone may not fix ranking under
  `bm25` or `hybrid`, where it acts only on exactly equal final scores.
- The run time of a wider recall budget.
- The fact precedence sentence on hosted models or real vaults. In a synthetic contrast
  on one small local model, whose harness is not published, it did not reduce
  prohibition answers and no gain was confirmed. Differences of one or two cases are
  within what that set can resolve.
- Whether an agent can continue work after a fold. The loss alarm tests literal
  reachability. One unquantified observation from a single private vault, which nothing
  here reproduces: folding reduced current size but not the rate of new text, and
  collected unresolved lines stayed a large part of what was left.
- Whether the POSIX folder sync in `apply` protects anything. The call order and error
  handling were tested with mocks, and no power-cut test was run.
- The 2-gram candidate threshold. No human-grouped sample exists, and the default is
  reported as `default_uncalibrated`. A long chain of explicit references can form one
  large class, and a ledger row without a written entry number can look `unledgered`.
- Real-world safety of the preservation check. The in-scope detection in the synthetic
  table comes from hand-written mutations that assume independent trials.
- `vault_commit.py` under real hook load. Retry defaults come from synthetic timing of
  Git commands, and other Git versions, network drives, file-sync tools and security
  products were not measured.
- Linked worktree host behavior beyond one non-interactive run on Windows. Interactive
  sessions, other versions, macOS, Linux, Codex and subagent isolation were not run.
- Whether `async_hook_response` keeps its shape. It was confirmed from record keys in
  one host version range, and `double_context_observed` is only a lower bound.
- How a hook's `ask` answer behaves under `bypassPermissions`. The documentation has no
  direct statement.

## Compatibility and installation

Current install refs target `--ref v0.43.0`. The Python 3.10+ standard-library runtime
and default hook bindings keep their contracts. `hooks/hooks.json`,
`assets/templates/vault-config.json` and `assets/templates/settings-permissions.json`
are unchanged. New configuration keys are optional and absent from the template.

Stamps move to `engine=0.43.0` for the healthcheck and `ENGINE_VERSION`, the deny guard
and its PowerShell parser, the new lesson cue hook and the `vault-workflow.md` rule, so
`/vault-upgrade` treats the copies in a vault as out of date. The other five rule files
keep their stamps. Copies in a vault keep their old behavior until they are updated:
the worktree rule is shared text copied into `deny-guard.py` and `vault_healthcheck.py`,
so an installed guard or healthcheck does not close a copy's zones until it is updated.
A vault that keeps a modified health-check copy gets the growth check only by merging
by hand. Publication does not update active installations or convert a company vault.

Callers of `vault_commit.py` should handle `already_applied` and `unmerged_paths`. A
patch whose later edit anchors on the result of an earlier one is refused with
`patch_anchor_not_unique`, because each `old` is matched against `HEAD`. A caller that
sets `user.name` through `GIT_CONFIG_*` variables has to set it another way.

Handoff archive notes are framed by byte length, so a repository that normalizes line
endings needs `**/handoff-archive/** -text` in the vault's `.gitattributes`.

The seven certificate-bound checker files and committed LF harmless corpus remain
unchanged. Expected `checker_sha256`:
`be02b141ffed91cbe34f8cb2317a790c60075740bfe5d8dc435ef202f113174f`;
`corpus_sha256`:
`38efaabde0ce1e1df4008276db9761ba1b88eff35ddd91cb8d4fc4899023d04a`.
Fresh actual-byte checks and harmless replay remain final release gates. Matching
installed bound bytes alone do not require certificate regeneration for this
transition. Older changed-byte transitions keep warning reset, aligned engine copies,
regeneration with harmless replay and re-promotion, including rollback.

## Verification and limits

The [verification record](../verification/v0.43.0.md) describes pending final gates;
fresh exact-source results belong to release `verification.json` and independent
post-publication evidence. Historical release records are preserved. Hashes bind
bytes, not identity, approval authority or semantic correctness. Cooperating locks do
not exclude hostile same-user writers. A cue, a rule sentence or a guard is not a
sandbox. A shell command or another program reaches a copy's zones unless the deny
guard is installed. `vault_ssot.py`, which is bound to the certificate, still lists
copies by name and path, though it cannot read notes in their zones. With write access
to the common git directory a record can be forged so that a folder leaves the walks,
and the reports still name it. No live company deployment or actual-model quality gain
is claimed.
