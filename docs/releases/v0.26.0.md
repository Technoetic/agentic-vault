# v0.26.0 — Jarvis via_bot 출처, 디렉터리 이름 목록 대조, 골드셋 키 가명화와 재현 가능한 릴리스 ZIP

Jarvis가 인라인 봇을 거친 메시지를 신뢰하지 않는 `via_bot` 출처로 수집하도록 기본 동작을 바꾼다. 선택형
질의 확장과 지침량 진단은 디렉터리 시각과 함께 항목 이름 목록을 대조한다. 골드셋 보고서의 키 가명화, 재현
가능한 릴리스 ZIP과 재빌드 확인, 간헐 실패 테스트의 반복 측정 도구를 선택형으로 더한다. 시험은 Windows 정션을
콘솔 출력 없이 만든다. 핵심 엔진은 Python 3.10+ 표준 라이브러리만 사용하며 기본 모델·네트워크 호출, 런타임
의존성, 훅 정의를 추가하지 않는다. `vault_provenance.py`가 바뀌어 경고 승격 인증서의 `checker_sha256`가
바뀐다(아래 업그레이드). [수집과 경고](../hardening.md#수집과-경고), [검색 평가](../hardening.md#검색-평가),
[키 가명화](../memory-evaluation.md#개인정보와-보관), [ZIP 재현과 재빌드 명세](../release-integrity.md#zip-재현과-재빌드-명세),
[간헐 실패 테스트](../evaluation-stability.md#간헐-실패-테스트-분류와-반복-측정),
[릴리스 검증](../verification/v0.26.0.md)을 함께 확인한다.

## 변경

- **Jarvis 인라인 봇 메시지 출처(기본 동작 변경):** 허용된 사용자가 인라인 봇으로 보낸 Telegram 메시지
  (`via_bot`)는 이제 `content_origin: via_bot`으로 수집된다. 이전에는 `own`으로, 링크 하나뿐이면 `url`로
  기록됐다. 본문은 제3자 봇이 만들었기 때문이다. 판정 순서는 forwarded → via_bot → url → own이며, 전달 정보가
  함께 있으면 계속 forwarded다. via_bot은 forwarded·url처럼 신뢰하지 않는다. 사용자가 일부러 인라인 봇으로 보낸
  메모도 같다. 파생 manifest의 신뢰도는 untrusted가 되고, 이를 참조하거나 그 자체인 privileged 노트에는 staged
  경고 `provenance-unresolved`가 붙는다. 브리지는 `getUpdates`에 계속 `message`만 요청한다. `guest_message`
  (Bot API 10.0) 같은 다른 업데이트는 처리하지 않으며 시험이 이 값을 고정한다. 이미 저장한 수집은 다시 분류하지
  않는다. 프런트매터 스키마 템플릿과 `commands/vault-ingest.md`·`commands/vault-jarvis-setup.md`에 via_bot을
  적었다.
- **디렉터리 이름 목록 대조:** Windows는 항목을 바꾼 직후에도 디렉터리 수정 시각이 그대로이거나 늦게 바뀔 수
  있다. 그래서 선택형 질의 확장의 별칭 inventory 확인과 지침량 진단은 시각만으로 도중 변경을 놓칠 수 있었다.
  이제 처음 걷기에서 본 각 디렉터리의 항목 이름 목록 SHA-256을 함께 묶는다. 이름만 정렬해 쓰고 inode·크기·내용은
  넣지 않는다. 걷기 때는 그 걷기의 목록을 다시 써서 디렉터리를 더 읽지 않는다. 끝의 확인에서 표지가 있는
  디렉터리마다 이름 목록을 한 번 다시 읽는다. 하위로 내려가지 않고, 항목 합계는 기존 상한(검색 20,000개, 지침
  512개)을 따른다. 이름 목록만 바뀌어도 변경으로 본다. 질의 확장은 `source_changed`로 닫고
  `inventory_verification.changed_directory`에 `change: listing`을 적는다. 시각 등 stat 차이는 `metadata`,
  다시 읽지 못하거나 상한을 넘으면 `unavailable`이다. 지침 진단은 `directory_changed_during_diagnosis`
  (`change: listing`)로 `partial`이 되고, 다시 읽지 못하면 `unreadable_instruction_directory`·
  `unsafe_instruction_directory`·`directory_entry_limit`로 `partial`이 된다. 별칭 inventory 확인은 처음 바뀐
  디렉터리에서 멈추므로 `listing_diagnostics`는 많아야 한 줄이다. 질의 확장을 켜지 않은 recall 기본 경로는
  바뀌지 않는다. 추가 비용은 `scripts/bench_directory_listing.py`로 잰다(아래 검증).
- **골드셋 보고서 키 가명화(선택):** `scripts/evaluate_recall.py`에 `--redact-key-file FILE`과
  `--redact-ephemeral`을 더했다. 둘 다 `--redact`를 포함하고 함께 쓸 수 없으며 기본값은 꺼짐이다. 기존
  `--redact`는 키 없는 sha256이므로 후보 값을 추측해 해시하면 되돌려 맞출 수 있다. 키 옵션은 자유 텍스트를
  HMAC-SHA256(키, 텍스트)으로 바꾼다. 볼트 상대 경로, `label_matches`의 라벨·후보, sha256 지문, 골드셋 경고 안의
  후보 경로, 시간 진단의 `superseded_by`도 같은 키로 바꾼다. 경로는 통째로 해시한다. 앞쪽 폴더 이름도 민감할 수
  있어서다. `valid_from`·`valid_until`·`checked_at`·`superseded_at`은 날짜 모양일 때만 남긴다. 키 파일은
  32바이트 이상, 64 KiB 이하여야 한다. 평가하는 볼트 안(fixture 모드에서는 fixture 디렉터리)에 있으면 읽기 전에
  종료 코드 2로 끝낸다. 이때 Windows 확장 경로 접두를 떼고 비교하고, 상위 폴더의 파일 식별자도 볼트 루트와 맞춰
  본다. 작업 디렉터리나 표준 출력 파일 옆의 키는 경고만 한다. `--redact-ephemeral`은 실행마다 32바이트 키를 새로
  만들고 저장하지 않는다. 보고서에 `redaction_mode`(`unkeyed`·`keyed`·`ephemeral`)와 `redaction_algorithm`
  (`sha256`·`hmac-sha256`)을 남긴다. 키와 키의 지문은 남기지 않는다.
- **재현 가능한 릴리스 ZIP과 재빌드 확인(유지관리 도구):** git은 ZIP 항목 시각을 실행 환경의 지역 시간대로
  적는다. 시간대를 고정하지 않으면 같은 태그도 다른 파일이 된다. v0.26.0부터 릴리스 ZIP을
  `TZ=UTC0 git -c core.autocrlf=false archive --format=zip --prefix=agentic-vault-VERSION/`로 만들고,
  `verification.json`에 `rebuild_spec` 블록(태그, 커밋, git 버전, `TZ`, prefix, `core.autocrlf`, 형식, 실행 인자,
  기대 SHA-256, 확인 단계)을 넣는다. 이 릴리스의 ZIP이 이 절차로 만드는 첫 자산이다. 새 스크립트
  `scripts/release_rebuild.py`는 표준 라이브러리만 쓰고 네트워크를 쓰지 않는다. `build`는 위 명령으로 ZIP을 만들고
  명세를 출력하며, 이미 있는 출력 파일은 덮어쓰지 않는다. `check`는 보고만 한다. L1은 다시 만든 ZIP과 SHA-256을
  비교한다. L2는 ZIP을 풀지 않고 읽어 파일 목록과 각 파일의 Git blob id를 태그 트리와 비교한다. 위험한 항목
  이름과, 읽는 방식에 따라 내용이 달라지는 ZIP 구조(`parser_ambiguity`)도 표시한다. `export-ignore`·`export-subst`는
  `git archive`와 같게 해석하고, `git archive`가 바꿔 넣을 수 있는 파일은 `conversion_unverified`로 적는다.
  일치·불일치·거부는 모두 종료 코드 0이고, 사용법 오류·없는 태그·git 실패는 2다. L2에는 git 2.40 이상이 필요하다.
  `git check-attr --source`가 실패하면 L1 결과를 유지하고 L2는 `refused`로 보고한다.
- **간헐 실패 테스트의 분류와 반복 측정(개발 도구):** `tests/test_vault_runs.py`의 동시 실행 시험은 실패한
  자식마다 예외 클래스, errno, winerror, 가장 안쪽 코드 위치, 경로 범주(lock·temp·receipt·manifest·other)를
  남긴다. 원래 경로·노트 내용·예외 문장은 싣지 않는다. 분류 코드는 시험 지원 모듈 `tests/runtime_failures.py`에
  있고 엔진 동작은 바뀌지 않는다. 재시도는 넣지 않았다. 새 도구 `scripts/flaky_repeat.py`는 unittest id 하나를
  N번 실행한다. 기본은 같은 프로세스이고, `--fresh-process`는 실행마다 새 인터프리터를 쓴다. 결과는
  `x/N failures; failure rate <= p`(단측 95% Clopper–Pearson)로 보고하고, 실패가 없으면 "N번 중 관측되지
  않음"이라고만 쓴다. 첫 실행 뒤의 불러오기 실패는 오류 사건으로 센다. 실패 서명의 절대 경로는 `<path>`로
  바꾸지만 상대 경로와 나머지 문장은 남으므로 공유하기 전에 확인한다. 수정 효과는 수백 번 겨냥한 반복으로 재고,
  전체 시험 한 번 통과는 회귀 확인일 뿐이라는 규칙을 [evaluation-stability.md](../evaluation-stability.md#간헐-실패-테스트-분류와-반복-측정)에
  적었다.
- **시험의 정션 생성 정리:** 시험이 Windows 정션을 만들 때 `cmd /c mklink /J` 대신 공용 도우미
  `tests/_winfs.py`의 `make_junction`을 쓴다. 도우미는 CPython의 `_winapi.CreateJunction`을 직접 부르므로 콘솔
  출력이 없다. 그 함수가 없을 때만 `mklink`로 돌아가며, 이때도 출력은 바이트로 받고 해석하지 않는다. 정션을
  만드는 시험 모듈 13개가 이 도우미를 쓴다. 건너뛰던 시험은 같은 사유로 건너뛰고, 생성 성공을 단언하던 시험은
  실패하면 그대로 실패한다. `tests/test_winfs.py`가 다른 시험 파일의 `mklink`·`CreateJunction` 직접 호출을 막는다.

## 하위호환·업그레이드

**기본 동작.** 의도한 기본 동작 변경은 Jarvis의 via_bot 분류 하나다. 나머지 변경은 명시적으로 켜는 경로 안에
있다. 질의 확장의 `inventory_verification`은 `listing_entries`·`listing_diagnostics`·
`listing_diagnostics_omitted`를 더하고 `method`·`assurance` 문구가 바뀐다. 실패하면 `changed_directory`가
붙는다. 지침 진단 보고서에는 `listing_diagnostics` 목록이 늘 있고, `directory_changed_during_diagnosis` 행에
`change` 키가 붙는다. 새로 닫히는 경우는 이름 목록만 바뀐 디렉터리, lstat은 되지만 목록을 읽지 못하는 디렉터리,
검사 때 항목 합계가 상한을 넘는 경우, 걷기 목록이 없는 표지다. `--redact`만 쓴 골드셋 출력은
`redaction_mode`·`redaction_algorithm` 두 필드가 더해진 것 말고 v0.25.0과 같다. 시험이 v0.25.0 코드에서 잡은
정준 해시로 이를 고정한다.

CI의 평가 명령 7개를 v0.25.0(`833d394`)과 통합 코드(`6bab83b`)에서 `PYTHONUTF8=1`로 돌려 표준 출력을
비교했다(2026-10-20, Windows, Python 3.12.10). 7개 모두 종료 코드 0이었고 stderr가 같았다. recall 기본,
recall_advanced 비교, 기억 작업 흐름, 한국어 기억, 도구 안전 대조군 5개는 경과 시간 키를 빼면 같았다. recall_hard
`--expand-query` 두 개(top-3·top-5)는 `query_expansion.inventory_verification`만 달랐다. 달라진 것은
`method`·`assurance` 문구와 새 목록 필드 세 개다. 이 블록(출력마다 54개)과 경과 시간 키를 빼면 두 출력도
같았다. 이 비교는 버전을 올리기 전의 통합 코드에서 실행했다. v0.25.0의 38건처럼 healthcheck·doctor·SessionStart
출력을 바이트로 비교하지는 않았다.

`hooks/hooks.json`, 훅 스크립트, git 훅 템플릿, 여섯 규칙 템플릿, 볼트 설정 템플릿과 CI 워크플로는 v0.25.0과
바이트가 같다. 프런트매터 스키마 템플릿(`assets/templates/frontmatter-schema.md`)과 명령 문서 두 개
(`commands/vault-ingest.md`·`commands/vault-jarvis-setup.md`)는 via_bot을 적도록 바뀌었다. healthcheck 스탬프와
`ENGINE_VERSION`만 0.26.0으로 올리고, 내용이 같은 규칙 스탬프는 그대로 둔다.

**경고 승격 인증서.** 이번 버전은 Jarvis의 via_bot 수집 출처를 위해 `vault_provenance.py`를 바꿨다. 이 파일은
`checker_sha256`가 묶는 일곱 파일(`vault_lint_extensions.py`·`vault_warning_policy.py`·`vault_provenance.py`·
`vault_egress.py`·`vault_ssot.py`·`jev_client.py`·`vault_paths.py`)에 들어가며, 일곱 파일 가운데 바뀐 것은 이 파일
하나다. 2026-10-20에 `vault_warning_policy.py`와 같은 방식으로 저장소 바이트(LF)에서 다시 계산하자
`checker_sha256`는 v0.25.0(`833d394`)의 `2ef4b9d4…`에서 릴리스 준비 트리의 `84cf5235…`로 바뀌었다. benign
corpus는 같다(LF `38efaabd…`). 같은 날 두 버전을 `git -c core.autocrlf=false archive`로 꺼내 합성 볼트에서
`missing-anchor`를 `fatal`로 올렸다. v0.25.0 인증서를 둔 새 healthcheck는
`warning promotion rejected: promotion certificate checker_sha256 differs from current harmless replay`와 함께
종료 코드 1로 멈췄고, SessionStart 훅은 hot 노트를 주입하지 않았다. 새 설치본에서 만든 인증서는 종료 코드 0이었고
훅도 주입했다. 단계를 `warning`으로 되돌린 같은 설정은 두 버전 모두 종료 코드 0이었다. 거꾸로 새 인증서를
v0.25.0 엔진에 두어도 같은 오류로 멈췄다. 그래서 갱신 전에 승격 단계를 `warning`으로 되돌리고, 새 설치본에서
`vault_warning_policy.py --certificate`로 인증서를 다시 만든 뒤 승격한다. 이전 버전으로 되돌릴 때도 같은 순서를
따른다. 실제 사용자 볼트의 인증서는 자동으로 다시 쓰지 않는다. corpus 바이트가 체크아웃 줄바꿈에 따라 달라지는
성질은 [v0.25.0 안내](v0.25.0.md#하위호환업그레이드) 그대로다.

**혼합 버전과 되돌리기.** v0.26.0 이전 엔진은 `content_origin: via_bot`을 모른다. 그런 엔진은 새 브리지가 쓴
via_bot 수집을 모두 `provenance-invalid`(`invalid_origin`)로 보고한다. 이 코드를 fatal로 승격했다면 검사가
멈춘다. Claude Code와 Codex의 플러그인 캐시는 따로 갱신되므로, 볼트를 읽는 설치본을 모두 함께 갱신한 뒤 새
브리지를 쓴다. 이전 버전으로 되돌리기 전에는 남은 via_bot 수집을 정제·격리하거나 `provenance-invalid`를
warning으로 둔다. 모르는 출처를 실패로 다루는 것은 의도한 동작이라 코드는 바꾸지 않았다. 이미 저장한 수집은
다시 분류하지 않는다. 이전 브리지가 받은 인라인 봇 메모는 own(링크가 있으면 url)으로 남는다. 인라인 봇을 썼다면
`10-inbox/jarvis/`의 이전 수집과 그것으로 만든 노트를 직접 검토한다.

Codex 설치 ref는 `--ref v0.26.0`이다. 기존 소스 교체·캐시 보존 절차는 [Codex 설치 안내](../codex.md#설치)에 있다.
플러그인 게시, 활성 캐시 갱신과 볼트 upgrade는 별도 작업이다. 이번 게시 준비는 활성 호스트 캐시와 운영 볼트를
바꾸지 않았다. Jarvis의 기존 API 인증 조건도 유지한다.

GitHub 불변 릴리스 절차를 계속 사용한다. 이번 ZIP은 새 절차로 `TZ=UTC0`과 `--prefix agentic-vault-0.26.0/`을
써서 만들고, `verification.json`에 `scripts/release_rebuild.py build`가 출력한 `rebuild_spec` 블록을 넣는다.
받은 사람은 `python scripts/release_rebuild.py check --spec verification.json --zip agentic-vault-0.26.0.zip`으로
다시 만들어 대조할 수 있다. 바이트 일치(L1)는 같은 git 빌드에서만 측정했으므로 다른 환경에서는 L2를 기준으로
쓴다. ZIP·`SHA256SUMS`·`verification.json`을 초안에 올린 뒤 게시하며 텍스트 자산은 LF 바이트로 쓴다. 게시 뒤 릴리스
증명과 공개 재다운로드 확인은 별도 기록에 남긴다. 잠긴 자산 안에 그 자산의 나중 검증 결과를 덧붙이지 않는다.

## 알려진 경계

**불안정 시험.** v0.25.0에서 알린 세 시험 중 디렉터리 시각 시험 두 개는 위 반복에서 0/300이었다. 세 번째인
`test_vault_retrieval`의 `test_later_source_verification_cannot_leave_earlier_source_stale`은 이번에 다루지 않았고
반복 측정도 하지 않았다. `test_vault_runs`의 동시 prepare 시험은 유휴 반복 300회에서 v0.25.0이 5회, 이번 코드가
1회 실패했다. v0.25.0 실패의 예외 연쇄는 `StateError` `unsafe_runtime_path` 4건과 `unsafe_lock` 1건이었다. 뒤의
1건은 200자 서명 상한에서 다음 예외 이름이 `Per`까지만 남아 PermissionError로 보인다. 이번 실패 1건의 분류는
`record: 1 of 2 children failed; lock_access_denied=0`이었다. 이 표본으로 두 버전의 차이를 판단하지 않는다. 원인은
아직 측정하지 못했다. 측정 호스트(Windows 11 build 26300, NTFS)의 탐침에서는 삭제 대기 가설이 재현되지 않았다.
원격 CI 작업이 이 시험으로 실패하면 시험 이름을 확인한 뒤 그 작업만 다시 실행한다.

**남은 한계.**

- via_bot: Jarvis를 인증된 채널로 옮기는 본 과제는 남아 있다. 이전 수집은 다시 분류하지 않는다. 수집이 아닌
  노트의 프런트매터 출처 검사는 v0.25.0처럼 나열된 비신뢰 출처만 위험으로 본다(via-bot-4).
- 목록 대조: 같은 이름으로 지웠다 다시 만든 항목은 이름 목록으로 잡지 못한다. 노트는 문서 stat 표지가, 측정한
  지침 파일은 끝의 재해시가 잡는다. 목록 확인은 한 시점의 확인이며 잠금이 아니다.
- 키 가명화: 키는 길이만 확인하고 무작위성은 확인하지 못한다. 하드 링크나 다른 마운트 경로로 볼트 안의 키를
  가리키면 잡지 못한다. 표준 출력이 파이프이면 작업 디렉터리 확인만 된다. 키 해시도 결정적이라 한 보고서 안의
  반복과 빈도가 드러난다. 행은 골드셋 순서를 따르므로 골드셋을 가진 사람은 행과 경로 토큰을 위치로 맞출 수
  있다. 공유하기 전에 행을 정렬하거나 섞는다. 경로 가명화는 필드 이름 기준이라 새 필드는 추가해야 가려진다.
- 재현 ZIP: 바이트 재현(L1)은 git 2.55.0.windows.3 한 빌드에서만 측정했다. L2는 항목 시각·권한·압축 방식·ZIP
  주석을 비교하지 않고, 대소문자만 다른 이름 충돌을 표시하지 않는다. `git ls-tree`·`rev-parse` 실패는 여전히
  종료 코드 2로 끝나 L1 결과를 잃는다. 재빌드 확인은 빌드 출처를 증명하지 않는다.
- 반복 측정 도구: 같은 프로세스 반복은 모듈·클래스 상태를 실행 사이에 공유한다. 따옴표 안 경로에 같은 따옴표가
  들어 있으면 일부만 가려질 수 있다.
- 로컬에서는 Windows의 Python 3.12.10만 실행했다. Python 3.10·3.14와 Linux·macOS 결과는 원격 CI가 맡으며 그 결과는
  게시 전 영수증에 기록한다.
- 새로 인용한 외부 자료(Gruber 등 ICST 2021, Reproducible Builds의 Archive metadata, arXiv 2608.18180, 키 가명화
  절의 ENISA·EDPB 자료)는 작업 중 네트워크가 없어 온라인으로 다시 확인하지 못했다.

합성 fixture와 한 기계의 측정이다. 실제 업무 볼트의 오탐률, 동시 실행 실패의 원인, 다른 git 빌드의 바이트 재현을
입증하지 않는다. GitHub 릴리스 증명은 게시 자산과의 동일성을 확인하며 빌드 출처·게시 승인자 신원·내용의 안전성은
증명하지 않는다.
