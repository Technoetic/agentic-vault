# v0.23.0 — 도구 호출 진단·근거 경고·한글 bigram·불변 릴리스

평가 결과의 원인을 더 나눠 보고, 근거 없는 값을 경고하고, 조사가 붙은 한국어 질의를 선택적으로
찾는 도구를 더한다. 새 기능 다섯 가지는 명시적으로 켜야 동작하거나 결과를 경고로만 남기고, 여섯째
항목은 게시 절차다. 기본 출력, 네트워크/모델 호출, 런타임 의존성과 기존 테스트 게이트는 바꾸지 않는다.
이 릴리스는 GitHub 불변 릴리스로 게시하는 첫 릴리스다. [평가 사용법](../memory-evaluation.md), [검색 패턴](../memory-patterns.md),
[보강 도구](../hardening.md), [릴리스 무결성](../release-integrity.md), [릴리스 검증](../verification/v0.23.0.md)을
함께 확인한다.

## 변경

- **도구 호출 실패 진단(선택):** `evaluate_tool_safety.py --receipt-out PATH`는 에피소드마다
  `failure_subtype`(우선순위를 정한 8개 유형), 파싱된 호출 수, 크기를 제한한 assistant 본문, 로컬 서버의
  파서 경로(`GET /props`)를 더한 전체 영수증을 새 파일에 쓴다. 옵션이 없으면 출력·종료 코드·모델
  요청이 v0.22.1과 같다(골든 비교). 2026-10-16 영수증을 다시 분류하면 한국어 2/2가 `arg_language_mismatch`,
  영어 2/2가 `none`이었다. 2026-10-17 재실행(로컬 Qwen3.5-9B Q8_0, llama.cpp `b10729-458681e1d`)도
  한국어 0/2·영어 2/2 완료, 공격 목표 0/4, 모델/통신 오류 0/4였다. assistant 본문 12개에 호출 표지가 없어
  파서 실패는 관측되지 않았다. 모델은 승인된 수신자에게 요청한 코드 대신 문서의 한국어 상태 문장을
  보냈다(측정, 에피소드당 1회).
- **불변 릴리스 게시 절차(문서):** [릴리스 무결성](../release-integrity.md)에 공개 자산, 초안 → 자산 3개
  업로드 → 게시 순서, 선택형 `gh release verify`·`gh release verify-asset` 확인과 각 확인이 증명하는 범위를
  적는다. 2026-10-17 조회에서 기존 GitHub 릴리스 23개는 모두 `"immutable": false`였다. 올린 `SHA256SUMS`
  11개 중 6개가 CRLF였고 GNU `sha256sum -c`는 v0.22.1 파일을 대조하지 못했다(측정). 불변 릴리스 동작
  설명은 GitHub 공식 문서의 보고 내용이다.
- **날조 후보·출처 뒷받침 경고(선택, 경고 전용):** `check_compile(..., report_unsupported=True)`와
  `vault_compile_quality.py --report-unsupported`는 정제본에만 있는 숫자·날짜·이름 literal과
  `fabrication_candidate_rate`를 관측으로 더한다. `vault_ssot.py check-support`는 시간 대장 행의 값이
  `source` 칸이 인용한 노트 본문에 있는지 보고 `ssot-source-unsupported`·`ssot-source-unresolved` 경고만
  낸다(경고만 있으면 exit 0). 기본 출력은 v0.22.1에서 캡처한 골든과 같고, 두 경고 코드는 승격할 수
  없다. 실제 볼트의 오탐률·놓침률은 측정하지 않았으며 근거는 합성 단위 테스트뿐이다.
- **CI 공급망 점검(경고 전용):** `tests.yml`에 `supply-chain-audit` 작업을 더한다. zizmor로 워크플로를,
  pip-audit으로 `requirements-dev.txt`를 점검하고 결과는 `::warning`으로만 낸다. 두 단계와 작업 모두
  `continue-on-error`이고 권한은 `contents: read`뿐이다. 게시 후 14일 유예를 지켜 zizmor-action v0.6.4
  (2026-09-09 게시, 커밋 고정)와 zizmor 1.30.1, pip-audit action v1.1.0(2024-08-08 게시)을 쓴다. 로컬
  오프라인 zizmor 1.31.1은 기본 persona 0건, pip-audit 2.10.1은 알려진 취약점 0건이었다(2026-10-17, 측정).
- **render-matched 대조군(선택):** `evaluate_recall.py --compare --render-matched`와
  `evaluate_korean_memory.py --render-matched`는 고급 검색과 같은 옵션을 쓰되 시간 상태 때문에 출처를
  빼지 않는 세 번째 팔(`temporal_filter="annotate_only"`)을 더해 겉보기 이득을 표시 효과와 기전 잔차로
  나눈다. recall_hard top3의 nDCG@5(답 있는 56쌍)는 legacy 0.570, 대조군 0.980, advanced 0.980으로 표시
  효과 +0.411(p=0.0001), 기전 잔차 0이었다. 기전 잔차가 0이 아닌 판정 지표는 0이 아닌 쌍이 2~4개뿐이라
  검정력 한계(최소 p 0.125~0.5)에 걸렸고, 세 구성 모두 미리 정한 규칙에 따라 `defer_richer_ledger_typing`이었다.
  한국어 근거 50건은 50/50 동일했다(측정). 논문([arXiv 2607.16019](https://arxiv.org/abs/2607.16019))의
  질문 2,907개, 겉보기 이득 +0.182, 기전 잔차 +0.021~+0.025는 초록의 출처 보고값이며 재현하지 않았다.
- **한글 음절 bigram BM25(선택):** `--lexical-ngrams hangul2`(Python `lexical_ngrams="hangul2"`)는 호출마다
  메모리에서 만든 한글 음절 bigram BM25 순위를 `bm25`·`hybrid` 백엔드의 RRF에 더한다. 인덱스·캐시는
  저장하지 않으며 `lexical` 백엔드는 이 채널을 무시한다. recall_hard 64질의(답 있는 56, 답 없는 8)에서
  CI와 같은 옵션은 64/64질의에서 채널이 무시되어 지표가 같았다. 질의 확장을 켠 `bm25` top5는 nDCG@5
  0.9948→0.9845(p=0.5053)로 개선이 없었다. 확장 없이 `bm25` top5는 recall@5 0.5714→0.7500(p=0.0017),
  nDCG@5 0.4506→0.6385(p=0.0003)였고 한국어 particles는 0/6→6/6, update는 0/4→4/4였다(측정). 기본값과
  CI 기준은 바꾸지 않는다.
- `vault_retrieval.retrieve()`의 키워드 전용 옵션 `lexical_ngrams`와 `temporal_filter`는 함께 쓸 수 있다.
  legacy 빠른 경로는 두 값이 모두 기본(`None`, `"exclude"`)일 때만 쓴다. 어느 쪽이든 잘못된 값은 노트를
  읽기 전에 `invalid_options`로 거부하고, diagnostics는 지정한 옵션만 표시한다. `--lexical-ngrams`를 주면
  render-matched 팔을 포함한 모든 고급 경로 팔이 같은 값을 쓴다.

## 하위호환·업그레이드

기본 세션 주입·검색·평가 출력, 네트워크/모델 호출, 런타임 의존성(표준 라이브러리만)은 바뀌지 않는다.
새 동작은 명시적 옵션으로만 켜지며, 기본 출력은 v0.22.1에서 캡처한 골든·digest와 비교한다.
`hooks/hooks.json`과 훅 스크립트, 명령 문서, 규칙 템플릿 6종은 v0.22.1과 같다(`git diff`로 확인).
healthcheck의 stamp/ENGINE_VERSION은 0.23.0으로 맞추고 내용이 같은 여섯 규칙의 스탬프는 유지한다.
기존 `tests.yml`의 테스트 작업·명령·게이트는 그대로이며 경고 전용 작업만 더했다.

**경고 승격 인증서.** `vault_ssot.py`의 바이트가 바뀌어 `warning_policy` 인증서가 묶는
`checker_sha256`도 바뀐다. v0.22.1에서 만든 인증서로 경고를 `fatal`로 올린 설정은 v0.23.0에서 거부된다.
이때 승격은 경고로 조용히 돌아가지 않고 설정 검증 오류로 멈춘다(fail-closed). 2026-10-17 측정에서 그런
설정의 healthcheck는 v0.22.1에서 exit 0, v0.23.0에서 `warning promotion rejected: promotion certificate
checker_sha256 differs from current harmless replay`와 함께 exit 1이었다. 같은 인증서를 두고 단계를
`warning`으로 되돌리면 v0.23.0에서도 exit 0이었다. 코드상 세션 시작 주입과 recall처럼 같은 설정을 읽는
도구도 이 설정을 오류로 처리한다. 인증서를 쓰는 볼트는 갱신 전에 `fatal` 단계를 `warning`으로 되돌려
경고로 운용하고, 설치한 v0.23.0에서 `vault_warning_policy.py --certificate`로 인증서를 다시 만든 뒤
승격한다.

이 릴리스부터 GitHub 불변 릴리스로 게시한다. 게시 후에는 태그와 자산(ZIP·`SHA256SUMS`·
`verification.json`)을 바꿀 수 없고, 불변 설정은 v0.22.1까지의 릴리스에 소급되지 않는다.
`SHA256SUMS`와 `verification.json`은 LF 바이트로 쓴다. 플러그인 배포, 설치 캐시 갱신, 실제 볼트
upgrade는 별개다. 기존 Jarvis API 인증 조건은 유지한다. 설치는 README 또는 Codex 안내의
`--ref v0.23.0`을 사용한다.

## 검증

Windows 11의 시스템 Python 3.12.10에서 로컬 전체 1,497개 중 1,464개 통과, 환경에 따른 33개 건너뜀,
실패·오류 0개였다. Hypothesis를 설치한 격리 개발 venv(Python 3.12.10)에서는 1,501개 중 1,470개 통과,
31개 건너뜀, 실패·오류 0개였고 상태 기반 수명주기 검사도 exit 0이었다. `tests.yml` unittest 작업의
평가 명령 7개, compileall, 전체 트리 `git diff --check`도 모두 exit 0이었다. 같은 트리의 첫 `-v` 실행에서는
v0.21.0부터 있던 디렉터리 시각 기반 검사 하나가 한 번 실패했고, 그 검사만 다시 실행한 8회는 모두 통과했다.
2026-10-17 render-matched·한글 bigram 기록의 측정 명령은 통합한 코드에서 다시 실행해도 기록과 같았다.
기능별 측정은 2026-10-17 기록([도구 호출 진단](../verification/tool-call-diagnosis-20261017.md),
[한글 bigram](../verification/hangul2-bigram-20261017.md), [render-matched](../verification/render-matched-20261017.md))과
[릴리스 무결성](../release-integrity.md)에 있다. 최종 source의 원격 CI, ZIP 멤버/Git blob 일치, 불변 릴리스
확인(`gh release verify`·`verify-asset`)과 공개 재다운로드 SHA256 검증은 게시 후 공개 릴리스의
`verification.json`과 `SHA256SUMS`에 별도로 기록한다.

## 알려진 경계

합성 fixture와 단위 테스트 근거다. 실제 볼트에서의 효과·오탐률은 측정하지 않았다. 실제 모델의 한국어
도구 과제는 두 날짜 모두 0/2로 여전히 실패하며, 각 1회 관측은 일반 성능이나 보안 인증이 아니다.
render-matched 비교는 판정 지표별로 0이 아닌 쌍이 최소 6개 있어야 기전 잔차를 가려낼 수 있고, 읽는
모델이 없어 표시 자체의 효과는 재지 않았다. bigram 채널은 형태소 분석이 아니어서 관련 없는 겹침이 후보를
늘릴 수 있다. 출처 뒷받침 검사는 literal 비교이며 다른 대장의 사실 표를 통한 순환 뒷받침, `-5` 같은
부호 값의 범위 표기 일치, 구역 안 노트의 `not_found` 보고, 인용 노트의 stat 기반 재확인 같은 한계가 있다
([한계](../hardening.md)). 공급망 점검은 경고 전용이고 pip-audit action은 실행할 때 pip-audit을 해시 없이
설치한다. CI에서 zizmor 1.30.1로 실행한 결과는 아직 관측하지 않았다. 릴리스 증명은 GitHub가 게시한 자산과의
동일성을 보일 뿐 빌드 출처, 승인자 신원, 내용의 안전성은 증명하지 않는다.
