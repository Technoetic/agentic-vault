# v0.50.0 — 낡은 PR CI 실행 취소와 연결 작업 트리 HEAD 확인

저장소 CI가 같은 풀 리퀘스트의 이전 실행만 취소하도록 하고, healthcheck에 어느 분기·태그에도 담기지 않은
HEAD를 가진 연결 작업 트리를 알리는 선택형 확인과 그 작업을 master에 반영하는 안내를 더한다.
기준은 공개 v0.49.0 커밋 `1fc8269039c06ecadb2852e2addbadfb0a40e15b`다.

## 변경

1. 낡은 풀 리퀘스트 CI 실행 취소(저장소 CI). `.github/workflows/tests.yml`의 `permissions:`와 `jobs:` 사이에
   워크플로 수준 `concurrency` 블록을 둔다. 묶음 이름은 `pull_request` 사건이면 `tests-pr-` 뒤에 풀 리퀘스트 번호,
   그 밖의 사건이면 `tests-run-` 뒤에 실행 번호(`run_id`)를 붙인 것이고, `cancel-in-progress`는 `pull_request` 사건에서만 참이다. 같은 풀
   리퀘스트에 새 커밋이 오면 그 풀 리퀘스트의 이전 실행만 취소된다. master·태그·후보 분기 push와 수동
   실행(`workflow_dispatch`)은 실행마다 묶음이 따로라 취소되거나 다른 실행 뒤에 줄 서지 않는다. 릴리스 관문으로
   쓰는 실행이 이 push 실행들이다. `on:`의 사건(`push`·`pull_request`·`workflow_dispatch`)과 작업 정의는 그대로이고,
   경로 거름·분기 거름·작업 수준 `concurrency`는 넣지 않는다. 시험(`tests/test_supply_chain.py`)이 블록이 정확히
   한 번 있고 두 줄이 위와 같은지, 작업 수준 `concurrency`가 없는지, `on:`에 `paths`·`paths-ignore`·`branches`·`tags`
   거름이 없는지 고정한다. 결정과 근거가 된 중복 실행 측정은 [릴리스 무결성](../release-integrity.md#ci-공급망-점검경고-전용)의
   2026-11-15 항목에 적었다.
2. 연결 작업 트리 HEAD 확인(선택형, 읽기 전용). `vault_healthcheck.py --worktree-heads`는 전체 검사에서만 동작한다.
   볼트 저장소에서 `git worktree list --porcelain`으로 등록된 작업 트리를 읽고, bare 항목과 분기에 걸린 작업 트리는
   건너뛴다. 분기에 걸리지 않은(detached) HEAD마다 그 커밋을 `--contains`로 넘긴
   `git for-each-ref --count=1 ... refs/heads refs/tags`로 그 커밋을 담은 분기·태그가 있는지 보고, 없으면 새 섹션
   `## 14c. 분기·태그 밖 HEAD를 가진 연결 작업 트리 — 관리성 (N)`(섹션 14b 바로 뒤)에 한 줄씩 적는다. 줄에는 경로(볼트
   안이면 볼트 기준 POSIX 상대 경로, 밖이면 슬래시로 쓴 절대 경로, 본 작업 트리는 `.`)와 HEAD 앞 12자를 쓰고, 작업
   트리를 지우기 전에 `git branch`로 그 커밋에 분기 이름을 붙여 고정하라고 안내한다. prunable 표시가 붙은 항목도 알린다. git이
   실패하면(저장소 없음·명령 오류·시간 초과) `- (확인 실패)`로 시작하는 짧은 이유 한 줄을 쓰고 N에 세지 않으며 예외를 내지
   않는다. 플래그를 주면 N이 관리성 합계에 더해지고 `--json-summary`에 `"unreachable_worktree_heads": N`이 생긴다.
   종료 코드는 바뀌지 않는다. `--staged`와 함께 주면 인자 오류(종료 코드 2)다. 새 코드는 `vault_healthcheck.py`의
   `# --- BEGIN SHARED WORKTREE RULE` 블록 밖에 있고, 그 블록과 사본, 금지 구역 가드는 바뀌지 않는다.
   시험은 새 모듈 `tests/test_healthcheck_worktree_heads.py`다.
3. 연결 작업 트리 작업 반영 안내. [동시 커밋 안내](../concurrent-commits.md)에 `Landing work from a linked worktree`
   절을 더한다. 작업 트리 작업은 detached HEAD가 아니라 자기 분기에 커밋한다. master 반영은 공유 본 작업 트리에서
   `vault_commit.py`로 한다. 바뀐 노트는 본 트리로 복사해 `--path`와 그 sha256으로 커밋하고, 공유 노트의 줄은
   `--own-lines`로 반영하되 패치 파일은 연결 작업 트리 밖에 둔다(연결 작업 트리 안의 경로는 패치 파일까지 거부된다).
   공유 본 트리에서는 `git merge`·`git cherry-pick`을 쓰지 않는다. 둘 다 공유 인덱스에 쓰고, 다른 세션이 스테이징한
   변경이 있으면 `git merge`가 중단되며, `vault_commit.py`는 병합이 진행 중이면 거부한다. 작업 트리를 지우기 전에
   `vault_healthcheck.py --worktree-heads`로, 또는 그 커밋을 `git branch --contains`에 주어 확인한다. 어느 분기·태그에도 없는
   detached 커밋은 작업 트리를 지운 뒤 git이 정리하면 사라진다. 백업 스냅숏은 등록된 작업 트리 사본을 건너뛰므로
   ([안전 보강 안내](../hardening.md#linked-worktree-copies-and-deny-zones)) 거기서 커밋하지 않은 작업도 스냅숏에 없다.
4. 판 표면. 세 매니페스트와 생성 `antigravity/plugin.json`, healthcheck 스탬프와 `ENGINE_VERSION`, README·
   `docs/codex.md`·`docs/README.md`·`docs/release-integrity.md`·`SECURITY.md`의 현재 판 줄과 Codex 설명을 0.50.0으로
   옮긴다. Antigravity CLI 생성 패키지는 원본에서 다시 만들고 사본 일치를 검사한다.

## 기본 결과 변경

- 판 메타데이터: 매니페스트 버전·설치 태그·healthcheck 식별이 0.50.0으로 이동한다. healthcheck의 버전 출력과
  `--help`가 바뀐다(`--help`에 `--worktree-heads` 줄이 하나 늘어난다).
- 저장소 CI: 같은 풀 리퀘스트에 새 커밋이 오면 그 풀 리퀘스트의 이전 실행이 취소된다. 이 저장소 자체의 CI에 관한
  변경이며 설치한 플러그인의 동작이 아니다. push 실행과 수동 실행은 취소되지 않는다.
- 그 밖에는 새 플래그 없이 바뀌는 결과가 없다. 플래그 없는 healthcheck 기본 보고서·`--staged`·`--json-summary`는
  판 표면 말고는 v0.49.0과 같다. 규칙·어댑터·권한 템플릿·git 훅·기본 훅 정의·기본 네트워크/모델 호출 설정은
  바꾸지 않는다.

## 하위호환·업그레이드

현재 설치 ref는 `v0.50.0`이다. 기존 설정 키는 추가하거나 마이그레이션하지 않는다. 활성 설치와 회사 볼트는 이
릴리스로 갱신하지 않는다. 볼트에 복사된 healthcheck는 `/vault-upgrade`(Codex는 `upgrade`)를 실행한 뒤에
`--worktree-heads`를 갖는다.

인증서가 묶는 일곱 파일은 v0.49.0과 같아 v0.46.0 이후 인증서는 실제 바이트가 같은 경우 계속 유효하다.
v0.45.1 이하와 오갈 때는 [v0.46.0 업그레이드 안내](v0.46.0.md#하위호환업그레이드)를 따른다.
healthcheck만 `engine=0.50.0`으로 이동하며 기존 규칙·어댑터 스탬프는 유지한다.
`checker_sha256`는 `09642e7aa77d0b812f5afa646b491fe2d79d44104e399bea4a3001a6f2f1279d` 그대로다.

## 검증

[검증 계약](../verification/v0.50.0.md)에 요구 관문을 적었다. 실제 최종 소스의 시험 수·종료 코드·건너뜀·CI·
독립 검토·ZIP 재빌드·설치 자원 바이트·인증서 결과는 릴리스의 `verification.json`에 기록한다.
게시 후 새 다운로드와 릴리스 증명 확인은 별도 기록으로 남긴다. 계약 문서 자체는 통과 결과가 아니다.

새 시험은 워크플로 파일의 `concurrency` 블록·사건·거름을 고정하는 `tests/test_supply_chain.py`의 시험, 임시 볼트
저장소에서 연결 작업 트리를 만들어 섹션 14c·분기 고정 뒤 0건·분기에 걸린 작업 트리 제외·플래그 없는 두 실행의
바이트 일치·`--staged`와의 인자 오류·`--json-summary` 키를 확인하는 `tests/test_healthcheck_worktree_heads.py`,
그리고 판 표면을 고정하는 `tests/test_release_metadata.py`의 v0.50.0 시험이다. 시험은 워크플로 파일의 내용만
확인한다. GitHub가 실제로 이전 풀 리퀘스트 실행을 취소하는지는 시험으로 확인하지 않았다.

## 연구 출처와 기존 기능의 차이

| 출처 | 준 것 | 이번 적용 |
|---|---|---|
| [개발동생 영상](https://www.youtube.com/watch?v=iysCcCRKZA4)(2026-11-14) | Anthropic·OpenAI·GitHub의 Git 규모 대응 소개와, 발표자가 작은 팀에 권한 조언 셋(에이전트마다 작업 폴더를 따로 주는 `git worktree`, 같은 풀 리퀘스트에 새 커밋이 오면 돌던 시험 취소, 줄 단위 대신 의도 중심 리뷰) | 1번 항목은 둘째 조언을 이 저장소 CI에 옮긴 것이다. 첫째 조언(세션마다 작업 트리)은 이미 [동시 커밋 안내](../concurrent-commits.md)가 권하고 있어, 2·3번 항목은 그 방식을 안전하게 쓰도록 이번에 더한 확인과 반영 안내다(발표자의 제안이 아니다). 셋째 조언은 기존 작업 명세([task contracts](../task-contracts.md))로 다루며 바꾸지 않았다 |
| [Anthropic, Redesigning source control](https://www.anthropic.com/research/redesigning-source-control) | 클라이언트가 항상 온라인이라는 전제에서 서버가 커밋과 계산을 맡는 자체 소스 관리(Scion). 저자들은 "Scion is by no means a suitable replacement for git for general use."라고 적었다 | 채택하지 않았다. 로컬 git·훅·미러를 유지하는 근거로 읽었다. 가장 가까운 기존 기능은 `vault_commit.py --own-lines`(공유 인덱스 없이 HEAD 위에 자기 변경만 얹어 커밋을 만들고, HEAD가 그사이 바뀌지 않았을 때만 분기를 옮긴다)다 |
| [OpenAI, Scaling Git at OpenAI](https://openai.com/index/scaling-git-at-openai/) | Git 사용 방식은 바꾸지 않고 저장소 뒤쪽 서버를 새로 만든 사례(Pando) | 맥락으로만 읽었고 채택하지 않았다 |
| [GitHub, Inside GitHub's new Git storage architecture](https://github.blog/engineering/infrastructure/inside-githubs-new-git-storage-architecture/) | 참조마다 순서를 매겨 다른 분기의 push끼리는 기다리지 않게 한 저장 계층("When two pushes do update the same reference, only one will append to the log.") | 맥락으로만 읽었고 채택하지 않았다 |

두 항목은 출처들이 소개한 서버 쪽 설계(Scion·Pando)가 아니라 발표자가 작은 팀에 권한 조언에서 나왔다. 서버 쪽
설계는 한 컴퓨터에서 여러 세션이 함께 쓰는 볼트라는 이 플러그인의 규모에 맞지 않아 채택하지 않았다. 기존의 해시를 선언한
경로 커밋·자기 줄 커밋(`vault_commit.py`), 연결 작업 트리 사본의 금지 구역 처리, 백업의 작업 트리 사본 제외를 새
기능처럼 다시 넣지 않았다. 이전 저장소 문서는 이 네 출처를 인용하지 않았다(`git grep`으로 네 주소를 찾아 v0.49.0
트리에 일치가 없음을 확인했다). 출처들이 보고한 효과 수치는 이 저장소의 효과로 주장하지 않는다.

## 알려진 경계

- CI 변경은 이 저장소의 워크플로에만 해당한다. 취소된 풀 리퀘스트 실행은 릴리스 관문이 아니며, 후보 분기·태그·
  master push 실행은 취소되지 않는다. GitHub의 실제 취소 동작은 공개 뒤 풀 리퀘스트에서 관찰해야 한다.
- `--worktree-heads`는 git에 등록된 작업 트리만 읽는다. 작업 트리 삭제나 `git worktree prune`을 막지 않고, 분기를
  만들지 않으며, 커밋하지 않은 변경과 등록되지 않은 사본은 보지 않는다.
- 안내 절은 순서를 설명할 뿐 일반 `git merge`·`git cherry-pick`·`git commit`을 막지 않는다.
- 실제 업무 볼트나 실제 풀 리퀘스트로 효과를 측정하지 않았다.
- 생성 Antigravity CLI 패키지의 사본 일치는 검사하지만 실제 agy 대화 세션은 실행하지 않는다.
