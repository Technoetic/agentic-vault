# v0.34.0 — 다섯 가지 선택형 진단·평가 기능

## 변경

기준 공개판은 v0.33.1 `4b213f3ed0a314595278adb7d70eb9a0c6fc61e5`이다. 명시적으로 켜는 기능 다섯 가지를 갈래마다 검토하고 고친 뒤 합친 공개 후보 소스는 `67af284583c19b050ed93a1fc77a8cc7babb9086`이며, 버전 문서를 바꾼 최종 소스는 게시 전 `verification.json`에 기록한다. 다섯 기능 모두 훅·CI 게이트·기본 실행에 연결하지 않는다.

- [`check-support --bind-subject`의 주어 왼쪽 경계](../support-row-diagnostics.md#subject-left-edge): 첫 글자가 ASCII가 아닌 글자인 주어는 바로 앞이 다른 글자이면 일치로 보지 않는다. 그래서 주어 앞에 한글 한 음절이 더 붙은 긴 이름(`이가나다전기` 안의 `가나다전기`)은 더 이상 주어 일치로 세지 않는다. 지정한 블록의 가나·한자, 대표 타이·라오·미얀마·크메르 범위의 글자, U+119E 뒤와 띄우지 않고 쓴 상법의 법인 형태 다섯 뒤는 경계로 본다. UAX #29 WB5를 1글자 뒤보기로 근사했으며 UAX #29 준수를 주장하지 않는다. 비슷한 이름이 다른 법인이라는 기록을 v2 `different_from` 행으로 적는 [형식 안내](../support-row-diagnostics.md#recording-confusable-names-format-guidance)도 더했다(파서는 바뀌지 않는다).
- [`evaluate_recall.py --abstention-calibration conformal`](../memory-evaluation.md#답-없음-보정-문턱): 평가기 안에서만 '신호가 문턱보다 작으면 거부' 규칙의 문턱을 커밋한 분할의 dev 쪽에서 분할 conformal p-value로 맞추고, heldout의 답 있는 문항과 그 쌍둥이에서 잰다. 선택 옵션 `--false-refusal-budget`(기본 0.05)과 `--abstention-signal`을 함께 쓸 수 있다. Learn then Test 조건부판, 동시 거짓 거부율 상한과 볼트 스냅샷 해시도 낸다. recall 엔진은 그대로 보류를 호스트에 맡긴다(`abstention: host_decision`).
- [`scripts/real_vault_audit.py plan`](../memory-evaluation.md#실제-볼트-표본-감사초기하-정확-상한): 라벨하기 전에, 놓침이 x개 이하로 나오면 `bound`의 상한이 목표 몫 안에 드는 최소 표본 크기(`sample_size`)와 NIST 소비자 위험 정의를 따른 엄격 크기(`strict_ltpd_sample_size`)를 정확한 정수 산술로 계산한다. `--oc`를 주면 합격 확률 표를 더한다. 입력 파일을 읽거나 출력 파일을 쓰지 않는다(`draw`·`bound`처럼 `scripts/eval_stats.py`는 불러온다).
- [`vault_improvements.py inspect`·`compare --receipt-order`](../improvement-experiments.md#영수증-기록-순서-선택): 응답 최상위에 `plan_created_at`·`recorded_before_plan`·`receipt_order`(`plan_first`·`results_first`·`mixed`)를 더한다. 기존 영수증의 로컬 시계 기록 순서일 뿐 관찰 시점이나 서명이 아니며 관문으로 쓰지 않는다.
- [`evaluate_tool_matrix.py --string-patterns`](../evaluation-stability.md#문자열-인자-패턴-짝-비교): 모든 trial을 현재 스키마 A와, `send_message`의 `recipient`·`body`에 형식 패턴을 더한 스키마 B로 같은 seed에서 한 번씩 실행하고, 호스트가 형식·길이·`re.fullmatch`로 낸 판정(`exact`·`valid_but_wrong`·`schema_invalid`)을 기록만 한다. 판정은 실행·채점·종료 코드를 바꾸지 않지만, 계획이 두 배(최대 160개 에피소드)가 되고 B 팔 에피소드도 A 팔처럼 보고서 전체 `summary`와 종료 코드 계산에 들어간다. B 요청은 패턴 두 개만큼(요청마다 78바이트) 길어서 `--max-request-bytes`를 빠듯하게 주면 B에서만 `request_bytes_exceeded`가 날 수 있으므로, 두 팔은 넉넉한 상한으로 비교한다. B 패턴은 `evaluate_tool_safety.lint_string_pattern` 허용 목록을 통과해야 한다.

세 매니페스트·healthcheck 식별은 `0.34.0`, Codex 고정 설치 ref는 `--ref v0.34.0`이다. 내용이 같은 규칙·어댑터 스탬프는 유지한다. 기본 훅·검색·15명령·Python 3.10+ 표준 라이브러리를 유지하며 기본 모델·네트워크 호출, 런타임 의존성, 실제 볼트 자동 갱신을 추가하지 않는다.

## 하위호환·업그레이드

새 옵션을 주지 않으면 기존 출력과 종료 코드는 v0.33.1과 같다. 다음은 예외다.

- `evaluate_recall.py`, `evaluate_tool_matrix.py`, `vault_improvements.py inspect`·`compare`의 `--help`에 새 옵션이 나오고, 앞의 두 CLI는 argparse 사용 오류의 usage 줄에도 나온다. `real_vault_audit.py`의 최상위 `--help`는 하위 명령 목록에 `plan`이 생기고 열 정렬이 바뀐다. `draw`·`bound`의 출력·표본 파일·종료 코드와 각 `--help`는 같다.
- argparse 약어: `evaluate_recall.py`에서 `--fixture`를 줄여 쓴 `--f`는 `--false-refusal-budget`과도 맞아 `ambiguous option` 오류(종료 코드 2)가 된다. 약어는 문서화한 인터페이스가 아니므로 `--fixture`를 쓴다. 새 옵션 하나에만 맞는 접두어(예: `--receipt`)는 이제 그 옵션으로 해석된다. v0.33.1에서는 사용 오류였다. `evaluate_recall.py`에서 `--ab`부터 `--abstention-`까지의 접두어는 두 새 옵션(`--abstention-calibration`·`--abstention-signal`)에 모두 맞아, v0.33.1의 `unrecognized arguments` 대신 `ambiguous option` 오류가 된다(종료 코드는 둘 다 2).
- 실행 코드의 SHA-256을 출력에 싣는 평가기(`evaluate_tool_matrix.py`의 `source_sha256`, `evaluate_retrieval_backends.py`가 싣는 `evaluate_recall.py`의 `code_sha256` 등)는 바뀐 파일의 지문 값이 다르다. `evaluate_tool_matrix.py`의 요청 바이트는 같고, 경과 시간은 원래 실행마다 다르다.
- 이미 있던 `check-support --bind-subject`를 켠 결과는 첫 글자가 ASCII가 아닌 글자인 주어에서 바뀔 수 있다(바로 아래 문단).
- `vault_warning_policy.py --certificate`가 내는 `checker_sha256`가 다르다(아래 인증서 문단).

`check-support --bind-subject`를 켠 결과는 바뀔 수 있다. 같은 줄의 주어 일치가 모두 새 경계에 막힌 행은 `bound` 대신 `subject_absent`가 되어 `binding_warnings`에 `ssot-subject-unbound`를 더하고, 인용 출처가 평가되지 않았으면 `unassessed`(`source_incomplete`)가 된다. ASCII 글자·숫자로 시작하는 주어, 오른쪽 경계, 값 비교와 기본 `check-support`의 출력·`warnings`·개수·종료 코드는 그대로다. 이 주어 식은 뒤보기로 시작해 검색이 느려진다. 2026-10-30 한 Windows PC(Python 3.12)의 합성 줄 측정에서 검색 한 번은 v0.33.1의 같은 주어 식보다 수십 배에서 200배 가까이 느렸고, 시간은 줄 길이에 비례했으며, 합성 최악 사례의 실행 전체는 0.65초에서 1.6초가 됐다([측정과 범위](../hardening.md#제목frontmatter-파싱과-코드링크-스캔의-선형-시간)).

선택형 주어 경계가 `vault_ssot.py`를 바꾸므로 경고 승격 인증서의 `checker_sha256`는 v0.33.1의 `af8f4c5ab9fc809a4998e55870e769d5f617d6742a53d0c5c2844df7ff3d7b92`(공개하지 않은 v0.33.0 후보와 같다)에서 `be02b141ffed91cbe34f8cb2317a790c60075740bfe5d8dc435ef202f113174f`로 바뀐다. 일곱 bound 파일 가운데 바뀐 것은 `vault_ssot.py`뿐이고 harmless corpus는 같다. 인증서는 버전 이름이 아니라 실제 바이트를 묶는다.

Claude Code와 Codex의 플러그인 설치본, 그리고 git 볼트에서 pre-commit 훅이 실행하는 볼트 안 엔진 사본(`00-meta/scripts/`)이 그 대상이다. 그래서 경고를 `fatal`로 올린 볼트는 갱신 전에 다음 순서를 따른다. 이전 버전으로 되돌릴 때도 같은 순서다.

1. 볼트 설정 `warning_policy.levels`에서 `fatal`로 올린 단계를 `warning`으로 되돌린다.
2. 볼트를 읽는 엔진을 모두 같은 버전(되돌릴 때는 이전 버전)으로 바꾼다. Claude Code와 Codex 설치본을 함께 바꾸고, git 볼트의 엔진 사본은 갱신할 때 `/vault-upgrade`(Codex `upgrade`)로 바꾼다. `/vault-upgrade`는 사본을 이전 버전으로 내리지 않으므로, 되돌릴 때는 그 사본도 이전 버전의 파일로 직접 되돌린다.
3. 바꾼 설치본에서 `vault_warning_policy.py --certificate`로 인증서를 다시 만들어 볼트 설정의 `warning_policy.certificate`에 넣는다. 이 명령은 harmless replay를 실행하므로 실행 결과와 설치 바이트를 확인한다.
4. 단계를 다시 `fatal`로 올린다.

맞지 않는 인증서를 유지하면 healthcheck는 종료 코드 1로 멈추고 SessionStart는 주입하지 않으며 `--staged`는 커밋을 막는다. doctor·recall은 `invalid_config`, `check-support`를 포함한 SSOT 명령은 `ssot_operation_unavailable`로 멈춘다. 게시만으로 활성 설치 캐시나 실제 볼트 엔진이 갱신되지는 않는다.

## 검증

공개 후보 소스에서 Windows 11·Python 3.12.10으로 전체 시험 2,626개를 실행해 실패·오류가 없었다(1,578.457초, 환경 제외 43). 환경 제외 가운데 3개는 이 PC에서 Aside 브라우저가 실행 중이라 건너뛴 Aside 도우미 시험이다. 같은 PC의 v0.33.1 기준선은 2,543개(환경 제외 40)였다. 통합한 다섯 기능의 읽기 전용 독립 검증(여섯 관점)과, 그 뒤 수정 커밋 아홉 개에 대한 두 번째 검증(두 관점)은 차단 0건이었다. 두 번째 검증의 지적은 `1228d4b`·`66a395f`·`67af284`로 반영했고 위 전체 시험만 다시 거쳤다. 이 PC에서는 Python 3.12만 실행했다. Python 3.10 호환은 정적으로만 확인했고, Python 3.10·3.14와 Linux·macOS는 CI 결과로 확인한다. 위 값은 공개 후보 시점의 관측이며 버전 문서를 바꾼 최종 릴리스 트리의 결과가 아니다.

최종 소스·플랫폼별 시험 수와 제외 수·CI·설치 확인·ZIP 재현·draft 자산·공개 게이트는 별도 절차다. 실제 명령·결과·고정 소스와 게시 전 상태는 `verification.json`, 공개 후 내려받기·해시·Latest/immutable 확인은 외부 `post-publication.json`에 남긴다. 문서를 준비한 시점에는 이 최종 게이트가 대기 중이며 문서 준비만으로 완료를 주장하지 않는다. [v0.34.0 검증 기록](../verification/v0.34.0.md)을 함께 본다.

## 알려진 경계

- 주어 왼쪽 경계는 UAX #29 단어 경계의 근사다. 가나·한자로 시작하는 주어도 바로 앞이 글자이면 막는다(UAX #29라면 끊는 자리다). 다섯 법인 형태 밖의 말이나 다른 낱말을 띄우지 않고 붙여 쓴 실제 언급(`고객사가나다전기`)은 놓쳐 `subject_absent` 경고가 될 수 있다. 렌더링하지 않은 줄도 비교하므로 글자와 주어 사이에 굵게·코드·링크 표시가 끼면 경계가 생긴다(`이**가나다전기**`·`이[[가나다전기]]`는 일치하고, 긴 이름 전체를 감싼 `**이가나다전기**`·`[[이가나다전기]]`는 일치하지 않는다). 같은 줄의 주어·값 동시 출현은 의미 귀속·권위·진실을 입증하지 않는다.
- 보정 문턱의 보장은 교환 가능성을 전제한 주변 보장이며, 조건부판과 동시 상한은 질의끼리의 독립도 전제한다. 빈 결과는 보장 밖이다. recall_hard(α = 0.05)에서는 팔마다 보정에 쓰는 답 있는 dev 문항이 28개 이하라 k가 1 이하다. 문턱이 있어도 보정 신호의 최솟값 한 점에 걸리고(n = 28이면 실현 거짓 거부율이 α를 넘을 확률이 약 0.238), Learn then Test는 어느 팔에서도 문턱을 내지 못한다. 볼트가 바뀌면 문턱은 무효다. 실익은 보정 집합을 늘린 뒤에 있다.
- `plan`의 크기는 무작위 추출·완전하고 정확한 라벨·고정 모집단을 전제한 계획값이며 보장이 아니다. 목표 몫과 x는 표본 파일에 남지 않는다. x = 0인 계획은 생산자 위험이 크다(N = 500, 목표 5%, 신뢰 수준 0.95의 54개 계획은 실제 놓침이 1%여도 약 44%의 확률로 목표 미달을 보고한다).
- `--receipt-order`는 로컬 시계로 찍은 기록 순서다. `plan_first`는 결과를 미리 보지 않았다는 증거가 아니고, `results_first`·`mixed`는 선택 편향 가능 표지일 뿐이다.
- 문자열 패턴 허용 목록은 값 길이에 대한 지수 시간 되돌아가기를 막는다. 다만 같은 문자에 맞는 수량자를 이어 쓴 패턴은 값 길이의 다항식 시간이, 수량자 없는 `|` 묶음을 여러 번 이어 쓴 패턴은 패턴 크기의 지수 시간이 걸릴 수 있다(지금 B의 두 패턴에는 해당하지 않는다). 소스를 읽어 확인한 llama.cpp b10729의 Qwen3-Coder XML 도구 호출 경로는 문자열 값의 `pattern`을 문법에 넣지 않으므로, 그 경로에서 B 패턴은 프롬프트 힌트로만 작동한다. 서버 동작은 실행으로 확인하지 않았고, 실제 모델로 A/B를 관측하지 않았다.
- 합성 대조군과 fixture 측정은 실제 모델 효능이나 실제 볼트 오류율을 측정하지 않는다. 설치 캐시·실제 볼트 엔진의 전환은 공개와 별도다.
