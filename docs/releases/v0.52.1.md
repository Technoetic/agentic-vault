# v0.52.1 — 같은 번호 보고, 가짜 머리글 줄 무력화, 판단 올리기 원답 보존

개선 조사가 먼저 볼 항목으로 고른 세 가지를 구현하고 저장소 설정 둘을 켠다. healthcheck는 한 노트에서 같은 번호를 단 결정·실수 제목을 보고만 하고, `SessionStart`는 훅 자신의 섹션 머리글처럼 시작하는 노트 줄을 무력화하며, `jev_ask.py --escalate-bizrouter`는 BizRouter 답 옆에 원래 Jev 답을 남기고 두 답이 다르면 검토를 요구한다. BizRouter 경로의 모델은 `google/gemini-decision-1` 하나로 줄인다. 저장소에는 `v*` 태그 규칙 집합(ruleset)과 비공개 취약점 제보를 켰다. 이 변경은 공개하지 않은 v0.52.0 후보에 처음 들어갔으며(저장소 설정 둘도 그때인 2026-11-16에 켰다), v0.52.1은 그 변경을 모두 담아 처음 공개하고 후보의 긴 Windows TEMP 경로 시험을 고친다. 기준은 공개 v0.51.0 커밋 `22168b7ddd10796e8ad0a894fe2c79a704bd7da2`다.

## v0.52.0 후보에서 고친 긴 TEMP 경로 시험

v0.52.0 후보의 독립 릴리스 검토는 검증 계약 1번 관문이 요구한 긴 Windows TEMP 경로 실행이 실제로는 기본 TEMP에서 돌았음을 찾아냈다. 그 실행은 TEMP·TMP를 Windows의 일반 경로 한계(260자)보다 긴 폴더로 잡았다. `LongPathsEnabled`가 0이면 Python `tempfile`은 그런 폴더에 파일을 만들지 못하고, 쓸 수 없는 TEMP 폴더를 오류 없이 건너뛰어 기본 임시 폴더를 쓴다. 그래서 그 실행은 보통의 기본 TEMP 실행과 같았다.

`tempfile`이 실제로 쓰는 150자 TEMP 폴더에서 전체 시험을 돌리자 v0.51.0과 v0.52.0에서 같은 131개 항목이 실패했다(시험 130개와, 시험 20개를 가진 시험 클래스 하나의 준비 단계. 26개 모듈, 두 판의 실패 목록이 같다). 기본 TEMP에서는 v0.52.0의 시험 4,518개가 실패 없이 끝난다(건너뜀 57개). 그러니 v0.52.0에서 생긴 회귀가 아니라 v0.51.0에도 있던 문제다. 131개 가운데 3개는 TEMP와 무관했다(아래 어댑터 시험 항목).

v0.52.1은 실패가 난 자리를 고친다.

- 저장소 도구 셋(`scripts/verify_codex_plugin.py`·`scripts/verify_antigravity_plugin.py`·`scripts/build_antigravity_package.py`)은 임시 작업 폴더가 그 아래에 만들 경로까지 더해 240자 기준에 닿을 때만 그 폴더를 Windows 확장 길이 형식(`\\?\`)으로 쓰고 같은 형식으로 지운다(패키지 생성기는 저장소·출력·비교할 패키지 폴더에도 같은 기준을 쓴다). 240자는 일반 경로 한계(260자) 아래에 여유를 둔 기준으로, `vault_evidence.fs_path`와 같다. 메시지와 보고서에는 일반 형식의 경로를 쓰고, git에는 늘 일반 형식의 폴더를 넘긴다. 세 도구는 같은 도우미 블록의 사본을 하나씩 갖고, `tests/test_long_path_helper_copies.py`가 사본이 바이트 단위로 같은지 확인한다.
- 런타임 모듈 `vault_lesson_metrics.py`는 관찰 기록 저장소의 파일 접근(상태 확인·목록·폴더 생성·잠금·임시 파일·링크·정리)을 `vault_evidence.fs_path`로 한다. 이 모듈은 v0.51.0이 긴 경로 도우미로 옮긴 모듈에 들어 있지 않았다. 관찰 기록은 볼트 루트에서 102자 아래에 놓이므로, 루트가 158자 이상이면 관찰 기록(`record`)이 `invalid_or_unavailable_input`으로 실패했다. 경로 검사도 맞췄다. 인증서가 묶는 `resolve_note_path`는 경로의 각 구성 요소를 일반 형식의 `lstat`으로 보아 링크와 재분석 지점(정션 포함)을 거부하는데, 일반 경로 한계를 넘는 구성 요소는 그렇게 볼 수 없어 없는 것으로 지나간다. 그래서 이 저장소는 240자 기준에 닿는 경로를 볼트의 확장 길이 형식에서 시작해 검사하고, 그보다 짧은 경로는 전처럼 검사한다. `tests/test_windows_long_paths.py`의 `LessonMetricsLongPathTests`는 어떤 TEMP에서도 172자 이상의 볼트를 만들어 기록과 요약을 확인하고, 확장 길이 형식으로 적은 볼트에서도 기록이 남김없이 끝나는지와, 일반 경로 한계를 넘는 기록 폴더에 놓인 정션을 짧은 경로에서처럼 `unsafe_path`로 거부하는지(Windows)를 확인한다. 오류 코드는 바꾸지 않았다.
- 평가 스크립트 넷은 임시 볼트의 영수증이 한계에 닿아도 그 볼트를 지운다. `scripts/evaluate_task_workflows.py`·`scripts/evaluate_improvement_experiments.py`·`scripts/evaluate_improvement_accounting.py`는 그럴 때 임시 볼트를 확장 길이 형식의 폴더에 만들고, `scripts/evaluate_memory_reliability.py`는 일반 형식 정리가 실패하면 확장 길이 형식으로 지운다. 전에는 `evaluate_task_workflows.py`와 `evaluate_memory_reliability.py`가 모든 확인이 통과한 뒤 임시 폴더를 지우지 못해 종료 코드 1로 끝났고, 두 개선 예제는 저장한 기록을 일반 경로로 확인하다 "native completion must be persisted"로 먼저 실패했다. `evaluate_memory_reliability.py`는 앞뒤 비교에서 한계를 넘는 기록 둘을 조용히 빠뜨리던 것도 `fs_path`로 읽고, `evaluate_improvement_experiments.py`는 저장한 기록의 확인 둘을 `fs_path`로 한다.
- 시험 fixture는 `tests/_winfs.py`의 `extended`·`plain`·`deep_path`로 한계를 넘는 경로를 만들고 읽고 지운다. 같은 파일의 `make_junction`은 링크 경로가 한계에 닿으면 확장 길이 형식으로 링크를 만든다. 전에는 긴 TEMP에서 정션을 만들지 못해 그 시험들이 건너뛰어졌다. 교훈 단서 훅의 프로세스 시험은 훅이 세션 표지를 둘 수 있는지 훅 자신의 함수로 물어, 둘 수 있으면 guard 왕복을, 없으면 문서에 적은 hint 전달을 확인한다. `SessionStart`의 긴 출처 이름 사례는 Windows에서 이름 길이를 폴더가 남기는 여유에 맞춘다(보통의 TEMP에서는 그대로 95자).
- 시험 패키지(`tests/__init__.py`)에는 한계를 넘는 항목이 있어도 `tempfile.TemporaryDirectory`가 임시 폴더를 지우게 하는 정리 보강이 있다. 전체 실행(`python -m unittest discover -s tests`)은 시험 모듈을 최상위 모듈로 읽어 이 패키지를 불러오지 않으므로, 지금까지 이 보강은 앞선 모듈이 패키지를 불러온 경우에만 켜졌다. 이제 이름순으로 맨 먼저 도는 `tests/test_000_environment.py`가 패키지를 불러와 전체 실행에서 늘 켜지고, 확장 길이 형식으로 다시 지울 때도 `tempfile`의 원래 정리 함수를 써서 읽기 전용 항목 처리를 유지한다. 모듈 하나만 discover 형식(`-p "test_x.py"`)으로 돌리면 지금도 켜지지 않는다.
- `tests/test_vault_adapters.py`의 실행 경로 시험 3개는 데스크톱 브라우저가 떠 있는지를 모듈을 읽을 때가 아니라 시험을 시작할 때 본다. 전체 실행은 첫 시험보다 훨씬 앞서 모든 모듈을 읽으므로, 그 사이에 브라우저가 켜지면 건너뛰어야 할 시험이 실패했다. 위 131개 가운데 3개가 이 경우였다.
- 한계보다 짧은 경로에서는 도구·모듈·스크립트·fixture가 쓰는 경로와 결과가 바뀌지 않는다.

같은 실행을 다시 할 수 있게 `scripts/long_temp_suite.py`를 더했다.

```text
python -B scripts/long_temp_suite.py [--length N] [--parent DIR] [--keep] [--summary OUT] [-- ARG ...]
```

이 도구는 경로 길이가 정확히 N자(기본 150)인 폴더를 `--parent`(기본은 현재 `tempfile.gettempdir()`) 아래에 만들어 TEMP·TMP·TMPDIR로 잡고, `AGENTIC_VAULT_REQUIRE_LONG_TEMP=N`을 준 채 저장소 루트에서 `python -m unittest`를 실행한다(`--` 뒤 인자가 없으면 `discover -s tests`). 시험을 시작하기 전에 자식 프로세스에서 `tempfile.gettempdir()`이 그 폴더인지 확인하고, 아니면 아무것도 실행하지 않고 종료 코드 3으로 끝난다. 그 밖에는 시험 실행의 종료 코드로 끝난다. Windows 상태 코드(예: Ctrl+C 뒤의 0xC000013A)도 그대로 넘긴다. 사용법 오류(예: 상위 폴더에서 만들 수 없는 길이)와 쓸 수 없는 `--summary` 파일은 2다. 폴더를 만든 실행은 끝난 뒤 폴더를 지우고(`--keep`이면 남긴다), Ctrl+C로 멈춘 경우까지 표준 오류의 마지막 줄에 `temp_length`·`tempfile_uses_temp`·`long_paths_enabled`·`returncode`·`python`·`platform` 키를 담은 한 줄 JSON 요약을 쓴다(`--summary OUT`이면 파일에도 쓴다). 사용법 오류에서는 폴더를 만들지 않으므로 요약이 없고, `--summary` 파일도 건드리지 않는다.

전체 시험 안에서는 `tests/test_000_environment.py`의 `DeclaredLongTempTests.test_tempfile_uses_the_declared_long_temp`가 같은 조건을 지킨다. `AGENTIC_VAULT_REQUIRE_LONG_TEMP`가 있으면 `tempfile.gettempdir()`이 TMPDIR·TEMP·TMP 가운데 처음 설정된 변수(`tempfile`이 읽는 순서)가 가리키는 폴더이고 그 길이가 선언한 값 이상이어야 통과하며, 없으면 임시 폴더를 쓸 수 있는지만 확인한다. 이 시험은 건너뛰지 않는다. `tests/test_long_temp_suite.py`는 `scripts/long_temp_suite.py`의 시험이다.

v0.52.0 태그는 다시 쓰지 않았고 그 태그에는 GitHub 릴리스가 없다.

## 변경

1. 같은 번호의 결정·실수 항목 보고(healthcheck 섹션 14d, 관리성, 보고 전용, `vault_healthcheck.py`).
   전체 검사는 다른 노트 섹션과 같은 노트 범위(금지 구역·제외 경로 적용)에서 2단계 제목(`##` 다음에 공백이나 탭) 가운데 글이 `ADR-<숫자>`나 `M-<숫자>`로 시작하는 것을 찾는다. 프런트매터·펜스 코드 블록·HTML 주석 안의 줄은 세지 않는다. 번호는 숫자가 아닌 첫 글자에서 끝나고 앞의 0은 번호에 넣지 않으므로 `ADR-12`와 `ADR-120`은 다른 번호이고, `ADR-007`과 `ADR-7a`는 `ADR-7`과 같은 번호다. 한 노트에서 같은 종류·같은 번호의 제목이 둘 이상이면 발견 한 건이며, 발견이 있을 때만 섹션 14c 자리 뒤·섹션 15 앞에 `## 14d. 같은 번호의 결정·실수 항목 — 관리성 (N)`을 쓴다. 줄마다 노트의 볼트 기준 POSIX 경로, 번호와 개수, 행 번호(편집기처럼 LF 줄 바꿈으로 센다)를 적는다. 볼트가 git 저장소이고 노트가 추적되면 `HEAD`의 노트를 같은 규칙으로 읽어 그 번호의 2단계 제목 수와 제목 줄을 본다. `HEAD`에도 있는 제목 줄이 노트에 더 많으면 어느 줄이 커밋된 것인지 가를 수 없다. 그렇지 않고 노트에 그 번호의 제목이 `HEAD`보다 많지 않으면 새 항목은 없으므로, 제목 줄이 모두 `HEAD`에 있으면 둘 다(셋 이상이면 모두) 두고 참조에 제목을 함께 적으라고 안내하고(제목을 바꾸면 앵커가 깨진다), `HEAD`와 다른 줄이 있으면 커밋된 항목의 제목을 고친 것이므로 `— HEAD와 제목이 다른 줄(<행 번호>행)은 커밋된 항목을 고친 것이다. 번호를 바꾸지 않는다.`를 쓴다. 노트의 제목이 k개 더 많고 `HEAD`에 없는 줄이 정확히 k개이면 그 행만 커밋 안 된 제목으로 적고 그쪽 번호를 바꾸라고 안내하며, `HEAD`에 그 번호의 제목이 하나도 없으면 `— 모두 커밋 안 됐다(<행 번호>행). 하나만 두고 나머지 번호를 바꾼다.`를 쓴다. 가를 수 없는 경우와 그 밖의 경우, git이 없거나 실패하거나 노트가 추적되지 않을 때는 `— 커밋 여부를 확인하지 못했다. 번호를 바꾸기 전에 참조를 확인한다.`를 쓰며 예외를 내지 않는다. 제목을 자동으로 고치거나 번호를 다시 매기지 않는다. `/vault-lint` 명령 안내(`commands/vault-lint.md`)에는 14d가 나오면 번호와 제목을 바꾸지 말고 줄 끝 안내대로 제안하라는 줄을 더했다. N은 관리성 합계에 더해지고, N이 1 이상일 때만 `--json-summary`에 `"duplicate_entry_ids": N`이 생긴다. 종료 코드·`--staged`·경고 정책·인증서는 바뀌지 않으며 이 섹션은 경고 정책으로 승격할 수 없다. 여러 세션이 함께 쓰는 볼트에서 같은 결정 번호를 단 항목 둘이 모두 커밋된 일이 계기다.
2. `SessionStart`의 가짜 머리글 줄 무력화(`hooks/session_start.py`).
   노트 줄이 앞의 공백 문자(`str.isspace()`가 참인 유니코드 공백: 공백·탭·줄 바꿈 없는 공백·전각 공백 등)와 폭 없는 문자(U+200B~U+200D·U+2060·U+FEFF)를 건너뛴 뒤 훅 자신의 섹션 머리글(`=== SESSION HANDOFF`, `=== HOT CONTEXT`, `=== FIXED CONSTRAINTS`, 훅의 머리글 상수에서 만든다)로 시작하면 그 줄 앞에 `NEUTRALIZED_PREFIX`인 `[note line, not a hook header] `를 붙이고 줄 끝은 그대로 둔다. 그런 줄이 없는 글은 그대로 돌려주며, 두 번 적용해도 결과가 같다. 비밀 마스킹 바로 뒤(`_neutralize_header_lines(_redact_sensitive_lines(text))`)에서 두 호출 지점(compact의 추가 노트와 주요 노트 섹션)에 모두 적용하므로 compact 고정 제약 발췌도 무력화한 글에서 만든다. 대화형 이벤트(`startup`·`resume`·`clear`·`compact`)와 `--host antigravity` 주입이 같은 처리를 받고, `vault_doctor`의 주입 추정도 같은 무력화를 적용한다. 그 줄이 훅의 섹션 머리글로 읽히지 않게 하는 위생 처리이며 프롬프트 주입 방어가 아니다([보안 정책](https://github.com/Technoetic/agentic-vault/blob/v0.52.1/SECURITY.md)). 전각 문자나 다른 철자로 쓴 머리글처럼 머리글을 닮기만 한 다른 줄은 그대로 지나간다.
3. 판단 올리기의 Jev 원답 보존과 BizRouter 모델 축소(`jev_ask.py`, `bizrouter_client.py`).
   `jev_ask.py run --escalate-bizrouter`가 저확신 문항을 BizRouter `google/gemini-decision-1`로 다시 물어 적용하면(`escalation.status: "applied"`), 그 문항의 결과는 지금처럼 BizRouter 답과 `"escalated_from"`(Jev 모델)을 담고, 새로 `"primary"`(올리기가 없었으면 나왔을 검증된 Jev 답, `id`를 뺀 같은 키와 값)와 `"agreement"`(참·거짓)를 더한다. 일치는 Choice는 같은 선택지, Noul은 두 확률이 0.5의 같은 쪽(어느 한쪽이라도 정확히 0.5이면 불일치), Score는 같은 단계 척도에서 두 `score` 값의 차가 1 이하일 때다. 검토 사유는 지금처럼 올린 답으로 `_review_reasons`를 다시 계산한 뒤, 일치하지 않는 문항마다 질문 순서대로 `{"id": <id>, "reason": "provider_disagreement"}`를 덧붙인다. 일치해도 사유를 지우지 않는다. `escalation` 객체에는 `"disagreed_ids"`(올린 순서, 비어 있을 수 있다)가 생긴다. `bizrouter_client.MODELS`는 `google/gemini-decision-1` 하나만 남기고(`model_limits`도 그 모델만 안다), 모듈 설명에 TypeSafe Jev 모델은 이 클라이언트로 부를 수 없다고 적는다. 그래서 `jev_ask.py`·`vault_judge.py`에서 `--provider bizrouter`와 `--model typesafe/jev-1.13.0`(또는 `typesafe/jev-latest`)를 함께 주면 기존 모델 검사가 지금과 같은 오류 코드 `invalid_arguments`와 종료 코드 2로 거부한다. TypeSafe Jev는 직접 TypeSafe API(`https://api.typesafe.ai/v1/systemone`, `TYPESAFE_API_KEY`)로만, `google/gemini-decision-1`은 BizRouter(`BIZROUTER_API_KEY`)로만 부르며, 어느 경로도 `typesafe/jev-*` 모델 이름을 BizRouter로 보내지 않는다. 일치는 정보이지 통과가 아니다([Jev 판단 안내](https://github.com/Technoetic/agentic-vault/blob/v0.52.1/docs/jev-judgments.md)).
4. 저장소 설정(유지관리자가 적용, 코드 변경 없음).
   태그 규칙 집합을 `refs/tags/v*`에 걸어 갱신과 삭제를 막았다. 생성은 막지 않고 우회 주체(bypass actor)는 없다. 비공개 취약점 제보도 켰다. 둘 다 v0.52.0 후보 때인 2026-11-16에 적용했고, v0.52.1 태그를 push하기 직전에 다시 읽어 그대로 켜져 있는지 확인한다. 그날 센 v0.52.0 이전 태그 70개 가운데 41개(불변 설정 전에 게시한 릴리스 23개, 초안만 있는 태그 4개, 릴리스가 없는 태그 14개)는 불변 릴리스 밖에 있었고, 규칙 집합은 켜져 있는 동안 그 태그들도, 릴리스가 없는 v0.52.0 태그도 옮기거나 지우지 못하게 한다([릴리스 무결성](https://github.com/Technoetic/agentic-vault/blob/v0.52.1/docs/release-integrity.md#v0230부터-불변-릴리스), [보안 정책](https://github.com/Technoetic/agentic-vault/blob/v0.52.1/SECURITY.md#reporting-a-vulnerability)).
5. 판 표면. 세 매니페스트와 생성 `antigravity/plugin.json`, healthcheck 스탬프와 `ENGINE_VERSION`, README·`docs/codex.md`·`docs/README.md`·`docs/antigravity.md`·`docs/release-integrity.md`·`SECURITY.md`의 현재 판 줄과 Codex 설명을 0.52.1로 옮긴다. Antigravity CLI 생성 패키지는 원본에서 다시 만들고 사본 일치를 검사한다. v0.52.0 릴리스 노트와 검증 계약은 미공개 후보로 표시한다.
6. 긴 Windows TEMP 경로에서 실패하던 저장소 도구·평가 스크립트·`vault_lesson_metrics.py`·시험 fixture 수정, `scripts/long_temp_suite.py` 추가.
   위 "v0.52.0 후보에서 고친 긴 TEMP 경로 시험" 절에 적었다.

## 기본 결과 변경

- 판 메타데이터: 매니페스트 버전·설치 태그·healthcheck 스탬프(`engine=0.52.1`, 2행)와 `ENGINE_VERSION`이 `0.52.1`로 이동한다.
- `vault_healthcheck.py` 전체 검사: 한 노트에 같은 `ADR-<n>`이나 `M-<n>` 번호의 2단계 제목이 둘 이상 있는 볼트에서만 섹션 14d가 생기고 관리성 합계가 늘며 `--json-summary`에 `duplicate_entry_ids`가 생긴다. 그런 노트가 없으면 보고서와 JSON 줄은 v0.51.0과 바이트 단위로 같다. 종료 코드와 `--staged`는 바뀌지 않는다.
- `SessionStart` 주입(대화형 이벤트와 `--host antigravity`, 같은 내용의 `vault_doctor` 출력): 훅의 섹션 머리글로 시작하는 노트 줄에만 `[note line, not a hook header] `가 붙는다. 그런 줄이 없는 노트의 출력은 v0.51.0과 바이트 단위로 같다.
- `jev_ask.py`: `--escalate-bizrouter`로 올리기가 적용된 실행(`escalation.status: "applied"`)에서만 올린 문항의 결과에 `primary`·`agreement`가, `escalation`에 `disagreed_ids`가 생긴다. 두 공급자의 답이 다르면 `review_reasons`에 `provider_disagreement`가 더해져 상태가 `needs_review`(종료 코드 2)가 된다. `unavailable`·`not_needed` 상태, 플래그 없는 실행, `prepare`, `vault_judge.py`의 출력은 기본 공급자와 `google/gemini-decision-1`에서 v0.51.0과 바이트 단위로 같다(`typesafe/jev-*` 모델을 BizRouter로 부르던 호출은 아래 BizRouter 모델 축소의 예외다).
- BizRouter 모델 축소: `--provider bizrouter`에 `--model typesafe/jev-1.13.0`이나 `typesafe/jev-latest`를 주면 v0.51.0은 BizRouter로 보냈지만 이제 `invalid_arguments`(종료 코드 2)로 거부한다. 기본 모델(`google/gemini-decision-1`)과 기본 공급자(`--provider jev`)의 결과는 바뀌지 않는다.
- 긴 경로: 저장소 도구 셋, 평가 스크립트 넷, `vault_lesson_metrics.py`와 시험 fixture는 다루는 경로가 240자 기준(일반 경로 한계 260자 아래의 여유)에 닿는 Windows 실행에서만 달라진다(위 긴 TEMP 경로 절). 그보다 짧은 경로에서는 바뀌지 않는다.

## 하위호환·업그레이드

현재 설치 ref는 `v0.52.1`이다.

기존 볼트 설정 키는 추가하거나 마이그레이션하지 않는다. 공개 준비 자체가 활성 설치나 운영 볼트를 자동으로 갱신하지 않는다. 볼트에 복사된 healthcheck는 `/vault-upgrade`(Codex는 `upgrade`)를 실행한 뒤에 섹션 14d를 낸다. `--provider bizrouter`에 `--model`로 `typesafe/jev-1.13.0`·`typesafe/jev-latest`를 함께 쓰던 호출은 `invalid_arguments`로 거부되므로 기본 공급자(`--provider jev`, 직접 TypeSafe API)로 바꾼다. `--escalate-bizrouter` 결과를 읽는 도구는 올린 문항의 새 키 `primary`·`agreement`와 `escalation.disagreed_ids`, 검토 사유 `provider_disagreement`를 무시하거나 처리해야 한다. v0.52.0 후보 태그로 설치했다면 같은 방법으로 v0.52.1로 갱신한다.

인증서가 묶는 일곱 파일(`vault_lint_extensions.py`·`vault_warning_policy.py`·`vault_provenance.py`·`vault_egress.py`·`vault_ssot.py`·`jev_client.py`·`vault_paths.py`)은 v0.46.0부터 v0.52.1까지 바이트 단위로 같아, 실제 설치 바이트가 같은 경우 기존 경고 승격 인증서가 그대로 유효하다. v0.45.1 이하와 오갈 때는 [v0.46.0 업그레이드 안내](https://github.com/Technoetic/agentic-vault/blob/v0.52.1/docs/releases/v0.46.0.md#하위호환업그레이드)를 따른다. healthcheck만 `engine=0.52.1`로 이동하며 기존 규칙·어댑터 스탬프는 유지한다. `checker_sha256`는 `09642e7aa77d0b812f5afa646b491fe2d79d44104e399bea4a3001a6f2f1279d` 그대로다.

## 검증

[검증 계약](https://github.com/Technoetic/agentic-vault/blob/v0.52.1/docs/verification/v0.52.1.md)에 요구 관문을 적었다. 최종 소스의 시험 수·종료 코드·건너뜀·CI·독립 검토·ZIP 재빌드·설치 자원 바이트·인증서 결과는 릴리스의 `verification.json`에 기록한다. 긴 TEMP 경로 실행의 결과와 그때의 `LongPathsEnabled` 값도 함께 기록한다. 게시 후 새 다운로드와 릴리스 증명 확인은 별도 기록으로 남긴다. 계약 문서 자체는 통과 결과가 아니다.

새 회귀 시험은 같은 번호 제목의 보고·커밋 상태별 안내·코드 블록 제외·노트 사이 구분·번호 경계·JSON 키·종료 코드와 `--staged` 불변을 확인하는 새 모듈 `tests/test_healthcheck_duplicate_entry_ids.py`, 대화형·`compact`·`--host antigravity`에서 위조 머리글 줄이 접두어를 받고 진짜 머리글이 하나씩만 남는지와 일반 노트의 바이트 동일·멱등·비밀 마스킹 순서를 확인하는 새 모듈 `tests/test_session_header_lines.py`, `MODELS` 축소·두 진입점의 `typesafe/jev-*` 거부·Choice/Noul/Score의 일치와 불일치 올리기(`primary`·`agreement`·`disagreed_ids`·검토 사유)·플래그 없는 출력의 v0.51.0 동일을 확인하는 `tests/test_bizrouter_decisions.py`의 시험, 그리고 이 노트·검증 계약·판 표면을 고정하는 `tests/test_release_metadata.py`의 `V0521ReleaseMetadataTests`다. 긴 TEMP 경로 쪽에는 선언한 긴 TEMP를 `tempfile`이 실제로 쓰는지 확인하는 `tests/test_000_environment.py`와 `scripts/long_temp_suite.py`의 시험 `tests/test_long_temp_suite.py`가 있다. 저장소 설정 둘은 시험 모듈이 아니라 태그 push 직전에 API로 다시 읽어 확인하고 결과를 `verification.json`에 남긴다(검증 계약 4번 관문).

| [GitHub Docs: Configuring private vulnerability reporting for a repository](https://docs.github.com/en/code-security/how-tos/report-and-fix-vulnerabilities/configure-vulnerability-reporting/configure-for-a-repository) | 공개 저장소의 소유자·관리자가 켜면 보안 연구자가 저장소의 **Report a vulnerability** 단추나 REST API로 비공개 보고를 낼 수 있다 | 4번 항목. 켜고 보안 정책의 제보 단계를 고쳤다. 양식이 없을 때 내용 없이 연락만 요청하는 공개 이슈 경로는 남긴다 |
| [GitHub Docs: About rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets) · [Available rules for rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets) | 태그를 대상으로 하는 규칙 집합, 우회 권한, 활성·비활성 상태. `Restrict updates`·`Restrict deletions`를 고르면 우회 권한이 있는 사용자만 이름이 맞는 태그를 push하거나 지울 수 있다 | 4번 항목. 우회 주체 없이 갱신·삭제를 막고 생성 규칙은 넣지 않았다. 관리자는 규칙 집합을 끌 수 있으므로 증명하는 범위를 릴리스 무결성 문서에 적었다 |

세 기능은 기존 동작 위에 얹었다. 2번 항목은 v0.51.0의 비밀 마스킹 바로 뒤에 붙는 같은 종류의 위생 처리이고, 3번 항목은 v0.51.0의 저확신 올리기(`--escalate-bizrouter`)의 대상과 호출을 그대로 두고 결과에 원답과 일치를 더한다. 1번 항목은 다른 관리성 섹션과 같은 노트 범위와 기존 git 보조 함수를 쓴다. 출처들이 보고한 효과 수치는 이 저장소의 효과로 주장하지 않는다. 이전 저장소 문서는 이 출처들을 인용하지 않았다(`git grep`으로 위 주소를 찾아 v0.51.0 트리에 일치가 없음을 확인했다). 공개하지 않은 v0.52.0 후보의 문서는 같은 출처를 인용했고, 긴 TEMP 경로 수정에는 새 출처를 쓰지 않았다. 릴리스 무결성 문서는 SLSA를 빌드 출처 증명(`actions/attest`)의 맥락에서만 언급했고 Source 트랙과 위 SLSA 문서는 인용하지 않았다.

## 알려진 경계

- 섹션 14d는 한 노트 안의 2단계 `ADR-<숫자>`·`M-<숫자>` 제목만 본다. 다른 형식의 번호, 서로 다른 노트의 같은 번호, 본문 속 참조는 보지 않고, 번호를 예약하거나 동시에 쓰는 세션을 막지 않는다. 펜스 코드 블록과 HTML 주석 안의 제목은 세지 않고, 앞의 0과 숫자 뒤 글자는 번호에 넣지 않아 `ADR-007`·`ADR-7a`도 `ADR-7`로 센다. HTML 주석은 인증서가 묶는 공용 줄 정리 함수(`vault_lint_extensions.py`의 `_clean_lines`)로 가리며 이 함수는 인라인 코드 안의 `<!--`도 주석의 시작으로 보므로, 그 뒤부터 다음 `-->`까지의 제목은 세지 않는다. 커밋 여부는 같은 경로의 `HEAD` 노트에 있는 같은 번호의 제목 수와 제목 줄로만 판단한다. 그래서 커밋된 제목을 고치면서 같은 번호의 제목을 새로 더하면 어느 쪽이 새 항목인지 가르지 못해 확인하지 못했다고 쓰고, 커밋하기 전에 옮긴(`git mv`) 노트는 `HEAD`에 그 경로가 없어 제목을 모두 커밋 안 된 것으로 본다.
- 머리글 줄 무력화는 앞의 공백 문자(`str.isspace()`가 참인 유니코드 공백)와 폭 없는 문자(U+200B~U+200D·U+2060·U+FEFF)를 건너뛴 뒤 훅 자신의 세 머리글로 시작하는 줄만 바꾼다. 머리글을 닮기만 한 다른 줄(전각 등호 `＝`나 다른 철자·띄어쓰기·대소문자로 쓴 머리글, U+00AD·U+200E 같은 다른 서식 문자가 앞에 붙은 머리글)과 다른 모양의 지시문이나 뜻으로 꾸민 주입은 그대로 지나가며, 이것은 위생이지 적응형 프롬프트 주입에 대한 보장이 아니다. 방어는 노트 글에서 권한이 생기지 않는 것과 금지 구역 같은 결정론적 통제다.
- 일치는 두 공급자의 답이 같은 쪽이라는 정보일 뿐 정답의 보장이 아니다. 두 모델이 같은 오해를 공유하면 함께 틀릴 수 있다. 올리기는 v0.51.0처럼 저확신 문항만 대상으로 하며, `BIZROUTER_API_KEY`가 없거나 호출이 실패하면 Jev 원응답과 `escalation.status: "unavailable"`만 남는다.
- 태그 규칙 집합은 켜져 있는 동안만 `v*` 태그의 이동·삭제를 막는다. 누가 태그를 만들었는지, 규칙 집합이 꺼져 있던 기간의 일은 증명하지 않으며 관리자는 규칙 집합을 끌 수 있다. 비공개 취약점 제보도 저장소 설정이라 꺼질 수 있고, 그때는 공개 이슈로 연락만 요청한다.
- `vault_doctor`의 주입 추정은 v0.51.0부터 비밀 마스킹을 적용하지 않아, 비밀 줄이 있는 노트에서는 추정 글자 수가 훅 출력과 다르다. 이번 판은 머리글 줄 무력화만 훅과 같게 맞췄다.
- 생성 Antigravity CLI 패키지의 사본 일치와 `agy plugin validate --strict`는 검사하지만 실제 agy 대화 세션은 실행하지 않는다.
- 긴 TEMP 경로 실행은 `LongPathsEnabled`가 0인 Windows에서 TEMP·TMP를 150자 폴더로 잡은 로컬 실행이다. 모든 길이의 TEMP에서 통과한다는 주장이 아니다. CI는 기본 TEMP에서만 돌고, GitHub의 Windows 러너는 긴 경로를 켜 두어(`LongPathsEnabled` 1) 긴 경로 시험이 이 수정 없이도 통과하므로, 이번 수정의 동작은 `LongPathsEnabled` 0인 로컬 관문 실행만 확인한다.
- git 자체의 경로 한계는 그대로다. `git bundle create`는 대상 경로가 254자일 때까지 받고 255자부터 거부한다(git 2.55.0.windows.3에서 확인). 150자 실행에서 git을 쓰는 시험의 여유는 5자쯤이어서, 그보다 긴 TEMP에서는 백업 이력 시험과 패키지의 git 모드 시험이 실패한다.
- 긴 TEMP에서 Codex 검증기는 넘기는 경로 자체가 한계에 닿을 때만, Antigravity 검증기는 작업 폴더가 한계에 닿으면 패키지 사본 경로와 홈 변수들을 확장 길이 형식으로 넘긴다(시작 폴더는 일반 형식이다). 어느 쪽도 실제 `codex`·`agy` 실행 파일로는 확인하지 않았다. 시험은 그 자리에 파이썬으로 쓴 대역을 쓴다.
- v0.51.0이 긴 경로 도우미로 옮긴 런타임 모듈(`vault_state.py` 등)은 경로 검사를 그대로 두었다. 그래서 볼트 루트가 아주 길어(약 230자 이상) 런타임 폴더 자체가 일반 경로 한계를 넘으면, 그 폴더 자리에 놓인 정션을 링크 검사가 보지 못하고 따라간다(호스트가 231자 루트에서 확인했다. 120자 루트에서는 거부한다). 이번 판은 이 동작을 바꾸지 않았고 `vault_lesson_metrics.py`만 고쳤다. 그런 정션을 두려면 볼트 폴더에 쓸 수 있어야 한다.
- 150자 실행이 닿지 않는 더 깊은 경로에는 긴 경로 도우미를 쓰지 않는 런타임 지점이 남아 있다. 예를 들어 `vault_proposals.py`는 도우미를 쓰지 않고, `vault_healthcheck.py`가 체크포인트 어긋남 검사에서 읽는 기록도 일반 경로로 읽는다.
- CI 워크플로의 스크립트 스모크 명령 22개는 150자 TEMP에서 명령으로 돌려도 종료 코드 0으로 끝난다(전체 시험과 별도로 확인했다). 그 밖의 스크립트를 긴 TEMP에서 명령으로 돌리는 경우는 확인하지 않았다.
- 긴 TEMP에서 통과하는 시험 가운데는 한계를 넘는 일반 경로의 존재 확인처럼 그 환경에서 조건이 약해지는 단언이 남아 있을 수 있다. 실패한 시험과 그 주변만 고쳤다.
- 교훈 단서 어댑터(`assets/adapters/lesson-cues/lesson-cues.py`)는 세션 표지를 TEMP 아래 92자에 사용자 이름을 더한 길이의 경로에 둔다. 그 경로가 Windows의 일반 경로 한계를 넘으면 표지를 쓸 수 없어, 문서에 적은 대체 동작대로 guard를 hint로 전달한다. v0.52.1은 이 어댑터를 바꾸지 않는다.
