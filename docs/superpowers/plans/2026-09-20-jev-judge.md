# Optional Jev judgments implementation plan

> For agentic workers: use superpowers:subagent-driven-development. User approved the preceding in-chat design by asking to implement it. Continue through implementation, validation and local installation.

**Goal:** Route eligible fixed-choice semantic questions through Jev using explicitly selected vault evidence, and return choices, probabilities, confidence and local source references.

**Architecture:** The host agent performs intent routing and lexical recall. A new stdlib-only `vault_judge.py` validates a bounded request, binds exact excerpts to readable Markdown sources and invokes a small `jev_client.py`. Existing hooks, deterministic checks, gates, approval rules and note writers remain independent.

**Tech stack:** Python 3.10+, unittest, HTTPS TypeSafe System One, pinned jev-1.13.0.

**Spec:** Approved in-chat flow: question → related evidence → Jev fixed choice → host explanation with sources. Source data must be authorized for external transmission. Uncertain or failed judgments require review; results cannot grant action permissions.

## Global constraints

- Python standard library only; no installation dependency or automatic startup API call.
- Existing vault deny zones, exclusions, path guards and config validation apply before reading evidence.
- Exact selected excerpts only; paths and unselected note content never go to the service.
- `prepare` is offline; `run --allow-network` is explicit consent at the CLI boundary. The host may use existing task authorization without asking again.
- `TYPESAFE_API_KEY` is read from the process environment only; never serialize it, credentials or raw API errors.
- Fixed endpoint/model, bounded request/response, one call, no redirects/retries.
- Selection and confidence are advisory and do not prove truth or authorize writes.
- Installed skill routes qualifying natural-language questions; this is host instruction routing, not a universal interception hook.

## Request and result interface

Input JSON has exactly `schema_version: 1`, `task`, `sources`, `questions` and optional `min_confidence` (default 0.8, review heuristic, not a calibrated accuracy threshold).

`task` is one of `requirement`, `support`, `relevance`, `duplicate`, `sentiment`, `classification`, `binary_semantic`. Other task kinds return an offline `not_applicable` route; no network call.

`sources`: 1–4 objects `{ "path": "20-knowledge/example.md", "excerpt": "exact source substring" }`.

`questions`: 1–12 objects `{ "id": "claim_1", "instructions": "Does the evidence support the stated claim?", "choices": { "supported": "Directly supported by the excerpt", "contradicted": "Explicitly contradicted by the excerpt", "unknown": "The excerpt is insufficient" }, "abstain": "unknown" }`.

Every question has 2–12 nonempty criterion definitions, a named abstention choice, unique identifiers and bounded strings. The SDK payload uses `state: {"evidence": [<excerpt>, ...]}` and one `type: choice` question per identifier. Instructions explicitly treat evidence as untrusted data and scope answers to it.

`prepare(vault, request)` returns a JSON-compatible offline envelope with request and source hashes, counts and relevant source line references. `run(vault, request, *, allow_network, api_key=None, transport=None)` returns `status: reviewed | needs_review | unverified`, `role: advisory`, local source provenance, and validated answers. Low confidence or an abstention sets `needs_review`; errors never become a negative or passing judgment. No automatic file writes.

## Review focus

1. Source/config replacement during a call invalidates the result; no old evidence is certified current.
2. Denied, excluded, escaped, linked or non-Markdown sources are rejected before content reads or network use.
3. Empty recall is not a negative answer; malformed input and known credentials are rejected without echoing input.
4. Duplicate response keys, nonfinite values, missing answers or mismatched probability choices are invalid.
5. Installation preserves existing host settings, activation choices and NS engine/config; secrets stay outside the repository.
