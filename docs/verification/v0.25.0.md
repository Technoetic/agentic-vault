# v0.25.0 verification

This release recommends Claude Code 2.1.295 or later and adds an on-request host-version check,
opt-in warning-only sync-conflict and checkpoint-drift healthcheck warnings, an opt-in in-place
gold-set recall evaluation with redaction, held-out splits and `inspected` marks, opt-in exact
paired p-values and rate upper bounds, opt-in llama-server measurement records, and a hash-pinned
pip-audit install in the advisory CI job. See the [release notes](../releases/v0.25.0.md).
Default dependencies, hook definitions, model/network calls and search settings are unchanged.
Publication, an active installed-cache update and a vault upgrade are separate operations.

### Release review fixes

A read-only release review of `bdcb328` raised two blocking findings. One commit fixes both; it
changes this record, the release notes, `docs/hardening.md` and one test file, and no feature code.

- **Python 3.10 test assertion.** `brute_force_p` in `tests/test_small_sample_stats.py` now adds the
  threshold and every pattern sum strictly left to right with a small loop instead of the built-in
  `sum()`, so its float noise no longer depends on the interpreter, and the zero-tolerance assertion
  pins 0.5 (four of the six exact ties break). On Python 3.12.10 the module ran 26 tests, OK. With the
  built-in `sum()` replaced by plain left-to-right addition, the CPython 3.10 rule, the previous test
  failed exactly like CI (line 148, `0.5 != 0.625`) and the fixed test ran 26 tests, OK. No Python 3.10
  interpreter was run locally; the exact-commit CI must show the three Python 3.10 jobs passing.
- **Malformed-key scope.** "Every config reader" generalised from code reading beyond what was
  measured. The release notes, `docs/hardening.md` and the
  [configuration-key section](#new-configuration-keys-and-downgrade) now name the measured components,
  and that section records the additional measurement.

## Compatibility and upgrade boundary

### Warning-promotion certificates

`vault_warning_policy.checker_sha256()` hashes the bytes of seven files: `vault_lint_extensions.py`,
`vault_warning_policy.py`, `vault_provenance.py`, `vault_egress.py`, `vault_ssot.py`, `jev_client.py` and
`vault_paths.py`. The list is the same at `476488b` (v0.23.0), `d2b9315` (v0.24.0) and the release
preparation tree. The certificate also binds the bundled benign corpus
`skills/agentic-vault/scripts/resources/lint-benign-v1.json`.
The changed engine files of this release, `vault_healthcheck.py` and `vault_doctor.py`, are not inputs,
and the Git blobs of the seven inputs and the corpus equal v0.24.0.

Measured on 2026-10-19 with every file in its LF repository bytes: v0.23.0, v0.24.0 and `4de01be`
exported by `git -c core.autocrlf=false archive`, and a copy of the release preparation tree's
`skills/` and `hooks/` with the working-tree CRLF of LF-indexed files turned back into LF (its corpus
blob equals the committed one):

| Tree | `checker_sha256` | `corpus_sha256` | `--certificate` |
|---|---|---|---|
| v0.23.0 `476488b` | `b7138def2c0ef0ff…` | `38efaabde0ce1e1d…` | exit 0, 21 cases, 0 false positives |
| v0.24.0 `d2b9315` | `2ef4b9d40f70132a…` | `38efaabde0ce1e1d…` | exit 0, 21 cases, 0 false positives |
| integration `4de01be` | `2ef4b9d40f70132a…` | `38efaabde0ce1e1d…` | all seven fields equal to v0.24.0 |
| release preparation tree | `2ef4b9d40f70132a…` | `38efaabde0ce1e1d…` | all seven fields equal to v0.24.0 |

A synthetic vault from the public sync golden fixture promoted `missing-anchor` to `fatal` with each
certificate. With the v0.24.0 certificate, the v0.24.0, integration and release preparation
healthchecks exited 0 and `session_start.py` injected the hot note. With the v0.23.0 certificate, all
three exited 1 with
`warning promotion rejected: promotion certificate checker_sha256 differs from current harmless replay`
and `session_start.py` printed only `agentic-vault: invalid session context configuration`. The same
configuration with the level returned to `warning` exited 0. Certificates made with v0.24.0 therefore
remain valid for v0.25.0, while v0.23.0 or older certificates still need the v0.24.0 procedure: return
promoted levels to warning before upgrading, then run `vault_warning_policy.py --certificate` on the new
installation and promote again. See the [v0.25.0 upgrade notes](../releases/v0.25.0.md#하위호환업그레이드)
and the [v0.24.0 instructions](../releases/v0.24.0.md#하위호환업그레이드). No actual user vault
certificate was rewritten.

The corpus JSON has no `eol=lf` attribute, unlike `*.py`. In this release's Windows working tree
(`core.autocrlf=true`) it is checked out with 159 CRLF line endings, giving `corpus_sha256`
`4b31a673f9948ea7…` instead of `38efaabde0ce1e1d…`; converting the v0.24.0 corpus to CRLF gives the same
`4b31a673f9948ea7…`. Running the same matrix with the working tree as the new engine, the LF v0.24.0
certificate was rejected with `promotion certificate corpus_sha256 differs from current harmless replay`,
and the working tree's own certificate was accepted by the working-tree engine and rejected by the LF
v0.24.0 engine. A certificate therefore carries over only between installations whose corpus bytes,
including line endings, are the same. This dependence predates this release.

### New configuration keys and downgrade

The v0.24.0 tree (`d2b9315`), extracted outside the repository, ran against one synthetic vault in three
variants: no new keys; `sync_conflict_check: true`, `sync_conflict_patterns: ["*.conflict-copy.md"]` and
`checkpoint_drift_check: true`; and malformed values (`"yes"`, `"dir/x.md"`, `1`). For each variant a
fresh copy at the same path ran `vault_healthcheck.py` (full mode), `hooks/session_start.py` (startup),
`hooks/session_checkpoint.py --event SessionEnd`, `vault_doctor.py --format json` and
`vault_recall.py --query Plan --format json`. Under v0.24.0 every exit code, stdout, stderr and report
byte was identical across the three variants, and the checkpoint was written each time: v0.24.0 ignores
the three keys, valid or not. Turning the warnings on in v0.25.0 and downgrading therefore switches them
off silently.

The preparation tree, in the same runs, matched v0.24.0 byte for byte in all five components without the
keys. With valid keys only the healthcheck changed: 8 additional §15 warnings (6 file names, 2 checkpoint
drifts), exit 0. With malformed keys the healthcheck exited 1 with `sync_conflict_check must be true/false`,
`session_start.py` injected nothing, the checkpoint was not written (`agentic-vault: checkpoint unavailable`),
and the doctor (`config_schema_invalid`) and recall (`invalid_config`) exited 2. A malformed key that had no
effect under v0.24.0 therefore stops these five components after the upgrade.

The release review measured more components on 2026-10-19: `bdcb328` archived with LF bytes, Python 3.12.10,
a fresh synthetic vault per variant with the same malformed values, and no-key and valid-key controls in
which every component below succeeded. With the config in the Git index, `vault_healthcheck.py --staged`
exited 1 with `sync_conflict_check must be true/false`, so the vault pre-commit hook, which passes that
exit code through, blocks commits. In the Jarvis bridge, `load_jarvis_config` returned the configuration,
but `do_capture` failed with `capture destination is denied or unsafe` (its capture policy validates the
config through `vault_evidence.Store`), and `_generation_prompt`, which builds the Q&A and briefing
context through recall, failed with `context unavailable`. `backup_vault.py`, whose own loader checks
only `backup_target` and `exclude_dirs`, created a snapshot with exit 0, and `--verify` exited 0. The
stop therefore covers components that validate the configuration with `validate_config`, not every
reader of `vault-config.json`.

## Publication receipts

The immutable-release draft receives the tagged-source ZIP, LF `SHA256SUMS` and LF
`verification.json`. That JSON records the pre-publication final source and metadata, remote CI,
ZIP/blob comparisons and the independent release review. It cannot contain the later verification of
its own locked published bytes.

After publication, `gh release verify`, all three `gh release verify-asset` checks and public
re-download hashes are recorded in a separate `post-publication.json` retained outside the immutable
release assets and referenced by the operational handoff. At record preparation these publication
checks were pending. The repository's immutable-releases setting was re-queried on 2026-10-19 and
returned `{"enabled": true, "enforced_by_owner": false}`; v0.23.0 and v0.24.0 report `isImmutable: true`.
Follow [release integrity](../release-integrity.md) for the commands and their limits. Release-service
signatures certify published-asset identity; they do not certify build provenance, the approving
person's identity or content safety.
