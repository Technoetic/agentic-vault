# v0.26.0 verification

This release records Jarvis messages sent through an inline bot as the untrusted `via_bot` capture
origin (a default change), adds a directory name-listing comparison to the opt-in query-expansion
inventory check and instruction-budget diagnosis, adds opt-in keyed pseudonymisation of gold-set
recall reports, a reproducible release ZIP build with a report-only L1/L2 rebuild check, a classifier
for the concurrent run-receipt test and a repeat runner with exact failure-rate bounds, and moves test
junction creation to a shared helper. See the [release notes](../releases/v0.26.0.md). Default
dependencies, hook definitions, model/network calls and search settings are unchanged. Publication, an
active installed-cache update and a vault upgrade are separate operations.

Certificates made with v0.25.0 or earlier therefore fail closed on v0.26.0, and a v0.26.0 certificate
fails closed after a rollback. The remedy is the same in both directions: return promoted levels to
`warning` before changing versions, then run `vault_warning_policy.py --certificate` on the installation
that will run and promote again. See the [upgrade notes](../releases/v0.26.0.md#하위호환업그레이드). No
actual user vault certificate was rewritten. The corpus line-ending dependence recorded for v0.25.0
(CRLF checkouts give a different `corpus_sha256`) is unchanged.

### via_bot captures across versions

The release review confirmed that the v0.25.0 `vault_provenance.ORIGINS` does not contain `via_bot` and
that parse validation raises `invalid_origin`, so an engine older than v0.26.0 reports every `via_bot`
capture as `provenance-invalid`, a promotable code. Claude Code and Codex plugin caches are updated
separately, so every installation that reads the vault is updated together before the new bridge writes
such captures. Before a rollback, pending `via_bot` captures are processed or quarantined, or
`provenance-invalid` stays at `warning`. Failing closed on an unknown origin is intended, so no code
changed. Captures stored before v0.26.0 are not relabelled; an inline-bot memo captured by an older
bridge stays `own` (or `url`).

### Opt-in diagnostics and report fields

Query expansion and the instruction-budget diagnosis run only when selected. When they run, the
inventory and report gain the fields listed in the release notes, a listing-only change gives
`source_changed` or `partial`, and an unreadable or over-cap re-listing fails closed. Plain `--redact`
output gains only `redaction_mode` and `redaction_algorithm`; the tests pin the rest against canonical
hashes captured from `833d394`. With `--expand-query`, `inventory_verification` also changes as above, and
the canonical-hash test normalises that block to the v0.25.0 shape before comparing. Without the new options, gold-set output is unchanged.

## Publication receipts

This is the first release whose ZIP is built with the documented reproducible procedure:
`TZ=UTC0 git -c core.autocrlf=false archive --format=zip --prefix=agentic-vault-0.26.0/`, through
`scripts/release_rebuild.py build`, whose `rebuild_spec` output goes into `verification.json`. Byte
reproduction (L1) has been measured only within git 2.55.0.windows.3; other git builds should rely on
the L2 member and blob comparison, which needs git 2.40 or later. See
[release integrity](../release-integrity.md#zip-재현과-재빌드-명세).

The immutable-release draft receives the tagged-source ZIP, LF `SHA256SUMS` and LF
`verification.json`. That JSON records the pre-publication final source and metadata, remote CI, the
rebuild specification, ZIP/blob comparisons and the independent release review. It cannot contain the
later verification of its own locked published bytes. After publication, `gh release verify`, all three
`gh release verify-asset` checks and public re-download hashes are recorded in a separate
`post-publication.json` retained outside the immutable release assets and referenced by the operational
handoff. v0.25.0's post-publication record (2026-10-19) reports `immutable: true` and all checks passed.
Release-service signatures certify published-asset identity; they do not certify build provenance, the
approving person's identity or content safety.
