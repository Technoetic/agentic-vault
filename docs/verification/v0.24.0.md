## Compatibility and upgrade boundary

The six rule templates, command documents, hook definitions and hook scripts retain their
v0.23.0 content. Healthcheck stamp and `ENGINE_VERSION` become 0.24.0; unchanged rule stamps stay
at their previous values. New model/retrieval comparisons require explicit CLI selection and
optional packages stay in external experiment environments.

`vault_paths.py` is part of `vault_warning_policy.py`'s checker-byte digest. Its change makes
older `checker_sha256` warning-promotion certificates stale. An existing fatal promotion with
an old certificate fails closed as a configuration error. Users should return promoted levels
to warning before upgrading, then use `vault_warning_policy.py --certificate` on the new
installation and review the current bundled replay before promoting again. See the
[v0.24.0 upgrade instructions](../releases/v0.24.0.md#하위호환업그레이드) and the
[previous measured failure example](../releases/v0.23.0.md#하위호환업그레이드). No actual user
vault certificate was rewritten during this publication task.

`verification.json`. That JSON records pre-publication final source/metadata, remote CI,
ZIP/blob comparisons and independent release review. It cannot contain the later verification

After publication, `gh release verify`, all three `gh release verify-asset` checks and public
re-download hashes are recorded in a separate `post-publication.json` retained outside the
immutable release assets and referenced by the operational handoff. At record preparation
these publication checks were pending. Follow [release integrity](../release-integrity.md)
for the commands and their limits. Release-service signatures certify published-asset identity;
they do not certify build provenance, the approving person's identity or content safety.
